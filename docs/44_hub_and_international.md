# 44. ハブ・国際線・夜間滞泊・区間能力の仕様（フェーズ 4 実装）

フェーズ 4（docs/42 §3.3、計画: docs/design/impl_phase4_plan.md）で実装した新機能の仕様。
すべての機能は任意（opt-in）で、有効化していない会社・レイアウトでは従来の結果が変わらない。
`SIM_MODEL_VERSION` は変えていない。保存形式は新しい項目を使うファイルだけ版 6 になる（§7）。

## 1. 格による解放と有効化（4-01）

- 解放の定義は `src/core/economy/unlocks.ts` の 1 か所（`UNLOCKS`）:
  夜間滞泊 = 格 1（地方空港）、整備・拠点 = 格 2（拠点空港）、国際・乗継・波 = 格 3（国際ハブ）。
  区間能力は格の対象外。
- 会社の格は `game.goals.tier`。サンドボックスと目標のない会社は全解放（格 3 扱い）。
- 解放に加えて、会社の `features`（overnight / based / international / hub）で機能ごとに
  有効化が必要。設定画面で切り替え、未解放のものは「格 N（格の名前）で解放」と表示して選べない。
  建設ツールでも、未解放のエリア（出国審査・入国審査・税関・乗継保安検査）は理由付きで無効になる。
- 契約の種類（通常の折り返し / 夜間滞泊 / 拠点）は提案・受け入れ時に解放と有効化を判定し、
  未解放なら理由 `LOCKED` で受け付けない。

## 2. 夜間滞泊・拠点・整備（4-02〜4-05）

### 2.1 夜間滞泊の計画と置き直し

- 夜間滞泊契約は「夕方着・翌朝発」のペアとして計画する。到着は閉場の 240〜30 分前、
  出発は翌日の開場 +30〜+120 分（夜間運航のある都市ではカーフューの明けが下限）。
- 日付の締め（0:00）で、在泊する機体を `company.carryOver` に記録する（便名・機種・スポット・
  出発時刻・遅れ・整備の保留を含む）。運航の開始時に記録どおりスポットへ置き直し、
  合成の到着便（旅客・手荷物なし）+ 通常の出発便として再開する。
- 置き直しのスポットが使えないときは、航空会社のホームスポット → ID 順の適合スポットの
  順に置き直し、どこにも置けなければ欠航（イベント理由 `overnightNoStand`）になる。
  スポットを撤去・閉鎖したまま保存すると検証の警告 `OVERNIGHT_STAND_REMOVED` が出る。
- 駐機料と欠航の補償は、新しい会計を作らず既存の集計を通る（合成ペアの地上時間が
  0:00 をまたぐため、駐機時間として数えられる）。
- 仕様上の注意（計画 §10.2 リスク 8）: 置き直した機体の地上作業は朝に始まる
  （降機・手荷物降ろしは省略し、それ以外は通常どおり）。テストは「便名・機種・スポット・
  時刻」の一致を求め、作業の状態までは従来と一致させない。

### 2.2 滞泊の能力と朝の波

- 滞泊の能力はスポット（運用中・ネットワーク入口・サイズ適合）の数で決まる。
  契約の仮想チェックでも同じ判定を使い、能力を超える滞泊・拠点契約は受け入れ不可になる。
- 日次レポートに朝の始発の波（出発便数・最初の/最後の離陸・間隔）と、
  能力ダッシュボードに「朝の始発（1 時間）」の行を記録する。

### 2.3 拠点航空会社

- 拠点契約は所属機（2〜4 機、提案で決定）を常駐させ、期間は通常の 3 倍。
  拠点にできるのはデータで `canBase` のある会社だけ。
- 条件: 滞泊の能力、整備の能力（§2.4）、整備士の数、作業員の数（当日のピーク折り返し数 × 4）。
  条件を満たさない日が 3 日続くと撤退し、評価 −5・その会社の満足度 30 になる。
  拠点が有効な会社では、日次の満足度の平均で拠点会社の重みが 2 倍になる。

### 2.4 整備の周期と不具合

- 所属機は出発 12 回ごとに整備が要る。夜の枠は、格納庫 1 棟 = 1 機（`maxSize` 以下）、
  整備施設 = 控えの端数を翌日へ持ち越して `bays × 0.5` 機（S・M のみ）。
- 周期を超えた機体は、超過率に応じた確率で不具合になる（遅れ 30〜120 分、
  超過率 1 以上では不具合の 30% が欠航）。不具合の保留（`techHoldUntil`）より前に
  プッシュバックしない。整備中も機体は滞泊スポットに置いたまま（牽引しない）。

## 3. 国際線（4-06）

- 区域に `departureIntl`（国際出発）と `arrivalIntl`（国際到着）を追加。エリアの種類に
  出国審査・入国審査・税関・乗継保安検査を追加した。
- 区域の移動規則（`canMove`）: 出発 → 国際出発は出国審査だけ、国際到着 → 到着は入国審査だけ、
  到着 → 出発と国際到着 → 国際出発は乗継保安検査だけが越えられる。既存の枝は変えていない。
- ゲートの施設属性 `routeType`（domestic / international / swing、無指定は国内）。
  国際・兼用ゲートだけが国際側の搭乗・降機エリアを持つ。兼用ゲートは使うたびに
  種類を記録し、切替には 600 秒の間隔が要る。国際便を割り当てるゲートがない場合は
  計画エラー `INTL_GATE_MISSING` になる。
- 旅客の工程: 国際の出発はチェックイン → 保安検査 → 出国審査 → 搭乗
  （国際便は来訪が早く、搭乗開始も 15 分早い）。国際の到着は降機 → 入国審査 →
  手荷物受取 → 税関 → 出口。通過は `ciq`（emigration / immigration / customs）に記録する。
- 国際の処理が使えるのは「機能が有効 + 審査エリアが揃い、国際ゲートが国際区域に
  つながっている」ときだけ。揃っていない路線は従来どおり計画エラー
  `INTERNATIONAL_PROCESSING_REQUIRED` になる。
- 検証の警告: `INTL_EMIGRATION_UNLINKED` / `INTL_IMMIGRATION_UNLINKED` /
  `INTL_CUSTOMS_UNLINKED`（審査エリアが両側の区域につながっていない）、
  `INTL_GATE_ZONE` / `SWING_GATE_ZONE`（国際・兼用ゲートが国際区域につながっていない）、
  `INTL_LOCKED`（国際の設備があるのに機能が未解放・無効）。
- 実装中に見つけて直した従来側の不具合 2 件:
  (1) 旅客の到着処理で、新しい工程（審査など）が施設の待ち行列に入らず止まっていた。
  (2) 不変条件 P3 の窓口数の数え方に `booths`（入国審査の窓口）が抜けていた。

## 4. 乗継旅客・MCT・乗継手荷物・波（4-07〜4-10）

### 4.1 最小乗継時間（MCT、4-08）

- 解析は `src/core/terminal/hub.ts` の `analyzeHub`。到着ゲートごとに 1 回だけ
  ダイクストラで全エリアへの最短時間を求め（配置が変わるまで保持）、
  ゲートの組ごとの MCT = max(30 分, 5 分切り上げ(歩行 + 境界の目安 + 降機 10 分 + 締切 10 分 + 余裕 5 分))。
  境界の目安は「処理時間 × 5 人 / 窓口数 + 300 秒」で、窓口 0 の境界は通れない。
- 乗継客は一般区域へ出ないので、経路探索では一般区域と出発保安検査を対象にしない
  （一般区域を回る経路は MCT に数えない。実装中にテストで見つけて直した）。
- 空港の MCT（種類ごと）は使えるゲートの組の最大値。経路がない種類は null で、
  その種類の乗継は計画しない（`MCT_UNAVAILABLE`）。
- 能力画面に種類ごとの MCT（最大・中央値）、1 日の乗継旅客（計画）、
  バンク時の最大機数・乗継処理能力を表示する。

### 4.2 乗継の計画（4-07）

- 契約の `transferShare`（0〜0.5、既定 0）の割合で、到着旅客の一部を乗継にする。
  候補は MCT 以上・最大乗継時間（既定 240 分）以内の出発便で、同じ航空会社か、
  相手の契約にも乗継率がある場合だけ。空席に比例して配り、地元の旅客は減らさない。
  乱数は便ごとの専用の種で、会社の乱数の流れは変えない。
- バンク（波）: 契約に `bankId` があると、到着・出発が会社の `hub.banks` の
  時間帯に集まる（計画の段階で寄せる）。

### 4.3 乗継旅客の移動と失敗

- 乗継グループは到着便の降機で先に降り、出発便のグループとして作る
  （到着便の人数保存のため、到着便の索引にも入れる二重の登録）。
  空港へのアクセスは使わない（`accessDone`）。手順は種類ごと:
  DD = 乗継保安検査 → ゲート、DI = 乗継保安検査 → 出国審査 → ゲート、
  ID = 入国審査 → 乗継保安検査 → ゲート、II = 乗継保安検査 → ゲート。
  乗継旅客は税関を通らない。
- 搭乗できれば接続成功、締切に間に合わなければ乗り遅れとして、乗継専用の補償
  （1 人 600）を払う。出発便の締切後に降機した乗継はその場で乗り遅れになる。
  到着便の欠航などで現れなかった分はノーショーとして締切時に数える。
  日次レポートに発生・接続成功・乗り遅れ・ノーショーを記録する。
- 人数の保存は不変条件 T1〜T3 で検査する（到着 = 退出 + 乗継、など）。

### 4.4 乗継手荷物（4-09）

- 乗継の手荷物は到着便の手荷物として作られ、到着の搬送が終わる時点で受取所へ
  送らず、出発便の預け手荷物に付け替える（付け替えは 1 回だけ、不変条件 B1）。
  その後は通常の仕分け・積込の流れに入る。乗り遅れた旅客の手荷物は、
  出発便の締め処理で通常どおり降ろされる・積み残される。

## 5. 道路・線路の区間能力（4-11・4-12）

- レイアウト設定 `accessCapacityModel: 'segment'` で opt-in。既定は従来の集約モデルで、
  設定のないレイアウトの結果は変わらない。
- 道路の区間の能力は `capacityPerHour`（明示）か `lanes × 900` 台/時。
  出入口から車寄せ・駐車場までの経路は最も太い経路（maximin）で選び、
  目的地の能力 = min(出入口のボトルネックの合計, 目的地の辺の能力の合計)。
- 運航中の遅れは区間ごとに BPR 型（自由走行時間 × 0.15 × (台数/能力)^4、上限あり）で、
  1 グループは最も空いている出入口の経路を使う。
- 鉄道: 区間の能力は明示か、単線 4・複線 12 本/時（`tracks`）。駅の能力は
  `platforms × 6` 本/時（既定 2 面）。実効本数 = min(宣言本数, 出入口のボトルネック, 駅の能力)。
  区間モデルのときだけ、駅からターミナルへの連絡通路の能力も鉄道の受け入れ上限に
  入れる（4-12）。不変条件 E1 で区間の台数と遅れの健全性を検査する。

## 7. 保存形式（4-13）

- 版 6 の項目一覧と読み込み規則は docs/21・docs/27 に追記した。要点:
  新項目を使うファイルだけ版 6 を書き、版 6 未満を名乗るファイルに新項目があれば弾く。
  `features` のない会社への読み込みでは、持ち越し・所属機・ハブ設定を落として取り込む。

## 8. 既知の制約・未検証

- 翌朝持ち越し便の「見積りの毒」が毎日自己増殖して出発できなくなる不具合を修正した（2026-11-18、実セーブで再現）。
  持ち越しの記録が前日の出発見積りの遅延（depDelaySec）を無制限に引き継ぎ、夜間待機で翌朝にずれた見積りが
  さらに翌日の見積りになった。搭乗開始が見積り基準のため、整備済みの機体でも搭乗が翌日まで始まらず、
  締めで再び大きな遅延が記録されて永遠に直らなかった。対策は 2 点: 置き直し時に引き継ぐ見積りを当日中に収める
  （overnight.ts）、見積りが現在より 3 時間を超えて先で予定を過ぎている便は整備完了時点で搭乗を始める
  （passengers.ts、夜間待機の指定がある便は除く）。実セーブ（21 機滞留）で 3 時間後の離陸が 4 機 → 23 機に回復することを確認。
- 翌朝持ち越し便の出発準備完了判定を修正した（2026-11-18、OD 計画）。
  持ち越し機は降機・荷下ろしを生成しないため、(1) 完了判定のタスク数一致と
  (2) 清掃・ケータリング・搭乗・積込の依存（降機・荷下ろし完了が前提）の両方で
  永遠に未完了になっていた。作業生成時に省略分を機体の `skippedTasks` に記録し、
  「要求されていない作業」として完了判定・依存判定で扱う。必須作業の欠落は
  未完了のまま。通しテスト（置き直し → 地上作業・搭乗 → プッシュバック → 離陸、
  持ち越し 2 機＋通常便 1 機）を tests/unit/sim/overnight.test.ts に追加した。

- 乗継のテストは単一ターミナルの配置で確認した。ターミナル間の乗継
  （連絡設備の利用率 `hubStats.byLink` の蓄積を含む）は実装済みだが、
  2 ターミナルの波の完了テストは未実施（4-10 の完了条件の一部が未検証）。
  連絡設備の利用率の画面表示も未実装（集計は保存される。表示はフェーズ 5 の 5-03）。
- 整備の枠の計算で、整備施設の端数の持ち越し（`maintenanceCredit`）は締め処理で使う。
  能力の単体値（`maintenanceCapacityPerNight`）は端数なしの値。
- II（国際 → 国際）の乗継には、国際到着側の区域にある乗継保安検査が要る
  （国内側の設備だけでは MCT が null になる）。
- E2E は全 22 ファイルを直列で再実行した（2026-11-18）。フェーズ 4 の新規
  spec（unlocks・phase3-traffic・terminal のエスカレーター回帰を含む）と
  access・busgate・capacity-nav・editor・ground・levels・operations は全件合格。
  残る失敗 11 件（dayloop 3、runway 5、gamemodels・management・project 各 1）は、
  実行環境（共有 1.5 CPU の VM）で 1 日分の運航やキャンバス操作が repo の
  E2E タイムアウト 30 秒に収まらないことが原因で、単体・統合テストで同じ
  処理が合格していることから、フェーズ 4 の回帰とは判断していない。
  速い環境での再確認が望ましい。
