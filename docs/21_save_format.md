# 21. 保存形式・バージョン管理・移行（Phase 10）

実装: `src/core/io/project.ts`（形式・検証・復元）、`src/editor/project.ts`（保存先・操作）、`src/ui/ProjectPanel.tsx`（画面）。

## プロジェクトファイル（`format: "skyport-project"`, `formatVersion: 1`〜9）

**版の書き方**: バス搭乗・ゲーム/天候・日次履歴など既存の任意項目は `formatVersion 2`。多層道路・階層接続・階層施設／建物内設備・ターミナル間連絡リンクを含むときは `formatVersion 3`。該当する新項目がなければ 1 または 2 のまま書く。`versions.format` も同じ値。現在は 1〜9 を読み（`PROJECT_FORMAT_MAX_READABLE = 9`）、10 以上は拒否する。版 1/2 を名乗るファイルに版 3 の項目がある場合も拒否し、旧アプリが未知の設備を誤読しないようにする。`PROJECT_FORMAT_VERSION` は基本の版 1、`PROJECT_FORMAT_VERSION_2 = 2`、`PROJECT_FORMAT_VERSION_3 = 3`、`PROJECT_FORMAT_VERSION_4 = 4`（フェーズ 2）、`PROJECT_FORMAT_VERSION_5 = 5`、`PROJECT_FORMAT_VERSION_6 = 6`、`PROJECT_FORMAT_VERSION_7 = 7`、`PROJECT_FORMAT_VERSION_8 = 8`、`PROJECT_FORMAT_VERSION_9 = 9`（機能H、搭乗橋）。新項目は任意で、旧セーブの不足項目は従来どおり読める。厳格な形の検査は `checkLayout`、`checkSim`、`checkJournal` で行う。旧運航状態の閉鎖理由台帳は閉鎖配列と発生中の障害から再構築し、外部遅延は運航に実際に加えた秒数だけを保存する。

`Flight.externalDelaySec` と分析記録の `arrivalExternalDelaySec` は任意の追加メタデータとして保存する。便の実績時刻やシミュレーションの進行条件は変えないため、この項目だけでは `formatVersion` を上げない。旧保存で項目がない場合は 0 秒として扱う。`FlightRecord` の形式は変更しない。便別レビューの締め時点の原因・実時刻・機体状態・作業・施設名、航空会社評価要素・EMA/満足度前後・不満/要望は `DayReview` に集約し、日ごとの IndexedDB 履歴の `review` に保存する。会社状態やプロジェクトJSONには追加しないため、プロジェクト保存形式・シミュレーションモデルの版は上げない。古い保存済みレビューにない項目は推測せず欠落として表示する。

| 項目 | 内容 |
|---|---|
| `name` / `savedAt` | プロジェクト名・保存日時 |
| `versions` | 保存形式・レイアウトのスキーマ・機種カタログ・3D アセット・シミュレーションの版（別々に持つ） |
| `layout` | 空港レイアウト（敷地・座標・滑走路・誘導路と接続・スポット・施設・ターミナル内部・道路・駐車場・駅） |
| `company` | 会社（資金・収支・日報・契約・保有機材と座席・料金・営業時間・工事・アクセス） |
| `catalog` | 使用機種のデータ（保存時の値）とその版 |
| `assets` | 機種 ID → 3D アセット ID と、アセットの版 |
| `scenarios` | シナリオ（初期条件・機種データ・シード・障害の条件・シミュレーションの版・変更履歴・結果と KPI） |
| `sim` | 運航中に保存したときの運航状態（`SimState` 全体と運航中の会社）。建設モードでは `null` |
| `journal` | 任意。日次締めで FlightRecord から更新するスポッティング・累計記録。シミュレーション状態とは独立 |

`SimState` には、便・機体（位置・状態・経路）、滑走路・スポット・誘導路の占有と予約、旅客グループ、手荷物、地上作業とユニット、
設備の状態、天候・障害と復旧状況、閉鎖対象ごとの独立した閉鎖理由、便ごとの外部遅延実秒数、乱数の状態、分析の記録が含まれる。

### 版の扱い

| 版 | 定数 | 変わるとき |
|---|---|---|
| 保存形式 | `PROJECT_FORMAT_VERSION = 1` 〜 `PROJECT_FORMAT_VERSION_9 = 9`（読込上限 `PROJECT_FORMAT_MAX_READABLE = 9`） | 新しい任意データを含むファイルだけ版を上げ、旧アプリが誤読しないようにする |
| 機種カタログ | `CATALOG_VERSION`（現在 2026.11.1） | 収録機種・値を変えたとき |
| 3D アセット | `ASSET_VERSION`（現在 2026.11.0） | 3D の形を変えたとき（表示だけに影響） |
| シミュレーション | `SIM_MODEL_VERSION = skyport-sim-10.11` | 運航の計算を変えたとき |

### 版の方針（Phase 11 で明文化。詳細は [22](22_geometry_architecture.md) §7）

- Phase 11 はどの版も上げていない。Phase 12 で `SCHEMA_VERSION` を 3 に上げ、自由形滑走路・実寸 `dims`・番号接尾辞・磁気偏角・判定ルールを追加した。
- Phase U の階層交通項目はすべて任意項目として追加し、内部 `SCHEMA_VERSION = 3` を維持した。多層交通・ターミナル間連絡リンクを含むプロジェクトは外側の `formatVersion 3` として保存する。`SIM_MODEL_VERSION` は変更していない。
- 旧版で誤って形式 1/2 と記録された施設の階層・建物内配置は、他の階層交通項目を含まない場合に限り読み込み時に形式 3 へ移行する。階層道路や連絡リンクの版不一致は引き続き拒否する。
- 階層のないノードは地上、連絡設備のないレイアウトは従来どおりとし、旧レイアウトを読み込むための必須書換えはない。内部スキーマ版は作成または最後に構造移行した版のまま保持する。
- 新アプリは `versions.layoutSchema > SCHEMA_VERSION` を拒否する。旧アプリは新しい階層・接続情報を正しく扱えない可能性があるため、多層設備を含むデータを旧アプリで編集しないこと。詳細は [27](27_migration_and_compatibility.md)、[34](34_vertical_transport.md)。
- 2026-CF（誘導路幅の F 区分）: `widthClass` に `'F'` を追加し旧 `codeF` を廃止。読み込み時に版に依らず（L ＋ codeF）→ F へ正規化し、`SCHEMA_VERSION`・`SIM_MODEL_VERSION` は上げない（導出・運航結果が不変のため）。詳細は [27](27_migration_and_compatibility.md)。
- **Phase 12 の不具合修正（C1・M1）は `SIM_MODEL_VERSION` を上げない**（PO 承認済み）。C1（連続横断で横断許可が上書きされ滑走路の占有が漏れる、Phase 2 からの不具合）は、漏れが起きる運航だけが変わり、起きない運航は 1 ビットも変わらない。
  修正前に保存された運航状態に漏れた占有がある場合は、読み込み時に修復して警告を出す（`heldCrossings` は任意項目で、無い保存は従来どおり読める。旧版のアプリは `heldCrossings` を無視して従来どおり漏れる）。
  以前に漏れた運航を記録したシナリオの結果は、同じ版の表記のまま再実行すると結果が変わる。
- `SIM_MODEL_VERSION` は **既存の（現行版のレイアウトで表現できる）レイアウトの運航結果が変わるときだけ** 上げる。上げると保存済みの運航状態は復元されず、建設モードで開く。
  この規則はゴールデンで機械的に守る: 運航ゴールデンは、版を上げずに内容を変える再採取を拒否する（docs/22 §5）。
- `skyport-sim-10.1` では航空会社別ホーム優先とバスゲート選択を統一し、`skyport-sim-10.2` では通常生成グループの約 5% に決定的な段差なし経路需要を割り当てた。`skyport-sim-10.3` を経て、`skyport-sim-10.4` ではフェーズ 1 の不具合修正（欠航便の手荷物の終端処理など。docs/42 §5.1）を反映した。`skyport-sim-10.5` では 5-16 T5（旅客の実移動: ポータルに接続した交通施設とターミナル入口/出口の間を PaxGroup が実際に歩く `accessWalk`）を反映し、ゴールデンを再取得した。`skyport-sim-10.6` では羽田・成田就航の実在航空会社 20 社のカタログ追加と SK（架空のスカイライン航空）から実在の SAS（スカンジナビア航空）への置換により、market あり会社の提案列と会社データを含む運航フィンガープリント 2 件（city core / sample airport）が変わったため版を上げ、ゴールデンとフィンガープリントを再取得した。`skyport-sim-10.7` では動く歩道（ターミナル内エリア種別 `movingWalkway`）と 5-25 Work Order を反映した。`skyport-sim-10.8` では 5-19 のシミュレーション粒度の既定を集約方式（`serviceGranularity: 'aggregate'`）へ変更した（店舗のある空港では同一セーブ再開後の結果が変わりうるため版上げ。既定変更の影響は legacyFingerprint で不変を確認済み）。`skyport-sim-10.9` ではターミナル隣接の自動接続（接しているターミナル同士は明示リンクなしで接続扱い）とスポット寸法・サイズ区分の見直し（S 2×2／M 3×2／L 4×4、コードA/B=S・C=M・D/E/F=L）を反映した（接しているターミナルがある既存レイアウトでは旅客の到達可能性と運航結果が変わりうるため版上げ。フィンガープリントは挙動同等性を確認のうえ再取得）。`skyport-sim-10.10` では夜間（22時〜6時）の着陸料に割増（×1.3、BALANCE.fees.nightSurcharge）を導入し、防音工事助成（費用でレベルを上げると住民満足度が即時回復し、騒音ポイントの日次影響が緩和される。未実施=Lv0では従来と同一）を追加した（夜間着陸を含む運航では収支が変わりうるため版上げ。フィンガープリントは挙動の同等性を確認のうえ再取得）。同じ 10.10 に、海上移転係数（格 4 以上で騒音ポイントの効きが段階的に軽減。格 3 以下では ×1.0 で従来と同一）、住民向け施設（ショッピングモール・文化ホール・公園。置くだけで住民満足度に日次プラスを与え、運航結果には影響しない）、騒音対策費の拠出（1 日 1 回の即時回復。状態は任意フィールド `CityConfig.lastNoiseContributionDay` で旧セーブ互換）も含む。`skyport-sim-10.11` では乗客生成の見直し（PAX）を反映した: 来港分布を空港の規模（格を S/M/L の3ステージに丸めたもの）に連動させ（S は従来と同一）、生成リードをステージ別の最早出現 + 30 分に連動（S は従来どおり 3 時間）、ラウンジ滞在を「搭乗開始まで」から分布で引いた希望時間と余裕の小さい方に変え、乗継グループにもラウンジ立寄りを追加した（規模の大きい空港、またはラウンジのある空港では旅客の出現・滞留が変わるため版上げ。S ステージかつラウンジのない空港では従来と同一）。**現在の `SIM_MODEL_VERSION` は `skyport-sim-10.11`**。ターミナル間連絡設備・垂直移動設備の時間当たり能力より大きい旅客グループは、複数の時間帯に分けて通路へ入る。10.2 以前の進行中シミュレーションは復元せず建設モードで開く。レイアウト・会社・過去の日報は保持する。同一モデルの保存で `airlineStandHomes` が欠けている場合は空の当日割当に移行する。
- レイアウトの版を上げると、`exportLayout` と `serializeProject` の出力（`schemaVersion` を含む）が変わる。ゴールデンには `schemaVersion` を除いた版非依存のハッシュがあり、
  版更新の前後でこれが一致すれば、版番号以外の変化はない。

### 版 4（フェーズ 2。実装済み）

次のどれかを含むときだけ `formatVersion 4`（`versions.format` も 4）で書く。**どれも含まないプロジェクトは従来の版（1〜3）のまま書き、バイト列は変わらない**（`tests/unit/projectFormat4.test.ts`、ゴールデン）。

| 項目 | 場所 | 検証（読み込みエラーの条件） |
|---|---|---|
| `taxiMode: 'block'` | `layout`（シナリオのレイアウトを含む） | `'block'` 以外 |
| `city.nightOps`（最終出発時刻など） | `company`（シナリオ・運航中の会社を含む） | 範囲外・型違い（最終出発時刻 1200〜1305 分、上空待機 0〜120 分、警告の前倒し 0〜120 分、`inboundPolicy` は `originHold`） |
| `state.taxiBlocks`（区間の占有・向きの確保・対向待ち・優先・統計） | `sim.state` | 存在しない区間・回廊・機体、終了状態の機体、空・重複、向き、統計の型、`taxiMode` が `block` でないレイアウト |
| `Flight.nightHold` | `sim.state.flights` | 種類・時刻の不正、`releaseAt < decidedAt`、`city.nightOps` のない会社 |

- `taxiBlockTiles`・誘導路の `blockMaxAircraft` は `taxiMode` が欠落のときに従来方式の運航へ影響しないため、これらだけでは版を上げない（範囲 4〜40 / 1〜10 の検証は常に行う）。
- 理由: 旧アプリ（最大 3 まで読める）が上の項目を無視して従来方式で運航を続けると、区間の途中状態が不変条件に反して読まれるため。4 にすれば旧アプリは「新しい版」として拒否する。版 1〜3 を名乗るファイルに版 4 の項目がある場合も拒否する。
- `SCHEMA_VERSION`（レイアウト）・`state.version`・`SIM_MODEL_VERSION` は上げない（任意項目の追加だけ・新方式は opt-in で既存レイアウトの結果は変わらない。`tests/unit/sim/legacyFingerprint.test.ts` とゴールデンで確認）。旧データの移行は不要（欠落 = 従来方式）。判断の経緯は [design/impl_phase2_plan.md](design/impl_phase2_plan.md) §1.6。
- 区間の構造（`ctx.blocks`）・経路 → 区間の対応は配置と経路から作り直す派生データで、保存しない。

### 版 8（ラウンジ。実装済み、PR #51）

レイアウト（シナリオのレイアウトを含む）にエリア種別 `lounge`（ラウンジ、`layoutUsesFormat8`）を含むときだけ `formatVersion 8`（`versions.format` も 8）で書く。含まないプロジェクトは従来の版（1〜7）のまま書く。ラウンジは席数（`props.seats`）を持つターミナル内エリアで、保存形式以外の版（`SCHEMA_VERSION` 等）は上げない。

### 版 9（搭乗橋 PBB・複合連絡施設・AGT。機能H・J-2・I）

レイアウト（シナリオのレイアウトを含む）に施設種別 `boardingBridge`（搭乗橋）、`connectionFacilities`（複合連絡施設のグルーピング記録）、または AGT の項目（施設種別 `agtStation`、`agtSystems`、`agtSegments`）を含むときだけ `formatVersion 9`（`versions.format` も 9）で書く（いずれも `layoutUsesFormat9` で判定）。含まないプロジェクトは従来の版（1〜8）のまま書く。`SCHEMA_VERSION` は 3 を維持し、`SIM_MODEL_VERSION` も上げない（明示 PBB の無いゲートは従来の `jetBridge` から tunnel1 相当を読み取り時に合成し、搭乗/降機速度が従来定数と一致するため運航結果が変わらない。複合連絡施設は通路段＋両端の垂直エリアを束ねる編集メタデータであり、部品自体は従来のエリア＋リンクで、旅客シミュレーションは記録を読まない。AGT は TerminalTransitLink とは別の記録で、辺は経路探索 `findTerminalTransferRoute` にだけ合成されるため、AGT の無いレイアウトの結果は変わらない）。版 8 以下を名乗るのに版 9 の項目を含むファイルは拒否する。`connectionFacilities` の参照切れは読み込みでは拒否せず、検証の `CONNECTION_FACILITY_DANGLING`（エラー）で報告する。AGT の記録も形だけを読み込み時に検査し、参照切れ・パラメータ範囲は検証の `AGT_*` で報告する。複合連絡施設の通路段は AGT セグメント（`segment.kind = 'agt'`）も束ねられる。

### 架空会社の就航制限・持ち替え（機能F。版上げなし）

カタログの航空会社・目的地に `fictional`（実在しない会社・都市）フラグを追加し、空港の格が閾値（格 3）以上のとき架空会社の新規提案を架空の目的地だけに制限した。また、既存の架空会社の有効契約は契約パネルから実在会社へ付け替えできる（変えるのは契約の `airlineId` だけで、条件はすべて不変）。
- `formatVersion` は上げない: `fictional` はカタログ（コード側データ）の属性でセーブには入らず、付け替え結果も既存フィールドの値変更にすぎない。持ち替え可能かどうかの案内表示は会社の状態から決定的に導出する派生表示で、保存項目は追加しない。
- `SIM_MODEL_VERSION` も上げない: 制限は提案生成（運航結果ではない）にのみ効き、目標のない会社・格が閾値未満の会社では提案列も従来と変わらない。

### 地下だけの建物（機能G。版上げなし）

ターミナルの任意項目 `floorRangeMin` / `floorRangeMax`（エリアを置ける相対階の範囲）を追加し、地下（mapLevel < 0）へのターミナル単独配置を解禁した（CDG 型の地下コンコース再現）。
- `formatVersion` は上げない: 追加は props の任意項目と配置・検証規則の変更だけで、項目が無いプロジェクトのバイト列・解釈は従来と変わらない（floorRange 欠落 = 従来範囲 [-3, 階数 − 1]）。旧アプリで地下ターミナルを含むセーブを開くと配置検証で弾かれるが、読み込み自体は可能。
- `SIM_MODEL_VERSION` も上げない: 地下ターミナルは旧版では作れなかったレイアウトであり、既存レイアウトの到達可能性・能力は変わらない。高さ区間（`facilityVerticalRange`）の変更も地下ターミナルに限られる。

## 機種データの固定（カタログ更新との互換性）

- 保存時に、使っている機種（契約・保有機材・運航中の機体・シナリオ）のデータをそのまま保存する。
- 開いたプロジェクトは保存時の機種データで運航する（`catalogPin`。保存データにない機種は現在のカタログから補う）。
- 最新カタログとの差分はプロジェクト画面で確認でき、「最新カタログを適用」したときだけ切り替わる（運航中は不可）。
- シナリオも保存時の機種データで実行する。「最新カタログで再実行」の結果は `catalogUsed = current` として別に残し、過去の結果は上書きしない。

## 読み込みと検証

読み込みは必ず **検証 → すべて通ったら適用**。エラーが 1 件でもあれば何も変更しない（開いているプロジェクトは壊れない）。

| 検証 | 結果 |
|---|---|
| JSON として読めない、形式・版が違う、新しい版 | エラー |
| 必須項目・型（名前・版・レイアウト・会社・機種データ） | エラー |
| ID の重複（同種・異種のエンティティをまたいで）、キーと ID の不一致 | エラー |
| 参照切れ（誘導路・道路の端点、ターミナル内エリアの建物、運航状態の機体 → 便・スポット・滑走路、スポット割り当て） | エラー |
| シナリオの形式・ID 重複・レイアウト・会社・機種データ | エラー |
| 運航状態を実際に復元して不変条件を検査（同じスポットに 2 機など） | 不整合があればエラー |
| 自由形の滑走路・磁気偏角・ルールの値の不正（`alignment` が未知、方位・長さ・`dims`・`designatorSuffix` が範囲外など。**新しい項目だけを対象とし、従来形の滑走路には新しい検査を足さない**） | エラー |
| 不明な機種 ID（保存データにもカタログにもない） | 警告。データは残し、未解決の機種（汎用の値、適合性は unknown）として扱う |
| 登録されていない 3D アセット | 警告。代替の形で表示 |
| 保存時の機種データの版が現在と違う、アセットの版が違う | 警告（差分は画面で確認） |
| シミュレーションの版が違う運航状態 | 警告。運航状態は復元せず建設モードで開く |

## 旧形式の移行

- **レイアウトだけのファイル**（Phase 1〜6 の書き出し、`format: "skyport-layout"`、スキーマ v1/v2）: これまでどおりレイアウトの置き換えとして読み込む
  （建設費の精算・元に戻すが効く）。会社は開いているものを使う。
- **旧版の会社データ**（保有機材の設定がない Phase 6 以前）: 航空会社の初期の保有機材を補い、契約で使っている機種
  （旧形式の汎用機材 `regional70` / `narrow180` / `wide300` を含む）をそのまま保有機材に加える。汎用機材を実在の機種に置き換えない。
- 汎用機材は汎用のまま運航でき、プレイヤーが契約の機種を変えたときに適合性・座席・地上支援が再判定される。

## 運航状態の復元

- 復元するもの: `SimState` 全体（機体・便・旅客・手荷物・作業・ユニット・設備・占有・予約・障害・乱数・記録）と運航中の会社。
- 文脈（ネットワーク・経路探索の情報）はレイアウトと機種データから作り直す。
- 復元後は一時停止の状態で再開する。続きを進めた結果は、中断しなかった場合とビット単位で同じ（テストで確認）。
- 時計の端数（フレーム間の補間）は保存しない。

## 保存先・バックアップ

- 保存先はブラウザの localStorage（`skyport.projects.v1` = 一覧、`skyport.project.v1.<ID>` = 本体）。ブラウザ・端末ごとに別。
- 作業中の状態は従来どおり自動保存（`skyport.layout.v2`・`skyport.company.v1`）し、開いているプロジェクト名と固定した機種データも
  `skyport.projectMeta.v1` に自動保存する。
- バックアップ・別端末への移動は「JSON に書き出し」。ファイル名は `skyport-<名前の英数字>-<日時>.skyport.json`（日本語の名前はファイルの中に残る）。
- サンプル空港・運航中の保存データは 1 件あたり数百 KB（運航 5 時間で約 660 KB を計測）。localStorage の容量（ブラウザにより約 5 MB）を
  超えると保存に失敗し、その旨を表示する。

## 日ごとの履歴（Phase 12B-2。保存形式の版は変えない）

- 日次の締めのたびに、**その日の朝（締めの直後）の建設モードの復元点**を IndexedDB に残す（DB `skyport`・ストア `dayHistory`・キー `<プロジェクトのスロット ID | "unsaved">:<締めた後の会社の日>`）。値 = `{ day, savedAt, cash, rating, operatingProfit, review（振り返りのデータ）, projectJson }`。`projectJson` は通常のプロジェクトファイル（項目に応じて `formatVersion` 1〜3）で、`sim: null`・`scenarios: []`（運航状態とシナリオは入れない）。完了した工事は、運航を終えたときと同じようにレイアウトへ反映済み。
- localStorage は小さい（約 5 MB。運航状態入りの 1 件が数百 KB）ため IndexedDB を使う。使えない環境（`indexedDB` がない・開けない）ではメモリに置き、1 回だけ「履歴はこのタブを閉じると消えます」と表示する。`DayHistoryStore` 抽象（`IndexedDbHistoryStore` / `MemoryHistoryStore`）は `src/editor/dayHistoryStore.ts`、IndexedDB は editor / ui 層のみ（core には置かない）。
- **保持規則**（`core/io/historyPolicy.ts` の純関数 `retainHistoryDays`、書き込みのたびに整理）: 現在の日より先の履歴は捨てる（戻ってやり直した別の経過の残り）／直近 7 日はすべて／それより古いものは 7 日ごとの区間につき 1 件（区間で最も新しい日）で新しい区間から最大 8 件。1 プロジェクトあたり最大 15 件。
- **戻す**: 「この日の朝に戻る」→ `validateProject`（読み込みと同じ検証）に通ったときだけ適用（レイアウト・会社・機種データの固定）し、失敗したら開いているプロジェクトは変えない。建設モードのみ。**現在のシナリオは保つ**（履歴に含めないため）。
- 未保存のプロジェクトは `unsaved` に残り、保存すると新しいスロット ID に付け替える。新しいゲーム・JSON の読み込みで `unsaved` は消す。スロットを削除するとそのスロットの履歴も消す。
- **書き出し（JSON）に履歴は含めない**（端末・ブラウザごと）。サイズ（計測: サンプル空港＋サンドボックス会社、2 日分）: `projectJson` は 1 件あたり約 77〜78 KB、振り返りのデータは約 2〜3 KB。15 件でも約 1.2 MB で、IndexedDB の容量には十分収まる。

**フェーズ 1（K-1）の追加項目**: リモートスポットの `Stand.terminalId`（所属ターミナル）は任意項目で、レイアウトに 1 つでもあれば `formatVersion 2`（`layoutUsesFormat2`）。**版は上げない**（旧版のアプリは属性を無視して従来の自動選択をするだけで壊れない）。欠落 = 従来の自動、null は保存しない（操作で null を渡すとキーを削除）。読み込み時は、施設がない・ターミナルでない・文字列でないものを `スポット <id> の所属ターミナル（terminalId）が不正です` で拒否する（`checkLayout`）。ターミナルの削除時は `finalize` が参照を掃除する。決定規則・検証は docs/29 §3.1・docs/26 §3b。`SIM_MODEL_VERSION` は変更していない（旅客生成後のゲート固定は運航側の挙動で、docs/42 §5 のとおり版の扱いは 1-23）。

**フェーズ 1（E-3）の運航状態**: 機体の任意項目 `requestedStandId`（運航者が `reassignStand` で指定したスポット）は、値があるときだけ書く（割り当てに成功したら消える）。読み込み時に `運航状態: 機体 <id> の指定スポット（requestedStandId）が不正です` として、文字列でない・レイアウトにないスポットを拒否する。版は上げない。

**Phase 12B-3a Part B / 3b**: 会社の `game`・`airlineEval`・`goals`・`city`、運航状態の `wx` を使うファイルは `formatVersion 2`。`checkGameFields` と `checkWxState` で既存項目を検査し、都市は `isCityConfig` で版・人口・距離・品質・住民満足度を検査する。`importCompany` は不正な任意項目を捨て、`validateProject` は不正な `city` を含むプロジェクトを拒否する。詳細は [docs/30](30_game_models.md)・[docs/31](31_city_models.md)。
