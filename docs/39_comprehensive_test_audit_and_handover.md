### 1.2 監査用テストの実行方法

監査用テストは通常の `npm test` / `npm run test:e2e` / CI に**含めていない**（別設定）。型検査と lint の対象には入る。

| コマンド | 内容 |
|---|---|
| `npx vitest run -c vitest.audit.config.ts` | 合格する監査テスト（`tests/audit/*.audit.test.ts`） |
| `AUDIT_KNOWN=1 npx vitest run -c vitest.audit.config.ts` | 未解決の不具合の再現（`tests/audit/known-issues/`）。**失敗するのが現状** |
| `npx playwright test -c playwright.audit.config.ts --trace off` | ブラウザ監査（`tests/audit/e2e/`、ポート 4174） |
| `AUDIT_KNOWN=1 npx playwright test -c playwright.audit.config.ts --trace off` | ブラウザの不具合の再現（`tests/audit/e2e-known/`）。**失敗するのが現状** |

長時間のシミュレーションを含むため、他の重い処理と並行すると時間切れになることがある。その場合は単独で再実行して切り分ける。乱数シードはテスト名または失敗メッセージに出る。

## 6. 仕様・設計の欠落や矛盾（E）

### 6.1 リモートスポットとターミナルの対応

現在の決定規則（監査テスト `b_multiTerminal` で確認）:

- 固定スポット: スポットに対応するゲート（複数あれば ID の小さい方、検証 `STAND_MULTIPLE_GATES`）→ そのゲートの所属ターミナル。
- リモートスポット: `remoteBoarding: 'bus'` は指定したバスゲートのみ（代替なし）。`'none'` はなし。`'auto'`（旧データを含む）は使えるバスゲートのうち直線距離が最も近いもの（同距離は ID の小さい方、定義順に依存しない）。

**レイアウトと閉鎖の状態が同じなら一意に決まる。ただし `'auto'` では時間とともに変わり得る。** 確認した例: 同じスポットで到着便は T1 を使い、T1 のゲートが閉鎖された後の出発便は T2 を使った。このとき T1 の中にいた旅客は行き先が T2 に変わり、連絡設備がなければ乗り遅れる（閉鎖の時刻により 3〜138 人）。1 つの出発便の旅客が 2 つのターミナルに分かれる（docs/35 §7.1 と緊張関係）。一方、docs/29 §1 と docs/32 §3 は再選択を明示的に許している。

「リモートスポットと紐づくターミナルを一意に定めたい」という要望に対する選択肢（決定は未了、実装方式は指定しない）:

1. スポット割当の時点でゲートを決め、搭乗開始前にそのゲートが閉鎖された場合を除いて到着・出発とも維持する。
2. 使えるバスゲートを持つターミナルが 2 つ以上あるとき、`'auto'` のリモートスポットを検証エラーにして明示指定を求める。
3. 旅客を生成した後はゲートを固定する。
4. スポット自体にターミナルの属性を持たせる。

どれも旧データ（`'auto'`）の結果を変える可能性があるため、互換の扱い（版・移行）と合わせて決める必要がある。

**決定済み（フェーズ 1、1-11 / K-1。docs/implementation/completed/phase1_plan.md）**: 上の 3 と 4 を採る。リモートスポットに任意の `Stand.terminalId`（所属ターミナル）を持たせ（欠落 = 従来の自動。保存形式の版は上げない）、旅客を生成した後はバスゲートを固定する（閉鎖中は再開を待ち、締切までに再開しなければ `facilityClosed`）。決定規則は `resolveBusGateForStand` の 1 つで、計画・検証・画面・運航が共有する。仕様は docs/29 §3.1・docs/32 §3・docs/35 §2.3・§7、検証コードは docs/26 §3b、保存は docs/21。選択肢 1 は 3 に含まれ、2 は採らない（`'auto'` のスポットは従来どおり使える）。実装の状態（運航側は Track S）は docs/42 を参照。

| # | 観察 | 影響 |

### 11.2 「滑走路まで 1 本の経路を取れないとき、途中まで進めるか」

**進めない。これは不具合ではなく、文書化された現在の設計である**（docs/11「経路の全区間を一括予約」、docs/10 F-01）。「途中まで進む」方式は未実装（分類 D）。

- 出発機は、スポットから滑走路の入口までの全区間が空いているときだけ動き出す。取れなければスポットで待つ（`src/core/sim/simulation.ts` の stepReadyForPushback）。
- 到着機は、滑走路の出口からスポットまでの全区間が空いているときだけ進入を許可される。取れなければ上空で待つ（stepInbound）。
- 途中で止まるのは、すでに全区間を確保した経路の中にある**滑走路の横断の手前だけ**。横断の手前で停止して待ち、その後に再開することを確認した（30 機×3 シード）。横断待ちの間、滑走路上に他機はいない。
- 空いている別の経路があれば迂回する。

実測（ゲーム内の値。シード d1-s1〜3）:

| 状況 | 結果 |
|---|---|
| 滑走路の入口が 1 つ、4 機が同時刻に出発 | 同時に地上走行できるのは 1 機だけ。後続は先行機が離陸を始めるまでスポットを離れない。離陸の間隔は 344〜362 秒で、滑走路の最小間隔 75 秒の約 4.7 倍。後続の待ちは 370〜560 秒、出発の遅れは 0 / 370 / 724 / 1,069 秒と積み上がる |
| 入口が 2 つある配置 | 後続が別の入口へ迂回し、同時に 3 機が動く。離陸の間隔は 271 / 111 / 111 秒に縮む。経路は最大 40% 長くなる |
| 到着と出発が同じ誘導路を逆向きに使う（25 通り×3 シード） | 競合 0、デッドロック 0。到着の上空待機は最大 115 秒、出発のスポット待ちは 165〜200 秒 |
| 8 スポットに 8 機の到着が続く | 上空待機は最大 11〜16 分。ダイバート 0 |
| 8 スポットに 12 機 | ダイバート 1〜3 件、出発の遅れは最大 28〜46 分 |
| 共通の誘導路 1 本で 14 往復・6 時間 | 全機が出発。追い越し 0。待ちは最大 321〜426 秒（中央値 1 秒） |

**影響**: 滑走路の入口が 1 つしかない配置では、出発の処理能力が滑走路の間隔ではなく「1 機が地上走行にかかる時間」で決まる。滑走路の手前に出発機が並ぶことはなく、待つ機体はスポットを占有し続けるので、到着機のスポット不足にもつながる。逆に、デッドロックと地上での競合は構造的に起きない。

途中まで進む方式（前方だけを順に確保する、滑走路手前に待機列を作る、など）を入れる場合の論点: デッドロックの検出と回避、交差点内での停止の禁止、対向する機体の扱い、既存データの運航結果が変わること（版と互換の判断）。

### 11.3 その他の確認（合格）

- 一方通行の誘導路は、到着・出発とも向きを守る。
- 幅の区分: 大型機は中型用の誘導路に入らない。通れる経路がなければ動かない（到着はダイバート）。
- 出口が複数ある滑走路では、着陸滑走距離より先の出口を選ぶ（機種により 1,000 / 1,500 / 2,000 m）。
- 運航中に共通の誘導路を閉鎖すると、走行中の機体は走り切り、後続は経路なしで待つ。20 分後に再開すれば出発する（遅れ 22〜34 分）。再開しなければ 60 分後に運航不能、新しい到着はダイバート。確保した区間とスポットは解放され、不変条件の違反はない。
- 駐機中のスポットを閉鎖しても機体は通常どおり出発し、閉鎖したスポットへの新しい割当はない。

### 12.3 アクセス交通

**動いているもの**（分類 A）:

- 道路: 出入口 1 つあたり 900 台/時。硬い上限ではなく、交通量が容量に近づくと遅れが増える（容量比 0.54 で 0.09 分、1.08 で 1.4 分、1.62 で 7.3 分、2.2 で 22 分）。出入口を増やすと同じ交通量で 1.38 分 → 0.09 分。
- 駐車場: 台数を超えて駐車しない。満車だと探す時間がかかり別の手段へ回る（10 台: 48 組中 38 組が満車、400 台: 0 組）。
- バス・鉄道: 1 時間の定員を超えた分は次の時間帯へ回る。バスだけの空港で 1 便/時だと 1,977 人が乗り遅れ、12 便/時なら 0 人。
- 到着側の乗り場（タクシー・バス・列車）の処理量は、分析の値と一致。
- 鉄道は、線路が敷地の外周に届いていないと使えない。地下・高架の駅は、ターミナルまでの通路と階層接続がないと使えない。
- 都市の鉄道整備度が 0 なら鉄道は使えない。アクセスが良いほど計画上の旅客が増える（道路なしでは約 3 割）。
- 道路に入力する「明示能力」は車両の容量には使われない（docs/34 の記載どおり）。

**不足・不一致**:

- 能力ダッシュボードに、空港全体で何人が来られるかの値（人/時・人/日）がない。駐車場・バス・タクシー・出入口・車寄せの行もない（分類 E）。
- 地下・高架駅の通路の能力は、分析の値には効くが運航には効かない（通路 100 人/時でも運航は 400 人/時まで受け入れる。分類 B）。
- サンプル空港の規模（滑走路 1 本・9 スポット）では、道路 900 台/時は飽和しない。道路が制約になるのは、より大きな空港になってから。

### 12.4 離発着数

- ダッシュボードの滑走路の能力は「本数 × 30 回/時」の固定値で、配置・交差・間隔に関係しない（docs/33 に記載どおり）。
- 飽和させたときの実績（60 分あたりの離着陸の最大）: 滑走路 1 本で 18〜21 回（表示の 0.60〜0.70 倍）、平行 2 本で 22〜27 回（表示 60 の 0.37〜0.45 倍）。
- 到着だけの間隔は平均 166〜270 秒、出発だけは 126〜241 秒。滑走路の最小間隔（中型機どうしで 75 秒）には届かない。
- **実際の制約は滑走路の間隔ではない。** 経路の一括確保による待ち（§11.2）と、スポットの占有時間（折り返しの地上時間 約 49〜58 分。16 スポットで 1 時間に 19〜21 回の折り返しが上限）。滑走路の出口・入口を増やすと間隔は縮む。
- スポットの能力は、運用中で誘導路につながったスポットの数（建設中・未接続は除く）。誘導路の能力は仕様どおり「未算出」。
- 運航中に手動で閉鎖したスポット・滑走路は、ダッシュボードの値に反映されない（docs/33 に記述なし）。

### 12.5 折り返し

- 作業員・各車両・整備士は、増やして悪化することはない。作業員 4 / 8 / 12 人で平均の遅れ 3,955 / 526 / 338 秒、12 人以上は同じ。
- トーイングカーは 1 台で足り、0 台だと出発できない。整備士が 0 人でも出発できない。
- 燃料管（ハイドラント）につながったスポットは、給油車が 0 台でも出発でき、給油時間は 0.6 倍。
- 地上支援の基地が遠いと準備の完了が遅れる（100 タイルで +175 秒）。
- **ダッシュボードの折り返し能力は大幅に保守的**。同時 6 機の折り返しは作業員 12 人（表示の能力は 3）で足りるが、表示が 6 になるのは 24 人。1 日の通し運航（3 シード）では、能力 3・需要 4〜7 で「能力不足」と出ながら定時運航率は 97〜100%。
- ダッシュボードの値は、トーイングカー・整備士・燃料施設・ハイドラント・基地の距離を含まない（ハイドラントがあっても給油車 0 台なら能力 0 と表示）。

### 12.6 拠点空港

- 格納庫: 費用だけで効果がない。撤去して 1 日運航しても、維持費以外は完全に同じ（§7.1 の T6 を確認）。
- 整備施設: **効果がある**（§7.1 の T6 の「効果がない」は格納庫と消防についてのみ正しい）。出発前の点検に整備士が必要で、撤去すると出発が 0 便になる。ただし計画・運航可否・ダッシュボードには表れない。
- 夜間滞泊: 計画には存在しない。通常の運航で、0:00 にスポットに残る機体は 0。計画は同じ日に折り返す便だけを作る。
- 手動で夜に到着・翌朝に出発する便を追加すれば、日付をまたいでスポットを保持して出発する（仕組みとしては動く）。
- 所属機・朝の始発・整備サイクル・予備機・格納庫への牽引は、データにも文書にも存在しないか、未実装と明記されている（docs/09、docs/11）。

### 12.7 ハブ空港

- 乗継旅客・乗継手荷物・最小乗継時間はない（未実装と文書に明記）。3 時間の運航で、到着旅客 1,024 組はすべて出口へ、出発旅客 977 組はすべて保安検査から来る。
- ターミナル間の連絡設備は、出発スポットが別のターミナルへ変わったときだけ使われる。170 人の移動で、能力 20 / 60 / 200 人/時のとき乗り遅れ 138 / 98 / 0 人。連絡設備がないと 160 人が乗り遅れる。
- 能力を入力していない連絡設備は、運航では 1,200 人/時として扱われるが、ダッシュボードには「未設定」と出る（分類 B）。利用率は未算出。
- ターミナル内の上下移動設備は処理量を制限する（エスカレーター 150 / 600 人/時で乗り遅れ 570 / 0 人）。段差のない経路が必要な旅客（約 5%）は、階段だけだと全員が到達できない。
- 到着と出発が集中する波（30 分に 8 機到着、60 分後に 8 機出発）は、1 ターミナルなら乗り遅れ 0。ゲートの待ち行列は最大約 140 人。
- ゲートごとの処理率はモデルにない。
