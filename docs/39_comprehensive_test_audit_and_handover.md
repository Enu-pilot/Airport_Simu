### 1.2 監査用テストの実行方法

監査用テストは通常の `npm test` / `npm run test:e2e` / CI に**含めていない**（別設定）。型検査と lint の対象には入る。

| コマンド | 内容 |
|---|---|
| `npx vitest run -c vitest.audit.config.ts` | 合格する監査テスト（`tests/audit/*.audit.test.ts`） |
| `AUDIT_KNOWN=1 npx vitest run -c vitest.audit.config.ts` | 未解決の不具合の再現（`tests/audit/known-issues/`）。**失敗するのが現状** |
| `npx playwright test -c playwright.audit.config.ts --trace off` | ブラウザ監査（`tests/audit/e2e/`、ポート 4174） |
| `AUDIT_KNOWN=1 npx playwright test -c playwright.audit.config.ts --trace off` | ブラウザの不具合の再現（`tests/audit/e2e-known/`）。**失敗するのが現状** |

長時間のシミュレーションを含むため、他の重い処理と並行すると時間切れになることがある。その場合は単独で再実行して切り分ける。乱数シードはテスト名または失敗メッセージに出る。

## 6. 仕様・設計の欠落や矛盾（E）

### 6.1 リモートスポットとターミナルの対応

現在の決定規則（監査テスト `b_multiTerminal` で確認）:

- 固定スポット: スポットに対応するゲート（複数あれば ID の小さい方、検証 `STAND_MULTIPLE_GATES`）→ そのゲートの所属ターミナル。
- リモートスポット: `remoteBoarding: 'bus'` は指定したバスゲートのみ（代替なし）。`'none'` はなし。`'auto'`（旧データを含む）は使えるバスゲートのうち直線距離が最も近いもの（同距離は ID の小さい方、定義順に依存しない）。

**レイアウトと閉鎖の状態が同じなら一意に決まる。ただし `'auto'` では時間とともに変わり得る。** 確認した例: 同じスポットで到着便は T1 を使い、T1 のゲートが閉鎖された後の出発便は T2 を使った。このとき T1 の中にいた旅客は行き先が T2 に変わり、連絡設備がなければ乗り遅れる（閉鎖の時刻により 3〜138 人）。1 つの出発便の旅客が 2 つのターミナルに分かれる（docs/35 §7.1 と緊張関係）。一方、docs/29 §1 と docs/32 §3 は再選択を明示的に許している。

「リモートスポットと紐づくターミナルを一意に定めたい」という要望に対する選択肢（決定は未了、実装方式は指定しない）:

1. スポット割当の時点でゲートを決め、搭乗開始前にそのゲートが閉鎖された場合を除いて到着・出発とも維持する。
2. 使えるバスゲートを持つターミナルが 2 つ以上あるとき、`'auto'` のリモートスポットを検証エラーにして明示指定を求める。
3. 旅客を生成した後はゲートを固定する。
4. スポット自体にターミナルの属性を持たせる。

どれも旧データ（`'auto'`）の結果を変える可能性があるため、互換の扱い（版・移行）と合わせて決める必要がある。

## 7. ゲームデザイン上の提案

機能の一覧ではなく「遊びとして何が薄いか」から出したもの。全文・根拠・依存関係・課題は付録 [audit39_game_design_analysis.md](design/audit39_game_design_analysis.md)。既存仕様（docs/30〜37、12B-3b の設計）と重なるものは不足分だけを挙げている。

### 7.1 いまのループで薄いところ

| # | 観察 | 影響 |
|---|---|---|
| T1 | 空港の格が上がっても、提案の便数上限が 1 増えるだけ。格 3 は「国際ハブ」だが国際線は常に無効 | 成長の報酬に中身がない |
| T2 | 目標は固定の 12 個で、達成後は方向がなくなる | 長期の動機が切れる |
| T3 | 新規ゲームの既定（地方都市）では、需要の上限が約 700〜1,000 人/日で、格 1 の条件 2,000 人/日に届きにくい（**式からの推定のみ。実行では未確認**） | 序盤で成長が止まる恐れ |
| T4 | 航空会社は搭乗率を気にしない。便を増やすほど着陸料が増える | 都市の需要上限が無視できる制約になる |
| T5 | 駐機料の倍率は、上げると不満だけが増える設定になっている（全便が短時間で折り返すため） | 罠の選択肢 |
| T6 | 格納庫・消防施設は費用だけで効果がない。管制塔は 1 つあればよい | 高価な施設が飾り |
| T7 | 都市イベントはプレイヤーが無料で入れられる需要増 | 「常に入れる」が最適で判断がない |
| T8 | 鉄道の目標は駅を置くだけで達成 | 目標が軽い |
| T9 | 旅客満足度は 1 つの数字で、内訳が見えない | 何を直せばよいか分からない |

強み: 決定的なシミュレーションと 1 日スキップの一致、航空会社評価の「何が足りないか」の言語化、仮想契約チェック、便別の遅延原因。この上に「判断」と「解放」を足すのが効率がよい。

### 7.2 提案（優先度別）

規模: S 小 / M 中 / L 大 / XL 特大。いずれも既存データの結果を変えないよう、新しい設定があるときだけ働く形が前提。

**優先度 1**

| 提案 | 価値・効果 | 主な課題 | 規模 |
|---|---|---|---|
| A1 格による機能の解放 | 「次に何ができるようになるか」が長期の動機になる。T1 を解消 | サンドボックスは全解放。中身は他の機能に依存 | S〜M |
| A7 消防の区分・管制塔のレベル | 安い解放段階が増え、T6 の施設に役割ができる | 既存の空港の結果を変えない仕組み | S〜M |

| B1 搭乗率を航空会社評価に入れる | 需要上限・料金・アクセス投資が意味を持つ。T4 を解消 | 既存の評価結果を変えない重み表の分け方 | M |
| B2 契約の逆提案（時間帯・便数・割引の交渉） | 能力のピークと結びつく経営判断が増える | 交渉の画面と相手の受諾規則 | M |

| C2 立地の型（海上・内陸・都市近郊など） | 周回ごとに違う制約で遊べる | 用地・騒音・アクセスとの組合せ | M |

| E1 目標の連鎖 | T2 を解消。達成後も次の方向が出る | 目標の生成規則 | M |

推奨の順序: (1) 見えていない結果を見せる（C1 → D1 → D2 → B1 → A1＋A7）、(2) 判断を足す（B2 → B4 → F1 → E1 → F2）、(3) 成長の新しい軸（A2 → A3 → A5 → A4）。

### 7.3 決めてもらう必要があること

1. 新規ゲームの都市の既定は地方都市のままでよいか（T3）。
2. 格を解放の段階にするか。サンドボックスは全解放でよいか。
3. 夜間滞泊は軽量版（翌朝に機体を置く）で足りるか。
4. 国際線と乗継のどちらを先にするか。
5. 都市イベントを現在の方式のまま残すか、判断・費用・リスクのある「出来事」に置き換えるか。
6. 鉄道の目標を「利用者 100 人/日」に変えるか。
7. キャリアで他社の機材の座席数を変えられるのは意図どおりか。
8. ゲートホールドなど運航結果を変える判断を、どこまでプレイヤーに渡すか。
9. 空港評価の表示を 0〜100 のままにするか、0〜5 つ星にするか。
