# 18. 運営分析・機種別統計・シナリオ比較（Phase 8）

実装: `src/core/analytics/records.ts`（記録）、`src/core/analytics/kpi.ts`（集計・ボトルネック）、`src/core/scenario/scenario.ts`（シナリオ）、
`src/ui/AnalysisPanels.tsx`（分析・シナリオ画面）、`src/render/MapRenderer.ts`（混雑マップ）。

## 値の区別

- **実績**: シミュレーションの記録から計算した値（下記の指標のほとんど）。
- **推定**: 航空会社の運航費（機種のゲーム値 × ブロック時間 1.5 時間）。画面でも「推定」と表示する。
- **設定値**: 機種の座席数・必要作業数など（機種カタログのゲーム値）。実績と混ぜて表示しない。

## 記録（FlightRecord）

機体 1 機の運航（到着便＋出発便）ごとに、終了状態（出発完了・ダイバート・欠航）になった時点で 1 件記録する。
機種 ID・航空会社・滑走路・スポット・ゲート、予定・実績の時刻（着陸・ブロックイン・準備完了・ブロックアウト・離陸）、到着便に実際に加えた外部要因別の遅延秒数と折返し余裕時間（古い記録では欠落）、
空中待機・地上走行の時間と距離、座席数・予約・搭乗・乗り遅れ、地上作業の所要時間、帰属した収入、障害の影響、遅延・運航不能の原因。
便別レビューでは既存の `FlightRecord` と、締め時点で参照できる `Flight`・機体状態履歴・地上作業・イベント・障害記録を組み合わせる。到着と出発の原因、実績/評価対象遅延、機体状態の時刻付き遷移、地上作業、施設名はレビューの履歴スナップショットに格納する。`FlightRecord` の保存形は増やさない。締め後に参照できない古い記録は追加情報を欠落として表示し、時刻・原因・名称を推測で補わない。
運航中の機体の収入は `live` に積み、終了時に記録へ移す。

## 切り口と指標（集計対象: 記録のある便、期間: 運航開始から現在まで）

切り口: メーカー / 機種ファミリー / 機種・派生型（機種 ID。777-300 と 777-300ER は別） / 航空会社 / 運航便 / 滑走路 / 駐機スポット / 搭乗ゲート。

| 指標 | 式 | 単位 |
|---|---|---|
| 便数 n・完了 | 記録数・出発完了の数 | 便 |
| 運航完了率 | 完了 ÷ n | % |
| 座席・搭乗・座席利用率 | 完了便の座席合計・搭乗合計、搭乗 ÷ 座席 | 席・人・% |
| 平均折り返し | 準備完了 − ブロックイン | 分 |
| スポット占有 | ブロックアウト − ブロックイン | 分 |
| 評価対象の出発遅延 | 実出発遅延から、到着実遅延が折返し余裕を超えた秒数を控除（0秒下限）した平均 | 分 |
| 実出発遅延 | max(0, ブロックアウト − 予定出発) の平均。評価値と分けて表示 | 分 |
| 定時運航率 | 評価対象の出発遅延が15分以内の完了便 ÷ n | % |
| 地上走行（到着・出発） | 着陸 → ブロックイン、プッシュバック → 離陸 | 分 |
| 地上作業の所要時間 | 作業ごとの開始 → 完了の平均 | 分 |
| 収入 | 便に帰属した空港の収入（着陸料・駐機料・旅客施設使用料・地上支援料） | cr |
| 運航費（推定） | 機種の運航費（ゲーム値）× 1.5 時間 | cr |
| 運航不能・障害の影響 | 運航不能の数、障害の影響を受けた便の数 | 便 |

**データ不足**: 便数が `MIN_SAMPLE = 5` 未満の集計は「データ不足」と表示し、優劣の判断に使わない。

### 空港全体の指標

滑走路ごとの使用率（占有時間 ÷ 経過時間）と平均待ち、スポットの使用率（占有時間 ÷ 経過時間）、
地上で止まった時間の多いノード（上位 8）、時間帯別の出発・到着旅客、処理施設（チェックイン・保安検査・ゲート）ごとの処理人数・平均待ち・最大待ち人数、
乗り遅れ、手荷物の処理時間（預け入れ → 積載）と積み残し、作業員・車両の稼働率（作業中の時間 ÷（台数 × 経過時間））、地上作業の停止時間（理由別）。

運航画面の「ターミナル」カードでは、現在館内にいる旅客数、チェックイン・保安検査の設定能力（人/時）、実績平均待ちをターミナルごとに表示する。詳細表は施設 ID 単位で処理人数・待ち・最大列・混雑を表示し、ID が属するターミナルに帰属する。

能力表示の前提: 運航計画のターミナル能力は有効な処理レーン・窓口数と1人あたり処理秒数から計算する静的概算で、計画時刻の便別需要と比較する。保存施設に処理秒がない場合は docs/12 の既定（チェックイン50秒/人・保安検査15秒/人）を使う。シフトや施設の営業時間を持たない施設について、1日能力を時間当たり能力の24倍として表示しない。滑走路は既存の30回/時/本という運用計画上の目安を使う。誘導路の時間当たり処理能力、プッシュバックの時間能力、ランプバスの往復能力は現モデルに十分な専用レートがないため数値化しない。実績の地上走行・停止、スポット稼働、車両・作業員稼働、バス待ちはシミュレーション記録から表示する。

### 日次振り返りの制約分析

日報の遅延原因と、期間内に終了した `FlightRecord` を原因コードごとにまとめ、影響便、記録時刻の範囲、対象原因に関係する平均地上停止・作業待ち・バス待ちを示す。対応案は原因コードに対応した確認・調整案である。時刻は原因の厳密な発生時刻ではなく便記録時刻。現モデルは施設別の時間帯ピーク、作業員・車両別の不足時間、原因が発生した正確な時刻を便記録へ残さないため、これらを特定・数値化したとは表示しない。シフト、道路往復能力、曲線誘導路の能力を推定しない。

便別の振り返りは到着便・出発便を同じ機体記録から表示し、実績遅延と評価対象遅延、原因、旅客・手荷物影響、地上走行・停止・作業・バス待ちを分ける。到着の外部要因遅延は実際に加算した原因別秒数を使う。締め時に `airlineScorecard` が使った当日分の評価要素、EMA 前後、満足度前後、不満・要望の更新は、会社状態や `DailyReport` ではなく日次レビューの履歴スナップショットに保存する。締め処理では評価スナップショットを `DailyReport` オブジェクトをキーにした一時領域へ渡し、その場でレビューへ複製する。翌日の計画分析は別セクションに表示し、当日の評価原因には使わない。便に帰属しない料金・契約・機材条件などは運営上の要因として表示する。

## ボトルネックの推定（根拠つき）

使用率だけで判断せず、待ち・停止・遅延への寄与を組み合わせる。各候補には参照した指標と、当てはまったルールを表示する。

| 対象 | ルール |
|---|---|
| 滑走路 | 平均待ち ≥ 2 分、または滑走路待ちで遅れた便 ≥ 20% |
| スポット | 使用率 ≥ 70% かつスポット不足で遅れた便がある |
| 誘導路（ノード） | 付近での停止の合計 ≥ 10 分 |
| 処理施設 | 平均待ち ≥ 10 分、または最大待ち人数 ≥ 30 人 |
| 地上支援 | 作業員・車両の不足による停止の合計 ≥ 30 分 |
| 手荷物 | 積み残しがある、または預け入れ → 積載が平均 60 分以上 |

## 混雑マップ

上部の「混雑マップ」で表示（運航中）。滑走路・スポットを使用率、ノードを停止時間、処理施設を平均待ちで色分け（緑 < 黄 < 赤）。
値は上の空港全体の指標と同じ計算（30 ゲーム秒ごとに再計算）。

## 適合性分析

機種ごとに、その空港の滑走路・スポット・ゲート・誘導路・地上支援の判定を一覧する（docs/17 の判定をそのまま使う）。
施設制約で割り当てできなかった便（空中待機 → ダイバート、出発不能）は記録の原因として集計される。

## シナリオ比較

- 保存する内容: レイアウト、会社（契約・保有機材・座席・料金）、使用機種のスナップショットとカタログ版、乱数シード、運航時間、障害の条件、
  シミュレーションの版（`SIM_MODEL_VERSION`）、変更履歴、実行結果（KPI・機種別集計・使ったカタログ）。
- シナリオは互いに独立（すべて複製して実行し、開いている空港・会社とも混ざらない）。
- 同じ条件の再実行は同じ結果（テストで確認）。保存した機種データで実行し、「最新カタログで再実行」は `catalogUsed = current` として別に残る。
- 比較は改善・悪化・同じ・判定不能を指標ごとに表示（指標ごとに「高い方が良い / 低い方が良い」を定義）。

## 自動最適化

**未実装**。手動で条件を変えたシナリオの比較のみ。

## Phase 12 の不具合修正の影響（シナリオ）

連続横断で滑走路の占有が漏れる不具合（Phase 2 から。従来形の平行滑走路を 1 本の誘導路が横切る配置など）を修正した。`SIM_MODEL_VERSION` は同じ表記のため、**漏れが起きていた運航を記録したシナリオの結果は、再実行すると変わる**（出発数の増加・ダイバートの減少など）。漏れが起きない配置の結果は変わらない。詳細は [21](21_save_format.md)・[23](23_runway_design.md) §7.1.1。

- 天候欠航の便の記録は `result: 'cancelled'`・原因 `weather`（Phase 12B-3a Part B）。振り返りに予報・評価の不満・達成した目標が加わる（[docs/30](30_game_models.md)）。
