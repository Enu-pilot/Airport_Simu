# 38. 総合テスト・不足項目実装プロンプト集

## 1. 目的

本書は、Airport_Simu の総合テストと不足機能の実装を Claude Fable に依頼するためのプロンプト集である。

既存のテスト計画・仕様・実装を出発点にし、テスト不足、不具合、仕様上の未実装を区別しながら、ゲーム全体の信頼性を高める。個別プロンプトは確認対象と目的だけを示し、実装方式・設計・使用するコード構成を固定しない。

本書はテストケースの追加だけを目的としない。必要に応じて、不具合修正や仕様上の不足機能の実装も対象とする。ただし、既知の未実装を仕様違反と誤認してはならない。

## 2. 使い方

1. 最初に「共通指示」と「事前監査」を実施し、現行ブランチのテスト結果・未検証領域・既知の制限を把握する。
2. 個別プロンプトは原則として上から順に、1項目ずつ実行する。関連する変更が競合しそうな場合は、先行項目の修正・テストを完了してから次へ進む。
3. 各項目で、既存テストによる保証、新規テストが必要な箇所、不具合、未実装項目を区別する。
4. 実装・テスト後は結果と未解決事項を記録し、最後に「統合総合テスト」を実施する。

## 3. 共通指示（各作業の前提）

> README、Docs、既存コード、テストを確認し、既存設計と仕様を尊重して作業してください。対象ごとに「実装済み・テスト済み」「実装済みだがテスト不足」「不具合」「仕様上の未実装」を区別してください。
>
> テストを通すことだけを目的に、期待値・ゴールデン・仕様を安易に変更しないでください。仕様変更が必要な場合は、根拠、影響範囲、運航結果・保存データ・旧セーブへの影響を示してください。既存の責務や機能を壊さないよう回帰を確認してください。
>
> 実装方式は既存コードと仕様を踏まえて判断し、特定の設計・アルゴリズム・ファイル構成に不必要に縛られないでください。未実装と明記された機能は、不具合と混同せず、ゲーム上必要な範囲・依存関係・副作用を確認してから扱ってください。
>
> 変更後は型チェック、Lint、全テストを実行してください。失敗したテストは原因を調べ、再現手順・シード・対象便/施設・発生時刻・ログなどを可能な範囲で記録してください。既存テストを削除・弱体化して合格扱いにしないでください。

## 4. 事前監査プロンプト

> 現行ブランチの全テストと品質ゲートを実行し、成功・失敗・未実行・未検証の領域を整理してください。README、Docs、ソースコードと照合し、既知の制限と実装状態も確認してください。この段階ではコードを変更せず、後続作業の基準となる監査結果を提示してください。

## 5. 個別テスト・実装プロンプト

各プロンプトは単独で渡せる短い依頼文である。共通指示を前提に、対象領域を監査し、不足するテスト・必要な修正・不足機能の実装を行う。

| ID | 対象 | Fable に渡すプロンプト |
|---|---|---|
| 01 | 基本プレイ・ゲーム進行 | 新規ゲームから建設・契約・運航開始・日次締め・翌日への進行まで、一連のゲームプレイを検証してください。 |
| 02 | 建設操作・描画 | 施設の配置・移動・回転・削除・複製・Undo/Redoと2D/3D表示の整合性を検証してください。 |
| 03 | 接続ネットワーク | 滑走路・誘導路・スポット・ゲート・建物・通路の接続について、分岐・交差・閉路・一方通行・切断・再接続を検証してください。 |
| 04 | 階層・建物内部設備 | 地下・地上・高架・建物内部の各階における重複配置、衝突判定、接続、移動、保存を検証してください。 |
| 05 | 滑走路運用 | 複数滑走路の離着陸競合、交差・平行運用、横断予約、閉鎖、間隔、デッドロックを検証してください。 |
| 06 | 航空機の移動 | 航空機の到着から駐機、折り返し、プッシュバック、出発までを追跡し、混雑・閉鎖時の動作も検証してください。 |
| 07 | 便生成・航空会社・スポット | 航空会社・機種・便数・時間帯を変え、増便時の割当、能力不足、ホームスポット、重複利用を検証してください。 |
| 08 | 旅客生成・出発動線 | 旅客の発生からチェックイン・保安検査・搭乗・乗り遅れまでを検証し、人数・ID・所属先の整合性を確認してください。 |
| 09 | 到着旅客・手荷物 | 到着旅客の降機から手荷物受取・退出まで、および手荷物の生成・仕分け・積載・受取を検証してください。 |
| 10 | 複数ターミナル | 複数ターミナル・独立ゲート・バスゲート・連絡通路を組み合わせ、旅客の誤誘導や経路不成立を検証してください。 |
| 11 | 階層移動・連絡設備 | 階段・エレベーター・エスカレーター・ターミナル間通路について、移動・能力制限・閉鎖・再探索を検証してください。 |
| 12 | リモートスポット・ランプバス | 複数便によるバスゲート共有、車両不足、故障、救援、搭乗締切、到着旅客の降機を検証してください。 |
| 13 | GSE・折り返し作業 | 地上支援作業の依存関係、人員・車両不足、同時使用、故障、復旧、折り返し不足を検証してください。 |
| 14 | 道路・鉄道・燃料設備 | 多層道路・鉄道・駅アクセス・燃料管の接続と現行機能を検証し、未実装の運行機能を明確にしてください。 |
| 15 | 障害・外部要因 | 天候・施設閉鎖・車両故障・人員不足・需要急増などの単独および複合障害を検証してください。 |
| 16 | 経営・空港能力・評価 | 契約可否・増便判定・施設能力・収支・日次KPI・空港評価が実績と一致するか検証してください。 |
| 17 | 保存・復元・日次進行 | 各種運航状態での保存・復元・継続、旧形式の移行、破損データへの耐性を検証してください。 |
| 18 | 長時間・高負荷 | 既存QAシナリオを基準に便数・旅客数・施設数・同時稼働数を増加させ、性能と不変条件を検証してください。 |
| 19 | UI・ブラウザE2E | 主要なゲーム操作をブラウザから検証し、複数解像度・2D/3D切替・コンソールエラー・操作不能を確認してください。 |
| 20 | ランダム操作・回帰 | 複数の乱数シードとランダムな建設・運航・障害操作で不変条件を検証し、失敗ケースを再現可能にしてください。 |
| 21 | 統合総合テスト | 建設・便生成・航空機・旅客・手荷物・地上支援・経営・保存を組み合わせた長期総合シナリオを検証してください。 |

## 6. 優先順位・進行上の留意点

推奨順序は ID 01〜21 とする。特に、接続・階層構造（03〜04）、航空機と便の運航（05〜07）、旅客動線（08〜12）は後続領域の前提になるため、先に安定させる。

- **基本構造と運航:** 01〜07
- **旅客・地上支援:** 08〜13
- **交通・障害・経営:** 14〜16
- **保存・品質保証:** 17〜21

確認では、少なくとも以下を意識する。

- 最終状態だけでなく、シミュレーション途中の不変条件・二重割当・占有漏れ・旅客消失・瞬間移動も検査する。
- 便数・旅客数・車両数・施設数を段階的に増やし、通常時と限界負荷を分けて記録する。
- ランダム障害・ランダム操作はシードと再現情報を残す。
- 保存・復元後の結果を、保存せず連続実行した結果と比較する。
- 機能の存在だけでなく、計画・生成・実運航・分析・UIの各段階に正しく反映されるか確認する。
- 未実装と明記された機能は、まず現状が仕様どおりかを判定し、テスト不足や不具合と区別する。

## 7. 完了報告に含める内容

各項目の終了時に、次を簡潔に報告する。

1. 確認した機能・シナリオと既存テスト
2. 追加・修正したテストと実装内容
3. 実行した品質ゲートと結果
4. 修正による仕様・運航結果・保存互換性への影響
5. 未実装・既知の制限・残存リスク
6. 再現が必要な不具合の手順・シード・ログ

全項目の終了時は、全テスト・E2E・長時間/高負荷シナリオを改めて実行し、回帰がないことを確認する。
