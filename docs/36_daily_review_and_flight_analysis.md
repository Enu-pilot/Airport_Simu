# 36. 日次振り返り・便別実績分析仕様（2026-11-14）

## 1. 目的

日次締め時点で確定した実績を根拠に、空港全体の結果、遅延原因、便ごとの影響、航空会社評価の理由、翌日の計画上の制約を分離して提示する。

この機能は記録の閲覧・分析であり、締め済みのシミュレーション状態や評価結果を再計算して書き換えない。

## 2. データの原則

- 基礎データは既存の `DailyReport`、`FlightRecord`、運航イベント、機体状態履歴、地上作業記録、障害記録、締め時点の航空会社評価スナップショット。
- `buildDayReview` は読み取り中心の純関数としてレビューを組み立てる。シミュレーション・会社状態を変更しない。
- 便別の詳細は既存 `FlightRecord` と締め時点で参照可能な記録を組み合わせる。FlightRecord の保存形を無用に拡張しない。
- 過去データに存在しない時刻・原因・施設名・バス待ち等を推測で補完しない。「記録なし」または null とする。
- 実績、評価対象値、設定値、推定値を明確に分ける。

## 3. 対象期間と便の選択

- 対象期間は日次締めの `dayStart` 以上、締め時刻 `end` 未満。
- 便記録の対象時刻は、着陸・ブロックアウト・離陸、または未完了便の代表記録時刻を使う。
- 便別一覧には問題がある便を表示する。対象は未完了/欠航/ダイバート、原因あり、実遅延あり、乗り遅れあり、手荷物積み残しあり、地上作業待ちありのいずれか。
- 並び順は、運航失敗、旅客・手荷物影響、評価対象遅延、地上停止/作業待ち、便名の順で優先する。

## 4. 遅延値の区別

到着・出発とも、実際の予定との差と評価対象遅延を別の値として扱う。計算の共通規則は `evaluateDelayPair` と [docs/11](11_operations_rules.md) の遅延評価仕様に従う。

- 到着実遅延: 実着陸時刻 − 予定着陸時刻。
- 到着評価対象遅延: 実遅延から、実際に記録された外部要因別の遅延秒数を控除し、0 秒未満にしない。
- 出発実遅延: 実ブロックアウト時刻 − 予定出発時刻。
- 出発の折返し余裕: 到着便の実遅延が折返し余裕を超えた部分を、出発遅延の評価対象から控除する。控除後は0秒未満にしない。
- 外部要因の記録がない古いデータは、外部遅延を推測して控除しない。
- 予定・実績時刻が存在しない場合は null とし、ゼロ遅延と解釈しない。

## 5. 便別レビューの表示項目

| 分類 | 表示項目 |
|---|---|
| 識別 | 到着便名、出発便名、航空会社、機種、機体 ID |
| 使用施設 | 到着/出発滑走路、スポット、搭乗ゲート（ID と記録がある場合の名称） |
| 時刻 | 予定着陸、実着陸、ブロックイン、作業完了、ブロックアウト、予定出発、離陸 |
| 遅延 | 到着/出発の実遅延、評価対象遅延、外部要因別遅延、折返し余裕 |
| 原因 | 到着原因、出発原因、便に記録された原因コード |
| 旅客・手荷物 | 予約旅客、搭乗旅客、乗り遅れ、到着旅客、積載手荷物、積み残し |
| 移動・作業 | 到着/出発地上走行、空中待機、地上停止、作業ブロック時間、バス待ち、作業別所要時間 |
| 時系列 | 機体状態の変化、運航イベント、地上作業の開始・完了、障害との関係 |

便別の影響は実記録からのみ構成する。記録のない項目を他便・計画値・施設の設定値から補完しない。

## 6. 遅延原因・ボトルネック

- 原因コードごとに、対象便数と対象便番号を集計する。
- 原因別の時刻範囲は便記録時刻の範囲であり、原因が発生した厳密な時刻ではない。
- 原因に関連する実測記録がある場合のみ、平均地上停止、作業待ち、バス待ち等を根拠として示す。
- 対応案は原因コードに対応した確認・調整案であり、原因を自動修正したことを意味しない。

例:
- バス関連: バス待ちの記録がある場合は平均バス待ちを示し、ピーク時の配車・台数・便時間の確認を提案。
- 誘導路混雑: 出発地上走行・停止時間を示し、経路と便時間の見直しを提案。
- 滑走路待ち: 地上停止時間を示し、滑走路運用と便集中の確認を提案。
- 地上支援/折返し: 作業待ちを示し、必要人員・車両と折返し時間の確認を提案。

天候（`weather` 項目）: 会社の `game.weather === 'levels'`（5 段階）のレビューだけ、その日の計画天候の最大段階と、1 時間ごとの段階が前の時間から変わった時刻・段階を示す（最初の時間は直前を晴れ 0 として比べる）。従来の天候・旧レビューでは項目を持たず、補完しない。手動・シナリオの天候の障害による上書きは障害の記録に出る。

施設別ピーク、作業員・車両別の不足時間、原因の正確な発生時刻が記録されていない場合、それらを推定・断定しない。

## 7. 航空会社評価の根拠

日次締めで使われた当日スコアカードを保存し、レビューでは次を表示する。

- 満足度の締め前・締め後・変化量。
- 評価要素（score components）と警告/悪化要素。
- EMA の締め前・締め後。
- 当日新たに発生した不満、継続中の不満。
- 未達の要望、当日達成した要望。
- 評価要素に結びつく便番号が存在する場合、その便への影響キー。

スナップショットは締め処理で評価計算に使った値から作る。翌日の計画値や翌日の評価を当日の評価理由として再利用しない。航空会社評価を無効にしているモードでは該当項目を表示しない。

## 8. 前日比較

前日の日報と当日の日報を比較する。比較対象は収入、費用、営業利益、OTP、平均遅延、旅客数、旅客満足度、航空会社満足度、空港評価、便数、乗り遅れ、手荷物積み残し、ダイバート、欠航。

| 指標 | 改善方向 |
|---|---|
| 収入、営業利益、OTP、旅客数、旅客満足度、航空会社満足度、空港評価、便数 | 高いほど良い |
| 費用、平均遅延、乗り遅れ、積み残し、ダイバート、欠航 | 低いほど良い |

比較値の差が0なら「同じ」。前日値または当日値が存在しない場合は「判定不能」。便数・旅客数が増えたこと自体は、他の品質指標と合わせて判断する。

## 9. 翌日の見通し

翌日の便数、計画上の警告・エラー、翌日に完成する工事、対象モードでの天気予報を別セクションで表示する。

**翌日の見通しは当日の実績・航空会社評価の根拠に混ぜない。** 当日のレビューは締めた日の記録だけで確定する。

## 10. 保存・履歴・互換性

- 日次レビューは日単位の履歴として IndexedDB に保存する。保持上限は直近7日と週ごとの最大8件。
- 日次締め時にレビューを作成・保存し、「その日の朝」へ戻す履歴と関連付ける。
- 旧形式レビューに便別詳細や評価スナップショットがない場合、欠損値は欠損のまま表示する。
- レビュー生成のためだけに既存の FlightRecord やセーブ形式を変更しない。保存構造を変更する場合は [docs/21](21_save_format.md) の版・移行方針に従う。

## 10.5 離陸の遅れ（フェーズ 2。`city.nightOps` があるときだけ）

- 定義: `takeoffDelaySec = max(0, 実離陸 − (出発の予定 + 標準の離陸までの秒数))`。標準の離陸までの秒数（`nominalOutSec`）は、スポットと滑走路・機種から決まるプッシュバック開始〜浮揚の見積り（混雑を無視した最短経路）。スポットを離れた後の待機と夜間の待機を含むため、スポットで夜を明かした便は 480 分を超える。保存項目は増やさない。
- 出発の実遅延（ブロックアウト基準）・評価対象の遅延とは**別の指標**で、置き換えない。振り返りの便別一覧に「離陸の遅れ」を別の行で出す。評価・補償（R16）にはまだ入れない（未実装）。
- 日報 `DailyReport.night`（`city.nightOps` があるときだけ）: `lastDepartureDelayMin`（その日に予定された最後の出発。未離陸なら予測離陸から求める）、`standHeld`・`originHeld`・`carriedOver`・`diverted`・`cancelled`。持ち越し便はその便の予定日に数え、日付をまたぐ収入・費用の計上は従来どおり。実装: `src/core/economy/takeoffDelay.ts`、`ops.ts` `settleDay`、`DayReview.tsx`。テスト: `tests/unit/takeoffDelay.test.ts`。

## 10.6 日報画面の構成（2026-11-20 再編、PR #61）

- 日報（日次レビュー）のタブは「経理／地上・サービス／運行／航空会社／履歴」の5分類に再編した。従来「振り返り」タブに1本の縦スクロールで並んでいた11セクションはすべて新分類のいずれかへ振り分け、表示情報は落としていない。経理には収入と費用・前日比較・目標・都市/旅客需要、地上・サービスには定時運行と遅延・旅客と満足度・障害と対応に加えて乗継・貨物・工程ピーク等を「地上実績」として整理、航空会社は数字のサマリと理由付き評価を分離した。
- 便別リストは初期表示を絞り「もっと見る」で展開する（便数が増えても日報全体が縦に伸び続けないため）。
- 「明日の収支見通し」は算出の基礎データが存在しないため作っていない（表示項目の追加ではなく未実装事項として扱う）。

## 11. テスト要件

- 同じ入力から同じレビューが生成される。
- レビュー生成前後で Simulation / CompanyState が変化しない。
- 日付境界で対象便が二重計上・欠落しない。
- 到着・出発の実遅延と評価対象遅延が別々に表示される。
- 外部遅延記録がない旧データを推測で控除しない。
- 作業・機体状態・イベントの時系列が時刻順になる。
- 問題便の選択・並び順が規則どおりである。
- 航空会社評価の当日スナップショットが翌日計画で上書きされない。
- 前日値がない場合に改善/悪化を表示しない。
- 旧レビューの欠損値をゼロで埋めない。
- IndexedDB の保持上限と「朝に戻す」操作が一貫する。
