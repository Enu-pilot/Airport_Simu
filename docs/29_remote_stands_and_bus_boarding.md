# 29. リモートスポット・ランプバスによるバス搭乗・独立ゲート（Phase 12B-3a Part A）

実装: `src/core/sim/apronBus.ts`（運行・配車）、`src/core/sim/busRules.ts`（定数）、`src/core/sim/passengers.ts`（旅客の分岐）、`src/core/model/gates.ts`（読み取り）、`src/core/terminal/model.ts`（独立ゲートの接続）、`src/core/validation/validate.ts`。数値はすべて **ゲーム値**（実在の運用基準・安全基準への適合をうたわない）。

## 1. 背景と方針

- 従来、ゲートのないスポット（リモートスポット）には機体は割り当てられるが、出発旅客は全員「ゲートなし」で乗り遅れ（`noGate`）、到着旅客は降機口がなく到達不能（`stranded`）だった（docs/12 §6）。
- **バスゲート**（`boardingMode: 'bus'` のゲート）と**ランプバス**（GSE 基地の `apronBuses`）を置くと、リモートスポットの便は旅客をバスで運んで運航できる。
- **プール方式**: バスゲートは特定のスポットに固定しない。バスゲートが 1 つ以上ある空港では、**コンタクトゲートのない運用中のすべてのスポット**がバス扱いになり、便ごとに負荷の少ないバスゲートを選ぶ。
- **従来のデータは 1 ビットも変わらない**: すべての新しい処理は `state.bus`（運用中のバスゲートがあるときだけ作る）と便ごとの `p.bus` が入口。バスゲートが 1 つもなければ新しいコードに入らない（`tests/golden/legacy-remote-sim.golden.json` が実装前の出力を固定）。

## 2. データモデル

| 場所 | 項目 | 意味 |
|---|---|---|
| ゲート（`Facility.props`） | `boardingMode` | `'contact'`（欠落 = 従来）/ `'bus'` |
| ゲート | `connectedTo` | 接続先ターミナルの ID（欠落 = 隣接で決まる従来の扱い）。§6 |
| GSE 基地 | `apronBuses` | ランプバスの台数 0〜30（欠落 = 0） |
| 運航状態 | `state.bus` | `{ trips, active, stats }`（バスゲートがある運航だけ） |
| 便 | `pax.bus` | `{ gateId, gateClosedAt, paxCarried, waitPaxSec }`（バス扱いの便だけ） |
| ユニット | `trip` | 担当している運行 ID（バスだけ） |
| 旅客グループ | `busTrip` | 乗車待ち・乗車中の運行 |

- `DEFAULT_PROPS` は変えない（新しく置いたゲート・基地の JSON は従来と同じ）。欠落 = 既定は `model/gates.ts`（`gateMode`・`connectedTerminal`・`apronBusesOf`）と `propDefault` が解釈する。
- 型の追加: `UnitKind 'apronBus'`、`PaxState 'waitingBus' | 'onBus'`、`MissReason 'noBus'`、`DelayCause 'apronBus'`、イベント `busRescue`。
- `contactStands` / `standGate` からバスゲートは除く。ランダムな `gateFailure` の候補（`standGate` の値）は従来どおりで、乱数の並びは変わらない。ランプバスは `apronBuses > 0` の基地だけに生成する（`createGroundUnits` の順序の末尾）ので、従来のレイアウトではランダムなユニット故障の乱数の引き方も `gu_n` の ID も同一。
- 空港アクセスの路線バス（`busStop`・`accessFees.bus`）とは無関係。混同を避けるため車両は `apronBus` と呼ぶ。

## 3. 出発旅客の流れ

```
… security → (shop/restroom) → walking → [バスゲートの搭乗口] dwelling
  → boardingQueue（gate:<id>、搭乗券の確認 2 秒/人）
  → waitingBus（搭乗口に滞在）→ onBus（乗車中）→ boarded（スポットで降車 → タラップで機内へ）
```

1. **バスゲートの選択**: スポットが決まりコンタクトでなければ、運用中のバスゲートのうち故障・閉鎖中でなく搭乗口があるものから、そのゲートを使っている未完了の便の数 → スポットとの距離 → ID の順で選ぶ（選んだら固定。搭乗開始前にゲートが故障したら選び直す）。候補がなければ `p.gateId = null`（従来どおり締切で `noGate`）。
2. **搭乗開始**は従来の条件に **+10 分**（S 30 / M 40 / L 50 分前）、最低の搭乗時間 20 分。
3. **ゲートの締切**: 従来の締切（`max(出発予定 − 10 分, 開始 + 20 分)`、ゲートの列が空）に達すると、ゲートより前のグループを従来の理由（締切に間に合わず・到達不能・施設閉鎖）で乗り遅れにする。**バス待ち・乗車中のグループは乗り遅れにしない**。
4. **バスが来ない**: ゲート締切から 15 分たっても配車されないグループは `noBus` で乗り遅れ。乗車中は必ず運ぶ。
5. 全員が搭乗・乗り遅れで終わったら搭乗を締める → 機体はプッシュバックへ（遅延の理由に `apronBus` を加える）。

## 4. 到着旅客の流れ

バス扱いの到着便は、降機口の代わりにスポットで `waitingBus` として現れ（降機速度はタラップの 12 人/分）、バスでバスゲートの降機口へ運ばれ、以後は従来どおり（手荷物受取所 → 出口）。1 時間バスに乗れない旅客は従来のリモートスポットと同じ「到達不能」として扱う。

## 5. 配車・運行（`stepApronBuses`、決定的）

処理順: 運行の段階を進める（故障の検出を含む）→ 乗車待ちのグループがいて受け付け中の運行がない便に新しい運行を作る → 未配車の運行へ空きバスを割り当てる（救援 → 出発の締切が早い順 → 到着順 → 運行 ID、乗車地点に最も近い空きバス）。空きがなければ `waiting` のまま（`stats.shortageSec` に加算）。

| 段階 | 時間（ゲーム値） | 終わる条件 |
|---|---|---|
| `toPickup` | 直線距離 ÷ 8 m/s + 30 秒（既存の車両の移動モデル） | 到着 |
| `loading` | ドア 60 秒 + 乗車 1 秒/人 | 満員（定員 60 人、グループは分割しない）／その便にもう来ない／乗車開始から 300 秒かつ 1 人以上／出発はゲートの締切後 |
| `driving` | 直線距離 ÷ 8 m/s + 30 秒 | 到着 |
| `unloading` | ドア 60 秒 + 出発 2.5 秒/人（降車してタラップ）／到着 1 秒/人 | 完了 → 出発は `boarded`、到着は降機口で歩き出す |

- 乗車地点: 出発 = ゲートのタイル、到着 = スポットのノード。バスは完了後に基地へ戻る（途中でも次の運行に割り当て可能）。

## 6. 独立ゲート（徒歩の連絡通路）

- ゲートの `connectedTo`（ターミナル ID）が明示の接続先。ターミナルに隣接していないゲートは**連絡通路でつながる独立ゲート**になる（隣接していれば従来どおりで、`connectedTo` は無視）。搭乗方式とは直交（コンタクトにもバスにもなれる）。
- `buildTerminalModel` が独立ゲートごとに合成ノード 2 つ（`<gateId>:dep` 搭乗待合、`<gateId>:arr` 降機口）を作り（保存しない派生データ。`byTerminal` には入れない）、接続先ターミナルの出発区域・到着区域のエリア（保安検査・上下移動を除く、ゲートに最も近いもの）へ、直線距離 × 1.25 の歩行リンク（上下移動の時間なし）でつなぐ。`TerminalModel.connectors` に記録する。
- 2D では連絡通路を破線で描く。実装した範囲は**徒歩の連絡通路だけ**（ピープルムーバー・サテライトターミナル・ターミナルからバスで運ぶ独立ラウンジは後続）。

## 7. 故障・不足の扱い

| 状況 | 扱い |
|---|---|
| バス不足 | 運行が `waiting` のまま → 乗車待ちが増え、ゲート締切から 15 分で `noBus` の乗り遅れ。機体は搭乗の締切待ちで遅延（`apronBus`・`boarding`）。UI は「ランプバス不足」のアラート |
| バスの故障（`vehicleFailure`・ランダム故障・手動） | 配車前・乗車中: 乗客を乗車待ちに戻して運行を未配車にし、別のバスを配車。走行中・降車中: 運行を `stalled`（故障位置）にして救援のバスを最優先で送り、乗り換え（120 秒）後に再開（`stats.rescues`）。UI は「ランプバス故障」のアラート |
| 運行中のバスの配置換え（`moveUnitToBase`） | `OCCUPIED` で拒否 |
| ゲートの故障 | 列が進まない（既存）。搭乗開始前ならゲートを選び直す |
| 欠航 | 運行を取り消し、バスは基地へ |

## 8. 不変条件・検証・互換性・経済・分析

- 不変条件（`checkBusInvariants`、`state.bus` があるときだけ）: BU1 乗車中のグループはちょうど 1 つの未完了の運行にいる / BU2 運行の乗車人数 = グループの合計 ≤ 定員 / BU3 配車済みの運行のバスの `trip` が一致し 1 台が 2 つの運行を持たない（故障したバスの運行の組み替えは次ティックなので、故障中のバスが運行を持つ一瞬は許す）/ BU4 バス待ち・乗車中のグループの便は `p.bus` を持つ。
- 検証コード: `GATE_BUS_HAS_STAND`（info）・`GATE_BUS_NO_VEHICLES`（warning）・`BUS_GATE_NO_REMOTE_STAND`（info）・`GATE_CONNECTION_INVALID`（error）・`GATE_CONNECTOR_LONG`（warning、60 タイル超）。バスゲートには `GATE_NO_STAND` を出さず、`STAND_REMOTE` の文言はバスゲートがあるときだけ分岐。docs/26 §6。
- 互換性（`checkGate`）: バスゲートは運用中なら適合（理由 `GATE_BUS`）。運航計画の分析はバスゲートがある空港のリモートスポットを `NO_GATE` の代わりに `BUS_BOARDING`（info）。
- 経済: ランプバスの購入費 250,000 cr/台、日次は運転士 1,500 cr + 車両維持費 300 cr、運行ごと 150 cr（`groundOps`）。料金の割引は入れない。
- 分析: `FlightRecord` に `boarding: 'bus'`・`busWaitSec`、`AirportKpis.apronBus`（運行・旅客・平均待ち・不足・救援）、遅延理由 `apronBus`、乗り遅れの理由 `noBus`。
- 保存: 新しい項目を使うファイルだけ `formatVersion: 2`（docs/21）。`SCHEMA_VERSION`・`SIM_MODEL_VERSION` は上げない。

## 9. UI

- 建設モード: ゲートの「搭乗方式」（バスのときは紐付けスポット・ブリッジを隠し、対象のリモートスポット数を表示）・「接続先ターミナル」、GSE 基地の「ランプバス」。
- 運航モード: 運航表のスポット欄に **BUS** の札（`fids-bus-<便名>`）、地上支援カードにランプバスの運行（`ground-apronBus`）、ターミナルカードにバス待ちの旅客（`terminal-bus-wait`）、機体の詳細にバスゲート・運行、アラート（不足・故障）、分析に `ランプバス` の行。2D は他の車両の 2 倍の長さのバス（乗車人数つき）、3D は色のみ。

## 10. 制限

- バスは直線で移動する（サービス道路の経路化は全車両の共通課題として後続）。タラップ（旅客用ステップ車）は作らず、時間だけを見込む。
- バスラウンジ（ターミナルからバスで運ぶ先の建物）・ピープルムーバー・サテライトターミナルは未実装。ターミナル同士の接続はない。
- ランダムな `gateFailure` の候補にバスゲートは入らない。
- バスゲートに接続されたスポットの固定指定（スポットごとのバスゲート）はない（プール方式のみ）。
