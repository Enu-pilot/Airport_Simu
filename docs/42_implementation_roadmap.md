## 4. 共通のテスト項目（全フェーズ）

1. 品質ゲート: `npm run typecheck`、`npm run lint`、`npm test`、`npm run build`、UI に触れたら `npm run test:e2e`。
2. 監査テスト（`npx vitest run -c vitest.audit.config.ts`）が合格し続ける。挙動を意図して変えた項目は、理由を記録して監査テストを更新する（合格目的の弱体化はしない）。
3. 修正した不具合の再現テストを `tests/audit/known-issues/`・`tests/audit/e2e-known/` から通常のテスト群（`tests/unit/`・`tests/e2e/`）へ移す。
4. シミュレーションに触れた変更: 決定性（同じシードで同じ結果）、不変条件、保存 → 復元 → 継続が連続実行と一致。
5. 新しい設定を持たない保存データが読み込め、従来どおり動く。不具合修正で結果が変わる場合は §5 に従う。
6. 新機能は opt-in。正常系・境界値・異常系・回帰のテストを付ける。

## 5. ゴールデンと版の扱い（2026-11-16 承認済みの 3 段階）

- 現状、ゴールデンは監査前から不一致（docs/39 G-1）。フェーズ 1 の不具合修正でも運航結果は変わる。
- **第 1 段階（完了）**: 修正前の基準値を保存した。期待値は `tests/golden/`、実測値と差分は `tests/golden-baseline/2026-11-16_pre-phase1/`（14 ファイル・テスト 13 件が不一致。2 回の採取が完全に一致することを確認）。
- **第 2 段階**: フェーズ 1 の修正を適用した後、同じ条件で複数回採取し（`tests/golden-baseline/capture-actual.sh`）、決定性と、KPI・13 件の変化を確認する。結果は `tests/golden-baseline/<日付>_post-phase1/` に保存し、どの修正がどの差を生んだかを記録する。
- **第 3 段階**: 不具合修正による正当な変化と判断できたものだけ `tests/golden/` を更新する。版・台帳（`sim-versions.json`）・docs/22・23 を同じ作業で合わせ、全件一致を確認する。正当と判断できない差は更新せず、原因を調べる。
- 第 3 段階までは、監査テストと決定性・不変条件のテストを回帰の検出に使う。

### 5.1 実施結果（2026-11-17。判断はプロダクトオーナーからコーディネーターに委任）

**第 2 段階**: 修正後に採取した実測値（`tests/golden-baseline/2026-11-16_post-phase1/`）を修正前（`2026-11-16_pre-phase1/`）と比べ、差ごとに原因の変更を 1 つずつ戻して特定した（記録: `tests/golden-baseline/2026-11-17_post-phase1-fix/README.md`）。意図しない副作用が 2 件見つかり、コードを直した（コミット eeba67f）。

| 差 | 原因 | 判断 |
|---|---|---|
| 障害のない通常の運航で旅客の歩行・待ちが変わる（例: 平均歩行 9.9 → 9.5 分） | 1-07 の「ゲートが決まったら旅客を付け直す」条件が、最初の割当（未定 → ゲート）でも働いた | 副作用。付け直しを「別のゲートへ変わったとき」に限定した。1-07 の再現テストは合格のまま |
| 積み残し手荷物の指標が 0 → 最大 1,747 個 | 1-09 で欠航便の手荷物を `leftBehind` にした結果、指標・便の記録（航空会社の評価に入る）がそれを数えた | 副作用（計画の既定は「欠航便の手荷物は積み残しに数えない」）。指標と便の記録からも除いた。回帰テストを追加 |

修正後の採取（2 回とも完全一致）では、フェーズ 1 による差は**欠航・ダイバートを含む 4 つの運航の状態ハッシュと状態の大きさだけ**になった（1-09 で手荷物が最終状態まで進むため）。KPI・収支・評価・旅客数はすべて修正前と同じ。

**第 3 段階の判断**: 次の 2 種類の差はどちらも正当と判断し、ゴールデンを更新した。

1. 監査前からの不一致（13 件）: 利用者が実装した機能（遅延評価とリモートスポット運用 3c637f5、多層交通 8c6e7f1、多層施設 419b8dd）と、それに伴う版の引き上げ（10.1・10.3）で、ゴールデンの再取得と台帳の更新が漏れていたもの。いずれも意図した仕様変更で、docs/31〜37 に記載がある。3c637f5 は版を上げずに旧レイアウトの結果を変えていたが、その後 10.3 へ上がっており、10.3 時点の結果として整合する。
2. フェーズ 1 の不具合修正（上記の状態ハッシュの差）。

フェーズ 1 は既存レイアウトの運航結果を（欠航のある日などの条件で）変えるので、docs/22 の方針に従い `SIM_MODEL_VERSION` を `skyport-sim-10.3` → **`skyport-sim-10.4`** に上げ、全ゴールデンを再取得した。`npx vitest run tests/unit/golden` は 30 件すべて合格。再取得したゴールデンと修正後の採取の差は、版の文字列と、それを含む保存データのハッシュだけであることを確認した。

影響: 10.3 以前で**運航中に**保存したデータは、読み込むとレイアウト・会社・日付はそのままで、運航状態だけ復元せず建設モードで開く（警告を表示。従来の版上げと同じ挙動）。保存形式の版は変えていない。
