# 実装計画: ターミナル建物の階範囲のプルダウン一本化（地下だけの建物をパネルから作れるようにする）

> 管理状態: **active（実装済み・PR 化待ち）**
> 作成日: 2026-11-21
> 更新日: 2026-11-21
> 根拠: PO 報告・要望（2026-11-21）「地下だけの建物の場合、level が 1 までしか対応してなさそうで建てられない。できればプルダウンのほうに一本化したい」
> 正本: 本書は実装計画。地下ターミナルのデータモデルの正本は機能G の設計（`docs/implementation/planned/underground_terminal_pbb_agt_plan.md` §G.2-3 の変換規則）。

## 1. 現状と課題

### 診断（コードと実測で確認済み）

- **新規配置は現行でも可能**: Toolbox のターミナルツールには「最下階・最上階（絶対階）」のセレクタと地下のみプリセットがあり、変換規則（基底階 = 最下階、階数 = 最上階 − 最下階 + 1、floorRange = [0, 階数 − 1]）で保存される。エディタ経路（ツール → ドラッグ → 確定）で B2〜B1 の棟が置けることをテストで確認した。
- **PropertiesPanel からは建物の階範囲を直接変えられない**（これが「建てられない」の直接原因）:
  - パネルのプルダウン（エリアの最下階／最上階）は **エリアを置ける相対階範囲（floorRange）** を編集するもので、建物の基底階（mapLevel）と階数（levels）は動かさない。地上ターミナルで最上階プルダウンを B1 に下げても、建物自体は 1F〜2F のまま（地下だけの建物にならない）ことをテストで確認した。
  - 既存建物を地下だけにするには「階層」（mapLevel）と `levels` の **2 つの生数値入力を手で一致させる** しかなく、プルダウン派の操作では到達できない。
  - `levels = 1` の建物では最上階プルダウンの選択肢が 1 つ（相対 0）しかなく、「level が 1 までしか対応していない」ように見える。
- 調査したコード: `src/core/layout/levelRules.ts`（terminalFloorRangeOf / levelsInUse / floorRangeInUse）、`src/core/layout/operations.ts`（placeFacility / updateEntity の検証）、`src/editor/tools.ts`（terminalPlacementOf）、`src/ui/Toolbox.tsx`（配置時の絶対階セレクタ）、`src/ui/PropertiesPanel.tsx`（階まわりの3コントロール）。
- 調査したテスト: `tests/unit/undergroundTerminalG.test.ts`（機能G の受入）。コアの配置・検証は地下単独棟を正しく扱えている。

### 実装済み（変更前）

- 機能G: 地下ターミナルの配置解禁、floorRange、配置時の絶対階セレクタ＋変換規則、地下係数の建設費、孤立警告。

### 不具合・未実装

- パネル側に「建物の絶対階範囲」を編集する導線がない（本計画の対象）。
- パネルの階コントロールが3系統（階層の数値入力／levels の数値入力／floorRange の相対プルダウン）に分かれ、相互の追随が片方向で分かりにくい。

### PO 追加指示（2026-11-21）

- 一本化のトレードオフ（パネルからエリア範囲だけを建物範囲より狭く絞る操作ができなくなる）について、PO は「詳細設定としておいて」と決定。主操作は絶対階プルダウン対のまま、エリア範囲の絞り込みを折りたたみの「詳細設定」として残す（T4）。

## 2. 目的・対象範囲

### 目的

- PropertiesPanel のターミナル階編集を、**絶対階の最下階・最上階プルダウンに一本化** し、地下だけ／地上だけ／跨ぎのいずれの建物もパネルから作れるようにする。
- `levels` と基底階（mapLevel）はプルダウンから導出される従属値とし、二重管理による不整合をなくす。

### 対象

- `src/core/layout/levelRules.ts`: 階範囲変更の純関数 `terminalSpanPatch` を追加（導出と可否判定の正本）。
- `src/ui/PropertiesPanel.tsx`: ターミナルの階コントロールを絶対階プルダウン対に置き換え。ターミナルについては「階層」数値入力と `levels` 数値入力を表示しない。
- `src/i18n/ja.ts`: 変更できない理由の文言を 1 件追加。
- テスト追加（`tests/unit/terminalFloorSpan.test.ts`）。
- （T4）`src/ui/PropertiesPanel.tsx` / `src/ui/styles.css`: 単独ターミナルに折りたたみ「詳細設定（エリアを置ける階の絞り込み）」を追加し、エリア範囲の相対プルダウン対（内包ターミナルと共有コンポーネント化）を置く。

### 非目標

- データモデル・保存形式の変更（mapLevel / levels / floorRangeMin / floorRangeMax の表現は従来どおり。配置時の変換規則 §G.2-3 と同じ三つ組を書く）。
- Toolbox（配置時 UI）の変更（既に絶対階プルダウン＋同じ変換規則）。
- TerminalWorkspace のフロアタブ、内包施設（floorIndex）の扱いの変更。
- スポット・滑走路など他種別の階 UI。

## 3. 設計方針

- **導出規則**（配置時の変換規則と同一）: 新しい絶対範囲 [最下階, 最上階] に対して
  - `mapLevel` = 最下階
  - `levels` = 最上階 − 最下階 + 1（1〜4。範囲外になる選択肢は UI で無効化）
  - `floorRangeMax` = levels − 1（エリア範囲の上限は建物の最上階に一致させる）
  - `floorRangeMin` = 従来の相対下限を保持する（基底より下のエリア許可＝旧データの地下エリア・地下コンコースの意味を変えない）。ただし新しい階数 − 1 を超える場合はそこまで切り詰める。
- **可否判定**: 範囲外になるエリア（新しい floorRange の外）または内包施設（新しい階数以上）がある場合は変更を拒否し、理由をトーストで出す（`levelsInUse` / `floorRangeInUse` の流儀）。判定は純関数 `terminalSpanPatch`（levelRules）に置き、UI とテストが共有する。確定は従来どおり `updateEntity` の単一 patch（mapLevel + props）で通し、コア側の検証（floorRange の整合・floorRangeInUse・子の階チェック）でも二重に守る。
- **詳細設定（エリア範囲の絞り込み）**: 主操作は絶対階プルダウン対とし、エリア範囲（floorRangeMin / floorRangeMax）の相対プルダウン対は折りたたみ「詳細設定」に副次コントロールとして残す。これにより「建物は 3F まであるがエリアは 2F までに制限する」といった、建物の階範囲から独立した絞り込みが引き続き可能。可否は従来どおり `floorRangeInUse`（UI）と `updateEntity`（コア）の検証に従い、下限は基底より下（TERMINAL_AREA_MIN_LEVEL）まで選べるため旧データの地下エリアの意味も変わらない。相対プルダウン対は内包ターミナルと共有コンポーネント（`TerminalAreaRangeFields`）にし、挙動を一本化する。
- **旧セーブ互換**: 表現は不変なので読み込みの意味は変わらない。floorRange 欠落の旧建物で範囲変更をすると floorRange が明示化されるが、解決値（下限 = 従来下限の保持、上限 = 階数 − 1）は欠落時の既定と一致するケースでは同一であり、エリアの実効範囲が変わるのは PO が範囲変更を選んだ場合だけ（範囲外エリアがある場合は拒否されるため、既存エリアの意味は変わらない）。
- **PO 判断・承認が必要な事項**: なし（PO 要望そのものの実装。版上げ・ゴールデン再採取は不要と判断し、必要になった場合は止まって報告する）。

## 5. 互換性・リスク

- 保存形式／スキーマ: 変更なし（SCHEMA_VERSION 据え置き）。書き込む props は配置時と同じ三つ組。
- シミュレーションモデル版・ゴールデン: SIM_MODEL_VERSION 据え置き。運航・能力計算には触らないためゴールデン不変が前提（変わる場合は止まって報告）。
- 既存データ: 範囲変更をしない限り一切書き換わらない。範囲変更時も、範囲外になるエリアがある場合は拒否され、既存エリアの階の意味（建物基底からの相対）は従来どおり。
- 失敗時の切り戻し: UI と純関数の追加のみ。戻す場合はパネルの該当節と関数の追加を取り除けば従来動作に戻る。
