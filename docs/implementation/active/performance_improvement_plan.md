## 1. 背景と監査要点

大規模空港（有効契約175件・1日327便規模）で運航の体感が重くなってきた。コード監査の結論:

- **負荷は「tick 計算」と「描画」の2系統**に分かれ、どちらが支配的かは監査時点では未計測だった。構造上の要因は両方にあるため、まず計測で切り分けるのが実施順の前提。
- **tick 側の本命は旅客**: `stepPassengers`（`src/core/sim/passengers.ts`）が全便＋全アクティブグループを毎tick走査する。グループは最大5人単位（`MAX_GROUP_SIZE`）で便ごとに生成され、出発最大3時間前から滞留するため、大規模空港ではアクティブグループが数千オーダーになりうる。
- **スポット割当 `assignStand` はスパイク型**: 候補スポット×滑走路ごとに全ネットワークのダイクストラ（`findPath`）を回し、1回の割当で数百回規模になりうる。到着が集中する時間帯に tick が跳ねる。
- **描画は毎フレーム全面再描画**: `MapRenderer.draw` はレイアウト・旅客点・機体を毎フレーム描き直し（地形テクスチャと混雑KPIのみキャッシュ）。さらに一時停止中でもフレームループが回るため描画は止まらない。
- その他毎tickの定数倍: 手荷物 `stepBaggage` の複数回全走査、`detectConflicts`（地上移動中機体の二重ループ、診断専用）、`sortedValues` の複数回ソート、React パネルの約10Hz再描画＋全便ソート等の集計。
- 既存の軽量化機構: 店舗・ラウンジは `serviceGranularity`（既定 `aggregate`）でカテゴリ×ターミナル集約済み。1日スキップとシナリオ実行は「描画なしで sim だけ回す」実績経路。tick 上限120/frame＋`dropped` は安全弁（ゲーム内時間が遅れる形で劣化する）。
- **sim は描画に依存しない**: 進行は `src/editor/simRunner.ts` の rAF ループが担い、地図は購読して描くだけ。このため地図なし実行は表示分岐だけで実現できる。

### 3.1 第1弾: 計測（実装済み）

- `src/core/sim/perfStats.ts`（新規）: 軽量アキュムレータ。直近ウィンドウ（取得以降）の平均 ms と規模カウンタを保持する。`takePerfSnapshot()` が平均を返してリセットする。core は実時間に依存できないため、時計は editor 層（simRunner）が `setPerfClock` で注入する（未注入時は計測値 0 で、結果に影響しない）。
- `stepSimulation`（`src/core/sim/simulation.ts`）のサブステップ境界に計測チェーンを挿入: 経済・日次／障害・天候／滑走路・誘導路管制／機体／旅客／アクセス・バス／手荷物／地上支援／競合検知／分析記録／その他。時刻の呼び出しはサブステップ単位までに抑える。
- 描画側は `MapView` の draw 呼び出しで所要時間を記録。フレーム側は `simRunner` がフレームあたり tick 数と `dropped` 発生を記録する。
- 表示: 運航画面左列（運航コントロール内）に性能パネル（`src/ui/operate/PerfPanel.tsx`）。トグルで開閉し既定は閉。開いている間は5秒ごとにウィンドウをリセットし、表示は購読更新のたびに読み取る。表示項目: tick 合計 ms（平均）、サブステップ内訳の上位5件（ms と割合）、描画 ms（平均）、旅客グループ数／機体数／手荷物数、tick/フレーム、dropped の有無。
- **計測は運航結果を変えない**: 状態・乱数・処理順には触らず、ゴールデン／運航フィンガープリントが不変であることをテストで確認する。

### 3.2 第2弾: 地図なしモード（実装済み）

- 運航画面（`src/ui/operate/OperateLayout.tsx`）に表示分岐を追加: 地図あり（従来どおり `Viewport`＋浮動の運航表）／地図なし（`Viewport` をアンマウントし、中央は運行表の全列表示 `FidsBoard` を主表示にする）。左の操作ナビと右列（状況・詳細）は地図なしでもそのまま使える。
- 切替は運航途中でも可能（地図のマウント／アンマウントだけで sim に触らない）。切替状態は UI 設定 `opsPrefs.noMap` として localStorage（`skyport.opsPrefs.v1`）に保存する。プロジェクトデータには含めない。切替 UI は運航コントロール内の「表示モード」（`data-testid`: display-map / display-nomap）。
- 機体の選択は運行表の行クリック（既存の `selectAircraftAndFocus`）で行う。カメラフォーカスは store への書き込みのみで地図が無くても例外なく動き、害はない。
- 地図なしで失われるもの（監査 §5.3 と実装の実態）:
  - 地図クリックでの機体・施設選択 → 運行表・カード・一覧からの選択で代替。カメラ追従（2D/3D）は機能自体が不要になる。
  - 選択機体の経路・予約区間の可視化、混雑／課題オーバーレイ、旅客点の表示 → 代替なし（見ないモードとして割り切る。数値は右列カード・ボード側にある）。
  - **地図起点でしかできない操作**: スポット・誘導路の手動の使用停止／再開（選択は地図クリックが主経路）などは、地図なしでは行えない。「地図」に戻して行う運用とし、無理な代替実装はしない（運航コントロール内に注意書きを表示）。
  - 編集操作は運航中は元々不可なので損失はない。
- 効果の前提: 消えるのは描画コストのみ。tick が支配的な空港では体感は変わらない場合があり、その切り分けは第1弾の計測と `dropped` 表示で行う。

### 3.3 第3弾: その他の方法（1〜3 実施済み・4 見送り・5 未着手）

結果を変えないものから順に実施した（2026-11-20）。いずれも運航ゴールデン／フィンガープリント全件不変を確認済みで、`SIM_MODEL_VERSION` は上げていない。

1. **停止中・tick 0 フレームの描画スキップ（実施済み）**: 原因は描画側ではなくループ側だった。`simRunner` の `frame()` が一時停止中も毎フレーム store を更新（`frame` カウンタと `uiVersion` の加算）し、その購読で `MapView` が全面再描画していた。対策として、一時停止中（速度 0）かつ tick が進まず `dropped` の残りもないフレームは store 更新自体を打ち止め、再描画を止めた。再開・速度変更・機体選択・障害対応などの操作はすべて各操作側が store を更新するため、操作直後の再描画は従来どおり起きる。`ops.frame` の表示側の利用者はいないことも確認した。なお 3D ビュー（View3D）は一時停止中もカメラ操作で回し続ける必要があるため対象外。
2. **画面外カリング（実施済み）**: `MapRenderer` に表示範囲（カメラ位置 + ビュー寸法 / zoom、グリッド描画のクリップと同じ式）を導入し、`drawLayout`（施設・スポット・道路・誘導路・節点）、`drawInterior`（エリア・内部設備の図形）、`drawOps`（滑走路状態・予約区間／節点・地上車両・機体シルエット）、`drawPax`（滞在中はエリア矩形、歩行中は代表点）に画面外スキップを入れた。線分は Liang–Barsky 法で正確に判定し、線幅・印の分だけ判定範囲を広げている。ラベル（エリア名・コールサイン等）は画面端に掛かりうるため図形とは判定を分け、見える範囲では従来どおり常に出す。ラベル自体・混雑表示・夜間シェード・滑走路本体は対象外（元々クリップされる／本数が少ない／全面描画が前提）。
3. **結果を変えない小粒削減（実施済み）**: 以下はいずれも「処理対象・順序・乱数消費が従来と同一」であることをコードで確認したものだけ。
   - `sortedValues` の tick 内共有: `stepSimulation` が作る機体一覧 `all` を `runwayControl` / `taxiBlockControl` / `detectConflicts` へ渡し、各所の再ソートをやめた。`all` の算出後に機体レコードの追加・削除が起きない（追加は日次スケジュール生成＝前段まで、削除はスナップショットの間引きのみ）ため同一になる。各関数は同じオブジェクト参照をその時点の状態で読む。
   - 集約サービス（`serviceAggregate`）の facilityById Map: 呼び出しごとの再構築を、layout 由来で不変な `profiles.facilities` をキーにした WeakMap の使い回しへ変更（中身は都度構築と同一）。
   - `stepPassengers` の施設キー一覧: 毎 tick の `Object.keys + sort` を、キー集合が変わったときだけ再構築するキャッシュへ変更。キーの追加は `facility()` の新規作成の場面だけで、そこでキャッシュを捨てる。
   - 滑走路別待ち機数の数え直しの 1 回化: `assignStand` の候補ループ内と `departurePath` の入口候補ループ内で、候補 × 滑走路ごとに全機体を数え直していたものを、ループ前に 1 回だけ数える形へ変更（数える対象・条件・比較式は従来と同一。経路探索は状態を変更しない）。
   - 見送ったもの: `detectConflicts` の間隔化は、衝突件数が運航フィンガープリント（`stats.conflicts`）に含まれるため「結果不変」とは言えず見送り。`stepGround` のタスクソートのキャッシュはソートキーが時変で不変性を担保できない。`stepAnalytics` の複数走査の統合は `analytics.live` のキー挿入順が変わりうるため見送り。
4. **assignStand の2段構え（見送り・設計メモ）**: 結果不変を厳密に担保できないため今回は実施せず、以下を設計メモとして残す。
   - 現行の候補選定は「優先順に最初に往復可能なスポット」であり、無障害コストによる事前順位付けへ変えると、同点・近接コスト時の選択が変わりうる（当初案どおりゴールデン再採取とセットの判断になる）。
   - 結果不変にできる事前絞り込みは「無障害経路でも到達不能な候補の除外」だけだが、現行ループは最初の成功で打ち切るため、成功候補より後ろの候補まで事前に評価すると総作業量が増える場面がある。効果が出るのは「失敗候補が多い」ケースに限られる。
   - 「障害物なし経路」のキャッシュは、予約・閉鎖・block 回廊の状態に依存するため、キーに状態の版数が必要だが現行に版数カウンタが無い。導入する場合は closures／予約の変更をフックする版数管理とセットで行うこと。
   - 代替として項目 3 の「待ち機数の数え直し 1 回化」でスパイクの定数倍の一部を削った。着手条件: 計測で assignStand が支配的と判明した場合に、ゴールデン再採取と `SIM_MODEL_VERSION` の判断とあわせて再検討する。
5. **Web Worker 化（最終手段・未着手）**: スコープに含めるが優先度は最下位。sim 本体（core/sim）は DOM・描画に依存せず分離自体は可能な構造だが、現行 UI は `sim` の可変オブジェクトを直接参照して描画・集計しており、Worker 化にはスナップショット転送（structuredClone）への全面的な置換と、UI から sim を書き換える経路（障害対応・会社操作等）のメッセージ化が必要で特大規模の改修になる。tick の総計算量自体は減らず転送コストが増えるため、第1〜3弾と簡略モードの判断を終えてもメインスレッド占有が問題な場合にのみ着手する。

計測（第3弾の前後比較）: ストレスフィクスチャ（flightsPerDay 120、機体 120・旅客グループ 1,083・手荷物 570 の規模）で 7,200 tick の所要時間を 3 回ずつ測り中央値で比較した。変更前 6.079 ms/tick → 変更後 3.834 ms/tick（約 −37%）。内訳では runwayTaxi（滑走路・誘導路制御）0.28 → 0.06、conflicts 0.34 → 0.03、aircraft（スポット割当を含む）0.41 → 0.23、passengers 3.48 → 2.36 ms/tick と下がった。VM のノイズが大きいため単発の数字ではなく中央値と範囲で見ること（変更後の最遅の回でも変更前の最速の回より速かった）。描画側（カリング・停止中スキップ）はヘッドレス環境で実測できていないが、停止中スキップは「停止中は store 更新が起きず再描画自体が発生しない」構造的な効果、カリングは画面外要素の描画コマンド発行自体を省く。

### 3.4 第6弾: 描画の軽量化（2026-11-21・結果不変）

第2弾（地図なし）・第5弾（無描画）は「描画を消す」受け皿だったが、地図を表示したままの運航では描画コストが残っていた。今回は地図ありの描画そのものを軽くする。

**計測（着手前）**: ユーザーの実セーブ（107 日目、敷地 350×332、滑走路 5・誘導路 621・スポット 128・施設 173・ターミナルエリア 156）から運航を新規生成し（便 930、06:10 時点で機体 465・旅客グループ 4,226・手荷物 1,026・地上車両 914）、`MapRenderer.draw` の所要時間とパス別内訳をヘッドレス（Node、共有 VM）で実測した。第3弾で「ヘッドレスでは実測できない」とした描画側も、Pixi の Graphics 命令発行までは Node で測れる（GPU 側のテッセレーション・ラスタライズは含まない）。

| 条件（1600×900） | draw 平均 | drawLayout | drawOps | その他 |
|---|---|---|---|---|
| 運航・全体表示（zoom 2.71） | 88.7 ms | **79.8 ms** | 7.3 ms | 1.6 ms |
| 運航・zoom 3 | 78.3 ms | **68.0 ms** | 9.2 ms | 1.1 ms |
| 運航・zoom 8 | 33.6 ms | **23.0 ms** | 6.1 ms | 4.5 ms |
| 運航・zoom 8・内部表示 | 25.0 ms | 12.4 ms | 5.0 ms | 内部 6.1 ms |
| 建設・全体表示 | 42.6 ms | **41.7 ms** | — | 0.9 ms |

- **支配的なのは `drawLayout`**（全条件で 5〜9 割）。静的なレイアウト（グリッド・滑走路・誘導路・道路・スポット・施設・節点）を 1 つの `Graphics` へ毎フレーム `clear()` から描き直しており、全体表示では約 6,500 件の描画命令を毎回再発行していた。地形テクスチャだけは従来からキャッシュ済み。
- `drawOps`（機体・車両）は 2 位だが 1 桁 ms。機体は補間で毎フレーム動くため静的化できない。
- 一時停止中の全面再描画は第3弾-1 でループ側から止めてある（本計測の「tick なし」条件でも drawLayout が支配的だったのは、計測ハーネスが draw を直接呼ぶためで、実アプリでは停止中に draw 自体が呼ばれない）。

**採用した最適化: 静的レイヤの Graphics キャッシュ**

- `draw` のうちグリッド＋レイアウト（`this.g` への描画）を、入力が変わらない限り再構築しない。キャッシュキーは「レイアウト参照・解析結果参照・zoom・mapLevel・グリッド表示・ネットワーク表示・ツール」の組。これらがすべて同じなら前回の Graphics 内容をそのまま使う（Pixi は内容が変わらない Graphics のジオメトリを使い回すため、命令発行とテッセレーションの両方が消える）。
- キャッシュ構築時は画面外カリングの範囲を敷地全域に広げて描く。カリングは「画面外を描かない」最適化であり、画面外の図形を描いても画面内の表示は変わらない（GPU がビューポートで切り取る）。これによりパン（カメラ平行移動）では再構築が起きず、追従カメラでもキャッシュが効く。再構築が起きるのは zoom 変更・レイアウト編集・表示レイヤ切替のときだけになる。
- 動的レイヤ（`overlay`: 機体・車両・旅客・選択・混雑・内部の占有など）とラベル、夜間シェードは従来どおり毎フレーム描く。描画順（重なり）も従来どおり。

**採用しなかった候補**

- 描画側での停止フレームスキップ: 第3弾-1 でループ側から実施済み。運航中は補間係数 `clock.acc` が毎フレーム変わるため描画側の署名スキップは効かず、二重化になるだけなので入れない。
- ラベルの間引き・カリング強化: zoom 8 で 3.4 ms/frame（Node 計測）。実ブラウザでは Text の位置設定は安価な見込みで、画面端でラベルが欠けるリスクに見合わない。
- `drawOps` の機体ポリゴン配列の使い回し等の小粒削減: 効果が小さく、今回は見送り（将来課題）。
- `drawInterior` / `drawPax` の静的化: 占有率・旅客位置が時変のため静的化できない。内部表示時の残課題として残す。

**視覚同等性の担保**: キャッシュ構築（全域描画）の命令列が、従来コードで敷地全体が見えるカメラで描いた命令列と一致することを単体テストで確認する（カリングは画面外分を落とすだけなので、全体が見える条件では従来と同一の命令列になる）。あわせて、パンで命令列が変わらないこと（＝再構築されていないこと）、zoom・レイアウト変更で再構築されることをテストする。運航・レイアウトのゴールデンには描画が含まれないため再採取は不要で、`SIM_MODEL_VERSION` / `SCHEMA_VERSION` は据え置く。

**計測（実施後・同じハーネス）**: draw の中央値で比較する（共有 VM のノイズで平均・最大は跳ねるため）。

### 3.5 第5弾: 無描画運行モード（実装済み）

PO 依頼（2026-11-21）: 運行中に地図描画で PC が重くなるため、描画せずに運行できるモードがほしい。第2弾（地図なし）でも残っていた負荷は、運行表（`FidsBoard`）が約10Hzで全便を絞り込み・ソートして最大150行を描くこと、カード類が1秒間隔で集計（`computeKpi` 等）を回すこと、`simRunner` が毎フレーム store を公開し（`uiVersion` は約10Hz）購読側が再描画すること。第5弾はこれらをまとめて止める上位モードとして実装した。

- **設定**: `opsPrefs.noRender`（UI 設定。localStorage `skyport.opsPrefs.v1` に保存し、プロジェクトには含めない。既定 false）。運航コントロールの「表示モード」は 地図／地図なし（運行表）／無描画 の3択になり、`noRender` が `noMap` より優先される。無描画を解除すると直前の表示（地図または地図なし）に戻る。運航途中の切替で sim には触らない。
- **画面**: `OperateLayout` が分岐し、左列は運航コントロールのみ、中央は最小ステータス（新規 `src/ui/operate/HeadlessStatus.tsx`: 日時・資金・評価・着陸/離陸/欠航・速度・dropped 警告と「描画に戻る」「日報を見る」ボタン）、右列のカード類・運行表・アラートは描画しない。上部バー（日報・1日スキップ・運航終了）と振り返りドロワーは従来どおり使え、「締めで止める」設定なら締めの瞬間に振り返りがそのまま開く。
- **公開の間引き**: `simRunner.frame` はモード中、store への公開を約1秒間隔（`HEADLESS_PUBLISH_MS = 1000`）に間引く。日次締めで停止したときと `dropped` の立ち上がりは即時に公開する。tick の進め方（`advanceClock` → `stepTicks` の列と回数）は通常モードと同一で、変えたのは「いつ画面へ知らせるか」だけ。
- **端数 clock の保持（結果中立の要）**: `advanceClock` の端数 `acc` は clock にしかないため、公開を間引く間は最新の clock をランナー内の `pendingClock` に保持して次フレームの入力にする。保持しないと端数が毎フレーム消えて進行が遅れ、結果が通常モードとずれる。clock を外から書き換える操作（速度変更・一時停止/再開・振り返りを開く・次の日へ・スキップからの再開・開始/終了）は `pendingClock` を失効させ、速度変更・一時停止・振り返りは保持中の最新 clock を土台に書き換える。
- **モード中に失われるもの**: アラート表示（重大な障害にその場では気づけない。締めで止める設定にするか、定期的に描画へ戻る運用）、機体・施設の選択と詳細、カード類の数値（最小ステータスと上部バーの資金・評価で代替）、地図起点の操作（使用停止など。描画に戻して行う）。性能パネルは左列に残るが、表示の更新は公開間隔（約1秒）に従う。
- **結果中立の検証**: 変更は editor 層（公開の間引きと表示分岐）と表示設定のみで、`core/sim` には触れていない。ランナー等価性テスト（`tests/unit/headlessRunner.test.ts`: 合成フレーム列で駆動し、状態・会社の JSON が通常モードと完全一致すること、速度変更・一時停止/再開を挟んでも一致すること、公開回数が毎フレーム→約1秒間隔に減ること）、設定保存テスト（`noRenderPrefs`）、公開判定テスト（`headlessPublish`）を追加。運航ゴールデン／フィンガープリント全件不変、`SIM_MODEL_VERSION` 据え置き、保存形式不変。
- **実測**: 実規模（107日目セーブ・890便規模）での tick 側の規模感と、公開回数の削減は §6 の進捗行に記録する。ブラウザ上の描画コストそのものはヘッドレス環境では実測できないため、削減量は「毎フレーム公開→約1秒間隔」「運行表・カード・アラートの描画自体が消える」という構造で示す。

### 3.6 第7弾: 建設画面の軽量化（ツール連動の簡略化）

運航側の第1〜4弾と別に、建設画面（エディタ）の対話中コストを削る。PO の要望: 「誘導路を触っている時は他のものを平面（簡略）で処理する」「ターミナルの作業中は誘導路を触れなくし判定もしない」といったツール連動の簡略化を、検証の恒久的な欠落にならない形で入れる。

計測（実セーブ: 敷地 350×332、誘導路 1,016・スポット 184・施設 328・ターミナルエリア 234。共有 VM のため絶対値は割り引いて読むこと。中央値）:

- `MapRenderer.draw`（全体表示）: 選択ツール 24.7 ms に対し、施設ツールでホバー中は **1,169 ms**。パス別の内訳では描画パス合計は約 22 ms で、残りのほぼ全てが「プレビューのゴースト（仮レイアウト）に対する `analyzeLayout` 全量実行」だった。`draw` はプレビューが成立するとゴーストを描画対象にし、`getAnalysis(ゴースト)` を呼ぶため、ホバーするたびに新しいゴーストへ全量解析（実測 1.1〜2.0 秒/回）が走っていた。
- `analyzeLayout` 単体: 1.1〜2.0 秒（帰属: 空側ネットワーク関係 約 1.4 秒、ターミナル関係 約 1.0 秒、施設関係 約 1.3 秒、スポットの運用可否 約 0.7 秒。相互に重なるため合計は一致しない）。モデル構築だけでも `buildAirsideNetwork` 約 600 ms、`buildTerminalModel` 約 200 ms、`collectFootprints` 約 80 ms。
- `computePreview`（= 実配置操作の試行）: ツールにより 18〜85 ms/回。これを `MapRenderer.draw`・ステータスバー・プロパティパネルの配置プレビューが各々独立に再計算していた（同一フレームで最大 3 回）。
- 配置プレビューの能力計算 `layoutCapabilities`: 130 ms/回をパネルが毎レンダー 3 回呼んでいた（仮レイアウト×2 + 現在×1）。
- ヒットテスト `pickCandidatesAt`: 約 1 ms でクリック時のみ。ツール別のピッカー（`terminalAt` / `pbbPickAt` / `agtStationAt` / `nextTaxiPoint`）は元々そのカテゴリしか走査していない。

設計（いずれも core/sim の運航挙動・保存データには触らない）:

1. **`computeOp` のメモ化（意味不変）**: `src/editor/tools.ts` に単一エントリのキャッシュを入れ、キー（実レイアウト参照・ツール・オプション参照・ホバー座標・ドラッグ下書き参照・内部階）が全て一致すれば前回の結果を返す。描画・ステータスバー・パネルの 3 経路が同じ計算を共有し、カメラ移動だけの再描画では再計算が起きない。プレビューと確定が同じ操作結果を使う従来の原則は不変。
2. **ゴースト判定の限定（本節の本体）**: `MapRenderer.draw` は解析を常に実レイアウト（`history.present`）から取る（WeakMap キャッシュ済みの全量解析）。ゴーストの形状は従来どおりゴーストレイアウトから描くが、ゴーストに対して解析を回さない。ゴーストの枠色は配置操作の成否のみで決める（成立 = 緑）。
   - **プレビュー中に表示されなくなるもの**: 接続（STAND_NOT_CONNECTED 等）・立地（UNBUILDABLE_TERRAIN・STAND_NOT_ON_APRON 等）・ターミナル充足（TERMINAL_NO_* 等）といった、配置操作は成立しても解析が付ける診断は、プレビュー中の枠色には反映されない。スポットの接続ドットやホールドショート印もプレビュー中は実レイアウト時点の表示になる。
   - **境界での全量検証の保証**: (a) 配置確定時 — 確定したレイアウトが新しい実レイアウトになり、次の描画・パネル表示で全量解析が従来どおり実行され、診断は課題マーカーと課題パネルに即時表示される。(b) ツール切替時 — プレビューが消え、実レイアウト＋全量解析の表示に戻る。(c) 保存前 — 保存されるレイアウトデータ自体は配置操作（op）の検証を通ったものだけで構成され、解析は元々診断（保存可否を決めるものではない）ため、無効なレイアウトが黙って保存される経路は生じない。自動保存（localStorage）も同じ op 経由のレイアウトだけを書く。(d) 運航開始時 — 運航モードの描画・警報は実レイアウトの全量解析を使う（従来どおり）。
3. **`layoutCapabilities` の同一性キャッシュ（意味不変）**: 純粋関数なので `WeakMap<AirportLayout, CapabilityReading[]>` で同一レイアウトへの再計算を止める。呼び出し側は結果を読み取り専用で使う（調査済み）。配置プレビューの 3 回呼びは「仮レイアウト 1 回 + 現在 1 回（初回のみ）」になる。
4. **ラベルのツール連動限定（描画の簡略化）**: 配置ツール使用中（建設モード・選択ツール以外）は、そのツールのカテゴリのラベルだけを描く（誘導路ツール = 滑走路番号＋誘導路名＋誘導路ノード名、スポット = 滑走路番号＋スポット名、施設・エリア = 滑走路番号＋施設名、PBB = 滑走路番号＋スポット名＋施設名、AGT = 滑走路番号＋施設名、滑走路・道路・土地 = 滑走路番号のみ）。選択ツール・通常表示の見た目は変えない。zoom ≥ 8 のラベル走査・発行（実測 約 10 ms/フレーム）の大半が対象外カテゴリだったための削減。
5. **採用しなかったもの**: ヒットテストのカテゴリ限定（実測 約 1 ms・クリック時のみで効果がなく、ツール別ピッカーは既にカテゴリ限定）。課題マーカー・接続線オーバーレイのカテゴリ限定（実測合計 0.5 ms 以下で効果なし）。`analyzeLayout` 自体のカテゴリ分割（チェック同士が network・terminal モデルと相互依存し、課題の意味論を変えるリスクが高い。代わりに「対話中は限定し、境界で全量」という本設計で対応）。描画の静的レイヤキャッシュは第6弾の担当範囲のため本節では触らない。

受入: 同一セーブ・同一操作での変更前後計測（ゴースト表示中のフレーム時間、プレビュー計算回数）。エディタ関連の既存テスト＋新規テスト（メモ化の同一性、ゴースト枠色の意味、境界での全量検証、ラベル限定）。運航ゴールデン不変（運航コードに触らない）。`SIM_MODEL_VERSION`・`SCHEMA_VERSION` 据え置き。

実施結果（2026-11-21、同じ実セーブ・同じベンチ）: 施設ツールでホバー中のフレームは **1,169 ms → 約 30 ms**（残りは描画パス自体で、第6弾の静的レイヤキャッシュの対象）。ホバータイルが毎回変わるドラッグ相当でも約 31 ms/フレーム（変更前はタイルごとに全量解析が走り秒単位）。新規テスト `tests/unit/editorPerf.test.ts` 4 件（メモ化の同一性・能力キャッシュ・ゴースト枠色＋境界での全量検証・ラベル限定）通過。関連既存テストは通過（shellPhase7b の 2 件と gaps510 の 1 件は pristine main でも同一に失敗する既存失敗で、本変更とは無関係と切り分け済み）。tsc・ビルド・ESLint 通過。残りの支配項は `drawLayout`（全体表示で約 25〜35 ms）で第6弾の担当範囲。

### 3.7 第8弾: 実セーブ基準の tick・画面更新の軽量化（2026-11-23・結果不変）

- **計測基準**: ユーザーの実セーブ `mainplay1-20261121-1141`（107 日目、契約 450 往復/日・890 回/日・旅客 約 12 万人/日、スポット 128・滑走路 5・施設 173）。レイアウトと会社から新規に運航を立ち上げ、1 日分（06:00〜翌 06:00）を 1 時間ごとの tick 平均で比較。CPU プロファイル（Node の `--cpu-prof`、ブラウザは CDP Profiler）で関数単位に特定した。
- **変更（いずれも結果同一）**:
  1. `nightOps.queueSec` / `standReleaseAt`: 件数・最大値だけを求めるのに全機体を毎回 ID 順ソートしていた（出発機ごと×毎 tick）。走査順に依存しないため並べ替えを除去。
  2. `apronBus.configuredBusGate`: `resolveBusGateForStand`（経路探索を伴う）を (コンテキスト, スポット, 閉鎖ゲート) でメモ化。運航中にレイアウトは変わらず、変われば `ctx` ごと作り直されるため。
  3. `apronBus.createRequests`: 2 つの効果（到着の到達不能化・運行の作成）はどちらも「未配車のバス待ちグループ」がある便でしか起きないため、`activePax` に該当がなければ全便走査を省略し、ある場合も該当便だけ詳細を見る。
  4. `sortedValues`: 比較のたびの文字列切り出し・数値解析をやめ、要素ごとに比較キーを 1 回だけ作る（比較規則は compareIds と同一）。`sortedValuesCached` で tick 内の機体一覧を、キー集合と参照が同じ間だけ使い回す（O(n) の検証つき）。
  5. `stepDepartureFlight`: スポット到着前・旅客生成前・搭乗未開始・計画ゲート決定済み（または計画スポットなし）・生成リード前の出発便は、どの分岐も状態を変えないため早期 return（深夜に翌日分の出発便が大半を占める）。
  6. `stepAnalytics`: 全機体の 2 回走査を配列確保なし（for...in。列挙順は Object.values と同一）・Set 判定に。
  7. 画面: `deriveAlerts`・`buildAttentionItems` を uiVersion 単位で画面間共有（アラートスタック 2 回・要対応バッジ 2 か所・要対応一覧で計 4〜5 回 → 1〜2 回）。
  8. `simRunner`: 描画のあるモードでは 1 フレームの tick を「描画・画面更新の実測 × 4（最低 50ms）」の予算に収める（上限は従来どおり 120）。描画が軽いモードでは画面が滑らかになり、進行速度の低下は最大約 2 割。描画が重いと予算が上限に達し従来と同じ進み方になる。無描画モードは従来のまま。
- **同一性の確認**: 実セーブ 1 日分の最終状態（SimState＋会社）のハッシュが変更前後で一致（`25e25318…`）。ゴールデン・legacyFingerprint は main で既に失敗している 6 件が出力まで同一で、ほかは全件合格。shadow 照合（`passengersEventShadow`）合格。新規テスト `tests/unit/perf8.test.ts`。
- **結果（同一 VM、他の処理なしで順に実行）**: Node の tick 平均は日中 5.84 → 4.58 ms（−22%）、深夜 2.18 → 1.17 ms（−46%）、最混雑時間帯 7.46 → 6.29 ms、1 日分の実時間 387 → 285 秒。ブラウザ（GPU なしの Headless Chromium・×600）は地図 ×156 → ×222（1.1 → 1.7 fps）、地図なし ×234 → ×349（3.7 → 6.1 fps）、無描画 ×306 → ×336。
- **残る課題**: 日中は旅客処理（グループ処理・経路探索 `findPaxRoute` の Dijkstra が毎回 sort する実装）と機体処理が主で、×600 の目安（約 1.67 ms/tick）にはまだ届かない。次段の候補は (a) `findPaxRoute` の優先度付きキュー化と経路キャッシュ、(b) 旅客の睡眠対象の拡大、(c) Web Worker（第3弾-5）。地図描画は GPU なし環境では 1 フレーム 200ms 級で、実機での計測が必要。

## 4. 簡略モード（保留）

- 内容の想定: 既存 `serviceGranularity` の第3粒度として、旅客グループのバッチ拡大、手荷物の件数集約、経路探索キャッシュ、診断・記録の間引きを束ねるモード。
- **保留の理由**: 簡略化は乱数消費と判定粒度を変えるため**運航結果が変わる**。導入には docs/21 の規則どおり `SIM_MODEL_VERSION` の版上げ、モードの保存・日報への記録、ゴールデンのモード別管理がセットで必要になり、表示・計測系の改善とは別枠の判断になる。
- **再開条件**: 第1弾の計測で tick 側（特に旅客）が支配的と判明し、第3弾までの削減でも不足する場合に、版上げの承認とあわせて再検討する。

## 5. 受入条件

- 計測: 運航ゴールデン／フィンガープリントが変更前と一致する。性能パネルで tick 内訳・描画・規模・dropped が読める。
- 地図なしモード: 地図なしで運航が進み、運行表の行クリックで機体を選択でき、左の操作・右列の状況表示が使える。途中切替で運航が止まらない。切替状態が再読み込み後も保持される。
- 第3弾以降: 各項目ごとに「結果不変」か「ゴールデン再採取あり」かを明記してから着手する。
- 第3弾 1〜3: 結果不変（運航ゴールデン／フィンガープリント全件一致、`SIM_MODEL_VERSION` 据え置き）。第3弾-4 は結果不変を担保できず見送り（設計メモは §3.3）。
- 無描画運行モード: 無描画で運航が進み、最小ステータス（日時・資金・評価・発着数）が約1秒間隔で更新される。左の運航コントロールで一時停止/再開・速度変更・モード解除ができ、「締めで止める」設定では日次締めで振り返りが開く。公開を間引いても運航結果が通常モードと完全一致（ランナー等価性テスト）し、運航ゴールデン／フィンガープリント全件不変、`SIM_MODEL_VERSION` 据え置き。
- 第6弾: 結果不変（表示内容不変）。静的レイヤの命令列が従来（全体表示時）と一致し、パンで再構築されず、zoom・レイアウト・表示レイヤの変更で再構築されることを単体テストで確認する。実セーブ計測で drawLayout の毎フレーム再構築が消えていること。
- 第7弾（建設画面）: 結果不変（運航コードに触らない）。プレビュー中の診断表示の限定が恒久的な欠落にならないこと（配置確定・ツール切替・保存・運航開始の境界で全量検証が走る）を新規テストで確認する。実セーブ計測で施設ツール・ホバー中のフレーム時間が 1,169 ms → 約 30 ms になること。
