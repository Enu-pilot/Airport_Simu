## 1. 現状と課題

- 就航都市データには貨物需要指数があるが、現行の需要配分・契約・運航・収支で貨物輸送として扱っていない。
- 航空会社データに貨物サービスを提供する会社はなく、貨物便契約・貨物専用便の生成もない。
- 機種カタログには貨物室容積を持つ機種があるが、旅客手荷物と一般貨物の積載・荷役は別管理になっていない。
- 手荷物仕分け場・乗継手荷物は実装済みだが、貨物ターミナル、貨物上屋、貨物用荷役能力、貨物トラック需要は未実装。
- 貨物需要指数を追加しただけで貨物輸送が実装済みとは扱わない。旅客手荷物・預け手荷物・郵便・一般貨物を混同しない。

## 2. 目的・対象範囲

### 目的

旅客輸送と独立した貨物需要・貨物便・貨物施設・荷役・陸側搬出入・収支を追加し、貨物空港・旅客空港・複合空港で異なる経営判断を成立させる。貨物機能は空港格Tier3〜7で段階解放し、空港の成長報酬として位置づける。貨物運営は昇格の必須条件にせず、旅客中心の空港も最高格を目指せるようにする。既存の旅客便・旅客数・手荷物の結果は、貨物機能を有効にしない保存データでは変えない。

### 対象

1. **貨物データ**
   - 都市ごとの貨物需要指数を、路線別・日別貨物需要へ変換する。
   - 航空会社カタログに貨物サービス・貨物契約の適格条件を追加する。
   - 貨物便・貨物契約に、便数、運航時間帯、貨物需要、契約期間、収支を持たせる。
   - 機種の貨物室容積を利用する。値がない場合は推定せず、積載能力を未算出または対象外とする。
   - 貨物室容積と貨物重量を混同しない。重量上限の実データがない場合、初期版は容積ベースのゲームモデルに限定する。

2. **貨物便と積載**
   - 貨物専用便は旅客を生成しない。
   - 旅客便の貨物室に貨物を積む「ベリー貨物」は、専用便とは別の後続拡張として扱う。
   - 便ごとに貨物需要・割当量・搭載量・積み残しを記録し、需要保存式を設ける。
   - 貨物積載・荷下ろしを折り返し工程へ接続する。手荷物タスクを貨物タスクとして流用しない。

3. **貨物施設・荷役**
   - 貨物上屋または貨物ターミナルを追加し、保管・仕分け・積み付け・荷下ろしの能力を持たせる。
   - 航空機スポットとの貨物搬送接続、トラック側の搬出入接続を検証する。
   - 処理能力は明示されたゲーム内単位（例: 容積単位/時）で統一し、根拠のない重量/時・台/時へ換算しない。
   - 施設階層・建物内配置は、Phase 5 のターミナル・建物構造と整合させる。

4. **陸側貨物アクセス**
   - 貨物トラック需要を、貨物取扱量から集約的に算出する。
   - 道路区間能力モデルを利用し、貨物搬出入が旅客アクセスと共有区間を使う場合は競合を反映する。
   - 初期版では個別トラックの位置・走行アニメーションは必須にしない。車両個別運行が未実装であることを明示する。

5. **経営・表示**
   - 貨物収入、荷役費、施設維持費、積み残し・契約未達を日報・経営分析へ反映する。
   - 貨物需要、契約供給、施設能力、実績取扱量、積み残しを表示する。
   - 空港能力に貨物工程を追加する際は、旅客能力と合算せず、貨物専用の指標として表示する。

6. **空港格との連動**
   - 格による段階解放を行い、格に達しただけで貨物施設・契約・便を自動作成しない。解放後にプレイヤーが設定・建設・契約する。
   - 国内貨物をTier3、国際貨物をTier4、取扱規模拡張をTier5、複数貨物地区と道路物流の統合をTier6、大規模な国際貨物ハブ運営をTier7で解放する。
   - 貨物運営は昇格の必須条件にしない。貨物路線・取扱実績をネットワーク軸の任意評価材料にできるが、貨物を扱わない旅客中心空港も格7へ到達可能とする。
   - 貨物の取扱量・収支は旅客数・旅客収支・旅客満足度へ換算せず、別軸として評価する。

### 非目標

- 個々の荷物・パレット・コンテナを一個ずつ追跡する物流ゲーム。
- 宅配・倉庫在庫・危険物・温度管理等の詳細物流。Tier4の国際貨物に必要な輸出入確認/通関は簡易なゲーム処理に限定し、書類審査・関税計算等の詳細通関は対象外。
- 郵便、危険物、生鮮品、動物、特殊貨物の個別ルール。初期版では一般貨物に限定する。
- 実在の航空会社の貨物運送契約・運賃を再現すること。
- ベリー貨物を貨物専用便と同時に初期実装すること。
- 個別トラック走行モデルを、道路車両モデルの完成前に独自実装すること。

## 3. 設計方針

- 貨物は旅客モデルから独立したデータ・需要・能力・収支として実装する。既存の PaxGroup、手荷物、乗継手荷物の状態を貨物に流用しない。
- 機種の貨物室容積は候補値として利用するが、貨物重量やペイロードを容積から推定しない。値の出典・状態は docs/16 のデータ品質ルールに従う。
- 都市貨物需要の正規化、1便あたり搭載量、積み残しの扱い、貨物契約評価は BALANCE 等の一元設定に置き、根拠とゲーム値であることを明示する。
- 既存の都市需要モデル・航空会社カタログ拡張と同様、データ追加だけで都市・航空会社・機種を拡張できる構造にする。
- opt-in を必須とする。貨物ルールを持たない会社・保存データは従来の便生成、旅客数、収支、乱数消費を維持する。
- 乱数は既存の会社・運航乱数列へ混ぜない。用途別・日別の専用シードを使い、貨物を無効にしたとき既存ゴールデンが一致することを確認する。
- 貨物施設を旅客ターミナルの処理能力に二重計上しない。共有アクセス・共有GSEだけを明示的な共有資源としてモデル化する。
- 格に応じた機能解放は [空港格8段階化計画](airport_tier_progression_plan.md) と同じ定義を使う。貨物側は解放後の具体的な施設・契約・能力を担当し、格側は到達条件と解放タイミングを担当する。

## 5. 互換性・リスク

- 保存形式: 貨物契約・会社設定・日次状態を永続化する段階で formatVersion の引き上げ要否を評価する。独断で版を上げない。
- シミュレーションモデル版: 貨物ONのときだけ貨物イベントが動く設計を基本とする。既存便の旅客・運航結果を変える場合は SIM_MODEL_VERSION とゴールデンの判断をPOへ提示する。
- 決定性: 貨物の需要・契約・荷役時間は同じseed・入力で一致し、既存乱数列を消費しない。
- 性能: 便・貨物荷物を個別オブジェクト化せず、便単位/時間帯単位に集約する。
- データ品質: cargoVolume が未設定の機種へ架空の貨物量を割り当てない。
- 失敗時: cargo 機能フラグを無効化して旧経路を使用できる設計とし、旅客便の既存データは保持する。
