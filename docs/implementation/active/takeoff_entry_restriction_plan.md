## 1. 現状と課題

- 現行の実装・テスト・仕様:
  - 経営 sim の離陸滑走（`src/core/sim/simulation.ts` の `startTakeoff`）は、整列した入口ノードから運用方向（`runwayConfig.direction`、`orderedRunway` で並べた滑走路ノード列）へ向けて滑走し、`takeoffDistanceM`（機種データ、`src/core/sim/aircraftTypes.ts`）で浮揚を判定する。滑走路端固定ではない。
  - 出発経路の入口候補（同 `entryCandidates`）は **既に**「残り距離 ≥ 離陸滑走距離 + 100 m」の入口だけを目標にしている。つまり入口位置ベースの絞り込みは経営 sim には実装済みである。ただし候補が 1 つも無い場合は経路を作れず、その機体は出発できない（フォールバックは無い）。
  - 計画・適合判定（`src/core/aircraft/compat.ts` の `checkRunway`）は滑走路の全長と必要距離の比較のみで、入口位置は見ない。
  - ATC コア（`src/core/atc/movement.ts`）の taxiOut は `holdShortNodesFor`（停止義務のある全入口）を対象にし、残り長さの絞り込みは無い。ATC セッションは経営 sim とは独立の管制シミュレーションである。
  - エディタ検証（`src/core/validation/validate.ts`）には入口の残り長さに関する診断が無い。`STAND_NO_RUNWAY_ROUTE` は残り長さを考慮しない到達可能性のみを見る。
- 実装済み: 経営 sim の入口候補の絞り込み（残り距離ベース）。
- 部分実装・テスト不足: 絞り込みの結果として出発不能になる構成を、プレイヤーが事前に知る手段が無い。
- 不具合・未実装:
  - 途中入口がその滑走路を使える最大級の機種に使えないことに気づけない（(a)）。
  - スポットから到達できる入口がすべて残り不足で、特定区分の出発が不能になる構成に気づけない（(b)。現行 sim でも発生しうる）。
  - 候補ゼロ時のフォールバック（第2段で扱う）。
  - ATC コア側の絞り込み（第2段で扱う。なお ATC コア単体では、スターター空港で lineUp が入口ノード→誘導路ノードの移動になり、takeoff 経路が始点側へ戻る列になることを実測で確認した。第2段で ATC 側に触る場合は、この経路形状の切り分けが先に必要）。
- 調査したコード・テスト: `src/core/sim/simulation.ts`（`entryCandidates` / `departurePath` / `startTakeoff` / `orderedRunway` は `src/core/sim/context.ts`）、`src/core/atc/movement.ts`、`src/core/aircraft/compat.ts`、`src/core/airside/network.ts`、`src/core/validation/validate.ts`、`src/i18n/ja.ts`（`ISSUE_TEXT`）。

## 3. 設計方針

- 変更するデータ・計算・状態遷移:
  - 新規純関数 `src/core/airside/runwayEntries.ts`:
    - `runwayEntryInfos(net, runwayId)`: 滑走路ノード列の順に、各ノードの始点からの距離（始点ノード位置からの直線距離 × `TILE_M`。`src/core/sim/context.ts` の `distFromStart` と同じ定義）、方向別の残り長さ（forward = 全長 − 距離、reverse = 距離）、誘導路接続の有無（`checkAirside` の入口定義と同一: outgoing / incoming に `kind = 'taxiway'` のエッジがあること）を返す。
    - `departureReachableRunwayNodes(net, standId, size, codeF)`: スポットから出発方向へ到達できる滑走路ノード集合。滑走路エッジと他スポットの接続エッジを除く outgoing の幅優先探索（経営 sim の `findPath` の通行規則に合わせる）。ただし editor 検証の既存診断（`checkAirside` のスポット判定）が `operationalOnly` を使わない構造判定であることに合わせ、本診断も運用状態では絞らない（建設中の誘導路も「届く」として扱う。根拠: 本診断は構成の問題を見るもので、運用状態の診断は `operability` 側の担当）。
    - 必要距離は `validate.ts` 内のローカルヘルパで計算する: その滑走路を `checkRunway` が `ok` とする機種（スポット判定ではスポットの区分以下の機種に限定）について、`takeoffDistanceM` の最大値。`ok` の機種が無ければ対象外（その滑走路は `RUNWAY_TOO_SHORT` 等の既存診断が担当）。compat の `requiredRunwayM` が足す +100 m の余裕は含まない（理由は下記の条件の絞り込みを参照）。
  - 診断（`validate.ts` の `checkAirside` から呼ぶ `checkDepartureEntries` に追加）:
    - `RUNWAY_ENTRY_ALL_SHORT`（warning）: 滑走路 × 方向ごと。誘導路接続のある入口（その方向の終端ノードを除く）が存在するが、残り長さが必要距離を満たす入口が 1 つもない。`params: { direction, maxRemainingM, requiredM }`、`at` は最も残りが長い入口ノード。
    - `STAND_NO_DEPARTURE_ENTRY`（warning）: スポットごと。滑走路へ到達可能（到達できる滑走路ノードがある）で、そのスポットの区分に適合する機種を受けられる滑走路が存在するのに、到達できる入口の残り長さが両方向とも必要距離未満しかない。`params: { size, requiredM }`（requiredM は候補滑走路のうち最小の必要距離）。対象外: スポット未接続・滑走路到達不可（既存コードが担当）、その区分の機種が使える滑走路が無い場合（`STAND_ROUTE_SIZE_LIMITED` 等が担当し、二重に出さない）。
  - 重大度の理由: どちらも、その方向・そのスポットでは対象機種が出発不能になる実害のある構成問題なので warning。ただし判定は機種カタログの「最大級」基準で、より小さい機種では運航できるため error にはしない（`STAND_ROUTE_SIZE_LIMITED` が warning である前例とも整合）。
  - 条件の絞り込み（実装時に確定。経緯は §8）: 当初案にあった「途中入口が最大級に使えない」旨の info 診断（`RUNWAY_ENTRY_SHORT`）は作らない。通常のインターセクション運用でも常に出るノイズであり、検証ゴールデンの基準レイアウトであるサンプル空港・スターター空港・自由形フィクスチャでも発火してゴールデンを壊すため。同じ理由で、必要距離は +100 m の余裕を含まない離陸滑走距離そのものとし、余裕分だけ足りない境界ケース（自由形フィクスチャで 42 m 不足の事例）では出さない。
  - 文言は `src/i18n/ja.ts` の `ISSUE_TEXT` に追加する（`Record<IssueCode, ...>` の網羅により tsc が強制する）。
- 依存関係・呼び出し元／呼び出し先:
  - `validate.ts` は既に `../sim/aircraftTypes` を import している（`takeoffDistanceM` を追加）。`../aircraft/compat`（`checkRunway`）と `../airside/runwayEntries` の追加 import に循環は無い（compat・runwayEntries は validation を import しない）。
  - `analyzeLayout` の呼び出し元（エディタ UI・運航前チェック）は、issues が増える以外の影響を受けない。`operability` の判定には新コードを使わない（warning は運用可否を変えない）。
- 既存データ・既存挙動を守る方法:
  - 追加のみで、既存の診断コード・条件・重大度は変更しない。シミュレーション本体（sim / atc）には一切触らない。
  - 新診断が既存の検証テストやサンプルで誤発火する場合は、期待値を弱めず、診断条件の側を実態に合わせて絞り、その判断を §8 に記録する。
- 運航中の検出（日報・ジャーナル）を第1段に入れない理由:
  - イベントログと日報はゴールデンのダイジェスト対象であり、「ゴールデン全件不変」の受入条件と衝突する。
  - 第1段の目的は建設時点で気づけることであり、エディタ検証で足りる。
  - 運航中の記録は、第2段でフォールバック挙動を定義する際に「フォールバックが発動した」記録としてセットで検討する。
- PO 判断・承認が必要な事項: 第2段の実施可否とフォールバック方針（§10）。第1段の診断コード・重大度は本書の設計で確定し、棚卸し結果とあわせて報告する。

## 10. 第2段の設計下書き（未着手・PO 判断待ち）

- 対象の切り分け: 経営 sim の入口候補の絞り込みは実装済みのため、第2段の不足は次の 2 点。
  - (i) 候補ゼロ時のフォールバック（現在は経路が作れず出発できない）。
  - (ii) ATC コア側に残り長さの絞り込みが無いこと（経営 sim とは独立の管制シミュレーションとして扱うかは PO 判断）。
- フォールバック方針案: 候補ゼロの場合に限り、到達可能な入口のうち残り長さが最大の入口を「制限緩和」として使い、その発動を日報・ジャーナルに記録する（黙って使わない）。代替案は、出発を翌日へ送る／欠航にする。現行の候補ゼロ時の帰結（便がどうなるか）を実測で確認してから PO が決める。
- 方向別判定: 判定は運用方向（`runwayConfig.direction`）に対してのみ行う。`orderedRunway` の距離を使う現行 `entryCandidates` の形を維持する。
- ATC コア: taxiOut の目標（`holdShortNodesFor`）を残り長さで絞る。ただし lineUp 後の takeoff 経路形状（§1 の実測メモ）の切り分けが先に必要。
- 版・ゴールデン: 挙動が変わるため `SIM_MODEL_VERSION` の版上げとゴールデン再採取（docs/42 §5 の手順）が必要。セーブ形式は変更しない（判定はすべてランタイム計算）。
- 計画との整合: 計画フェーズの適合判定（全長ベース）はそのまま残るため、「計画では可だが運航では緩和フォールバック」という不整合がありうる。第1段の診断が建設時点の歯止めになる。
