## 1. 現状と課題

### 現行実装

- `src/core/terminal/model.ts` の `buildTerminalModel()` が、ターミナル内部の隣接エリア、上下階の移動設備、ターミナル間連絡設備から旅客用の派生グラフを構築する。
- `src/core/terminal/route.ts` の `findPaxRoute()` は、区域・保安検査・段差なし移動・閉鎖エリア等を考慮して運用可能な経路を探索する。
- `src/core/sim/passengers.ts` が、入口選択、必須工程、搭乗口、到着出口等で経路探索を呼び、経路がない場合は一時閉鎖待ちまたは到達不能に分けている。
- `TerminalTransitLink` は `planned / underConstruction / operational` を保持する。現状は `buildTerminalModel()` と `findTerminalTransferRoute()` が `operational` だけを経路に含める。
- ターミナル内部のエリア間接続は、同じ階の隣接・上下階の重なりから自動生成される。`TerminalArea` 自体に `buildState` はなく、内部接続ごとの建設状態は表現できない。
- `src/core/access/verticalWalk.ts` の `RoadEdge.roadClass === 'walkway'` は駅等から施設へのアクセス用経路であり、通常の `PaxGroup` のターミナル内歩行グラフとは別系統である。
- `src/core/economy/expansion.ts` の建設プロジェクト対象（`entityOf()` / `allIds()`）に `terminalLinks` は含まれていない。リンクに建設状態があっても、既存の工期進行・完成反映と一貫して連携するかは未対応。
- `tests/unit/terminalTransit.test.ts` は、建設中リンクが現在の経路探索に使われないことと保存・復元を検証している。一方、完成後接続可能性を分類するテストはない。

### 不足

現在の実経路探索は「今使える経路がない」ことを検出できるが、次の2つを区別できない。

1. 建設中の通路を含めても目的地まで経路が成立しない。
2. 建設中の通路が完成すれば目的地まで経路が成立する。

このため、構造的な未接続と建設完了待ちを旅客移動・構造検証で別々に扱う共通判定が必要。

## 2. 目的・対象範囲

### 目的

旅客の出発エリアから次の必須目的地まで、経路全体の接続状態を次の3状態で判定する。

| 状態 | 意味 |
|---|---|
| `operational` | 現在、通行可能な経路が存在する |
| `underConstruction` | 現在は通行できないが、建設中の接続設備が完成すれば経路が成立する |
| `unreachable` | 運用中・建設中の接続設備を使っても経路が成立しない |

判定は接続設備1本の状態ではなく、起点から目的地までの経路全体に対して行う。

### 対象

- ターミナル内部の旅客経路（通常の隣接エリア・上下階移動を含む）。
- 明示的なターミナル間連絡設備（`TerminalTransitLink`）。
- 出発・到着・乗継等で `PaxGroup` が次の必須工程へ移動する際の接続判定。
- 建設中の連絡設備が完成したときの経路モデル再構築と、旅客の次回再判定。
- 構造検証での「建設完了待ち」と「未接続」の区別。

### 非目標

- `RoadEdge` の徒歩ネットワークと通常のターミナル内 `PaxGroup` 経路探索の統合は、本書単体の直接実装範囲から分離し、**Phase 5 / 5-16** の統合計画で扱う。5-13の3状態判定は複合グラフに適用できる形で実装する。
- 個別の道路車両・列車の移動実装。
- 新しい旅客需要、旅客数、生成時刻、便割当て、運航スケジュールの変更。
- 建設中設備を実際の旅客が通行すること。
- 混雑・能力・待ち時間KPIの追加（必要なら docs/42 5-03 と別計画で扱う）。

## 3. 設計方針

### 3.1 3状態の判定

旅客条件を共通化したうえで、次の順序で判定する。

1. 運用中の通路だけで目的地まで経路探索する。見つかれば `operational`。
2. 見つからない場合、運用中と建設中の通路を含めて探索する。見つかれば `underConstruction`。
3. それでも見つからなければ `unreachable`。

- `planned` は着工前であり、「建設中・完成待ち」には含めない。
- 運用中の迂回路が存在する場合、別経路に建設中設備があっても `operational` を優先する。
- 複数の建設中リンクを連続して通れば接続する場合も `underConstruction` とする。
- 建設中リンクが途中で切れている場合は `unreachable` とする。
- 返却する経路情報は、状態判定用の将来経路と、実際に歩かせる現在経路を混同しない形にする。将来経路を `PaxGroup.route` に設定してはならない。

### 3.2 共通して維持する経路条件

現行 `findPaxRoute()` の条件を、現在経路・建設完了後経路の双方で維持する。

- 起点・目的地エリアが存在し、正しいターミナルに属すること。
- 接続の方向（一方通行・双方向）。
- 旅客区域と `canMove()` の区域遷移制約。
- 保安検査未通過・通過済みの区別。
- `stepFree` の旅客が階段を利用しないこと。
- 経路の途中で接続が切れず、目的地まで到達できること。

一時閉鎖（`closedAreas`）、施設の窓口数0、輸送能力待ちは、構造上の建設状態とは別の運用阻害要因である。既存の待機・再試行の意味を維持し、これらだけを理由に `underConstruction` と誤分類しない。建設待ちが存在する場合でも、既存の閉鎖・設備待ち理由を失わないよう、判定結果に補助的な阻害理由を持たせるか呼び出し側で区別する。

### 3.3 ターミナル内部の建設状態

現状の `TerminalArea` には `buildState` がなく、隣接エリア・上下階移動の接続は自動生成である。したがって、ターミナル間リンクの状態だけを見て「空港内のすべての通路」を3状態に分類できるとは限らない。

実装前に以下を調査し、最小差分の設計を確定する。

- 建設中にしたい対象がエリア（ホール・通路・階段・エレベーター等）そのものか、エリア間の接続区間かを整理する。
- エリア単位の `buildState` で表現するか、明示的な内部接続データを設けるかを比較する。
- 既存の自動隣接接続・上下階接続・階層設備の意味を変えずに、建設中の接続だけを将来経路グラフへ含める方法を検討する。
- `TerminalArea` に任意の `buildState` を追加する場合は、旧データの欠落値を `operational` と扱えること、編集・費用・保存・検証の整合性を確認する。
- データモデル拡張の必要性・保存互換性・画面編集方法を実装計画へ記録する。現時点では追加フィールドや新しい接続モデルを確定したものとして扱わない。

### 3.4 建設プロジェクトとの連携

`TerminalTransitLink` の `underConstruction` が実際に完成へ進むよう、既存 `expansion.ts` の建設プロジェクト管理との接続を調査・実装する。

- プロジェクトの列挙・検索・同期・削除・完成反映にターミナル連絡設備を含める。
- 形状変更・端点変更時の改修扱い、工事中の編集、取消し・復元の整合性を定義する。
- 工期・建設費は根拠のない値を追加しない。既存道路・通路との整合を調査し、必要な値はPO判断事項として提示する。
- 完成反映は既存の工事完了タイミングを守り、レイアウトから派生グラフを再構築する。建設完了を確認する前に経路を有効化しない。

## 5. 互換性・リスク

- 保存形式: `TerminalTransitLink` は既に建設状態を持つ。内部エリアへ状態を追加する場合は任意項目・旧データ既定値・入出力検証・往復テストを確認する。スキーマ版を独断で変更しない。
- シミュレーションモデル版: 既存レイアウトの旅客経路・待機・到達不能・乗り遅れ結果が変わる場合は、`docs/22` と `sim-versions.json` の規則に従って版の必要性を判断する。版を先に決めない。
- Golden: 期待値を合格目的で変更しない。結果変更が不可避なら、変更前後の差分・主要KPI・理由を提示し、承認後に扱う。
- 決定性: 経路候補・同コスト時のタイブレークは既存ID順の決定性を維持する。接続状態判定のために運航用乱数を消費しない。
- 旅客保存: 既存 `PaxGroup` の ID・人数・発生時刻・工程進捗・便割当てを、判定だけを理由に変更しない。建設待ちによる待機が締切に及ぼす影響は既存締切仕様を維持する。
- 性能: 旅客グループごとに無制限な2重探索を追加しない。必要に応じて同じモデル・同じ条件の結果をキャッシュするが、建設状態・閉鎖・階層・区域などキャッシュキーの不整合を作らない。
- リスク: `TerminalArea` に建設状態がないため、内部通路・階段・エレベーターまで同じ粒度で判定するにはデータモデルの検討が必要。
