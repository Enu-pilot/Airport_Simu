## 1. 現状と課題

- src/core/model/site.ts の既定マップは幅 160・高さ 112 タイル。createSite() は width × height の地形配列を生成する。
- 1 タイルは 25m。既定マップは 4,000m×2,800m、17,920 タイル。
- SiteOptions は幅・高さを受け取る。現状の createSite() には 320×320 の一元的な上限検証がないため、作成 API・UI・保存読み込みの全経路を調べて同じ上限を適用する必要がある。
- 最大 320×320 は 102,400 タイルで、既定マップの約 5.7 倍。大規模マップでは地形配列だけでなく、2D/3D 描画、施設・交通ネットワーク解析、保存・読み込みの性能確認が必要。
- 調査済みの主なコード: src/core/model/site.ts（DEFAULT_SITE_WIDTH・DEFAULT_SITE_HEIGHT・SiteOptions・createSite）。実装開始時に現在のブランチとコードを再確認し、追加の生成・リサイズ・読み込み経路を検索する。

## 羽田空港スケールの受入目標（2026-11-18追記）

- POが確定したゲーム内最大サイズは幅・高さそれぞれ320×320タイル、1タイル25m、最大8,000m×8,000m。最大102,400タイル。新規マップの既定160×112は維持する。
- 国土交通省東京航空局の空港概要では、羽田空港の面積は1,516ha、滑走路はA 3,000×60m、B 2,500×60m、C 3,360×60m、D 2,500×60mとされる。4滑走路・ターミナル・エプロン・貨物/整備地区を含むレイアウト再現を受入ケースにする。
- 8km×8kmの矩形は64km²で、羽田の公表面積15.16km²より大きいが、面積比だけでは東西/南北の外形が収まることは保証されない。公式資料で正確な軸平行の外形寸法を確認できていないため、8kmを実在空港の外形の公称値として扱わない。
- 実装受入では、出典付きの空港配置図/航空写真を基に4本の滑走路、主要ターミナル、エプロン、貨物・整備地区、アクセス線/道路を置き、外周に建設余白を残して320×320内に収まるか確認する。収まらない場合に最大値を独断で変更せず、どの領域が入らないかと選択肢をPOへ提示する。
- 公式参考資料: 国土交通省東京航空局「空港の概況・羽田空港」 https://www.cab.mlit.go.jp/tcab/conditions/04_kanto/haneda.pdf

## 2. 目的・対象範囲

### 目的

- 空港マップの最大寸法を **320×320 タイル**に統一する。
- 1 タイル = 25m として、最大マップを **8,000m×8,000m** とする。
- 大規模マップでも既存の編集・検証・保存・復元・描画が成立することを保証する。

### 対象

- 幅・高さそれぞれの上限定数と、core 側の寸法検証。
- 新規マップ作成・サイズ変更 UI と関連 API。
- プロジェクト検証、保存・読み込み、JSON 入出力。
- 320×320 の性能・メモリ・配列境界・表示の回帰テスト。
- 必要な機能別 Docs と本計画・ロードマップの更新。

### 非目標

- 新規マップの既定寸法を 320×320 に変えること（既定は 160×112 のまま）。
- 既存マップを自動拡張・縮小すること。
- このフェーズで羽田空港の施設配置を再現すること、滑走路・誘導路・ターミナル等の新機能を追加すること。
- 320×320 を超えるマップを許可すること。

## 3. 設計方針

- **寸法上限**: 幅・高さをそれぞれ 1〜320 の整数とする。長方形を許可し、総タイル数は最大 102,400。UI だけでなく、地形生成・サイズ変更・プロジェクト読み込みなど core の入口で検証する。
- **既定値維持**: DEFAULT_SITE_WIDTH = 160、DEFAULT_SITE_HEIGHT = 112 を維持する。既定 seed で生成される地形・配列順序を変えない。
- **保存互換性**: 現行 Site の width / height / terrain を尊重する。上限以内の既存セーブは寸法・地形・施設配置を変えずに読み込む。保存形式の版上げや移行は必要性が確認された場合だけ行う。
- **上限超過の旧データ**: リポジトリ内のフィクスチャ・既存セーブサンプルを調べる。320 を超える既存データが見つかった場合、切り捨て・自動縮小・破壊的な拒否を実装者判断で行わず、影響と選択肢を提示して PO 判断を得る。
- **性能**: 160×112 と 320×320 の同一条件ベンチマークを取り、地形生成、検証、ネットワーク解析、2D/3D 描画、保存・読み込みを測る。測定前に合格閾値を定め、結果に合わせて閾値を後から緩めない。
- **シミュレーション互換性**: マップ寸法の上限だけの変更で運航結果が変わらないことを確認する。SIM_MODEL_VERSION と保存形式の版は独断で変更しない。結果に影響する変更が見つかった場合は作業を止め、差分・KPI・互換性への影響を整理して承認を得る。
- **空港再現性の扱い**: 8km×8km は本ゲームのマップ設計上限であり、実在空港の敷地境界や特定空港の外形寸法を保証する数値ではない。

## 5. 互換性・リスク

- **保存形式／スキーマ／移行**: 現行の Site が寸法を保持しているため、上限の追加だけなら保存形式変更は不要の見込み。読み込み時の寸法制約追加が旧データに影響しないか T1 で確認する。
- **既定マップ**: 160×112 の寸法と同一 seed の地形が一致することを固定テストで保証する。
- **シミュレーションモデル版・ゴールデン**: 運航ロジックに変更を入れない。ゴールデンは原則不変。差が出た場合は更新せず原因を調査し、CLAUDE.md と docs/42 §5 に従う。
- **性能**: タイル数は既定マップの約 5.7 倍。配列・描画・全タイル走査が比例以上に増える可能性がある。測定なしに「問題なし」と判断しない。
- **既存データ**: 320 を超える保存データが確認された場合、移行・互換方針を PO 承認前に決めない。自動 crop・自動 resize は禁止。
- **失敗時の切り戻し**: 上限定数・入力検証・UI 制限を個別に戻せる小さな差分にする。既存セーブの書き換えを行わない。
