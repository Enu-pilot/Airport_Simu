# 5-25 夜間整備・工事 Work Order（計画）

> 管理状態: active（2026-11-19 に着手。PO が SIM_MODEL_VERSION の版上げとセーブデータ連携を承認）
> 要求: docs/42 の 5-25。夜間の作業枠・人員・機材・進捗を Work Order として管理し、GSE・滑走路・誘導路・照明・ターミナル・アクセスの点検/修理/工事と資産閉鎖を調整する。Phase 4 の機体周期整備とは統合し、二重管理しない。

## 前提

- 機体の周期整備は Phase 4（features.periodicMaintenance 系）が既に担う。本計画は「空港資産側」の作業だけを扱い、機体整備の予定とは夜間枠の競合として連携する。
- 夜間の時間帯と方向制約は 5-24（カーフューと方向別許可）が正本。Work Order の実施可能時間はそれに従う。
- 整備士・GSE の人員/機材は既存の units と maintenance 施設の props が正本。新規の人員プールは作らない。

## 設計方針

1. Work Order = { 対象資産、作業種別（点検/修理/工事）、必要人員・機材、所要時間、実施可能窓（夜間枠）、進捗、状態（予定/実施中/完了/延期） } を会社データの任意項目として持つ（欠落 = 機能オフ、旧セーブ互換）。
2. 実施中は対象資産を閉鎖する（滑走路・誘導路は buildState とは別の「夜間閉鎖」として sim が参照する。恒常的な状態変更にしない）。
3. 進捗は夜間枠の経過時間で進み、日次締めで未完分を翌日へ繰り越す。

## 実装記録（2026-11-19）

- **T1**: `CompanyState.workOrders`（任意項目、欠落 = 機能オフ）と `WorkOrder` 型・`addWorkOrder` を company.ts に追加。保存連携: 会社 JSON の往復で欠落しないことをテストで担保し、Work Order を使う会社は**保存形式 7**（PROJECT_FORMAT_VERSION_7）で書く（旧版アプリが読み違えないため）。動く歩道エリアを使うレイアウトも形式 7。
- **版上げ**: SIM_MODEL_VERSION 10.6 → **10.7**（PO 承認）。ゴールデン 9 件は再採取し、差分が版文字列（と、それを含むプロジェクトハッシュ）のみであることを全件確認した。fingerprint は不変（Work Order 欠落時は状態に現れない）。
- **T2**: 実施エンジン `src/core/sim/workOrders.ts`。夜間枠 23:00〜05:00 で開始し、進捗は枠内かつ整備士を確保できた tick だけ進む。実施中のみ対象を一時閉鎖: 誘導路・スポット・ゲートは閉鎖理由台帳に `workorder:<id>`、滑走路は runwayConfig の mode='closed'（元 mode は Work Order 側に保持し、障害による閉鎖と重なるときはそちらの復旧を優先）。窓を出る・整備士不足・完了・延期・削除のいずれでも閉鎖は解ける。テスト workOrders 7/7（夜間開始・理由付き閉鎖・完了解除・昼間不開始・窓外し・整備士不足・滑走路 mode 復旧）。
  - 残: 閉鎖時点ですでに接近中の便の振替（disruptions の releaseInbound 相当）は次段。夜間枠の開始前に閉鎖されるため実害は小さいが、枠開始直前の到着便は対象滑走路へ向かっている場合がある。
- **T3**: 整備士プールは整備施設の engineers 合計（`engineerCount`、既存の正本）を複数件で ID 順に共有。Phase 4 の機体周期整備は日次決済時のチェックで tick 単位の人員を消費しないため、二重割当は起きない。
- **T4**: 経営画面（PlanPanel）に Work Order パネルを追加: 対象（滑走路・誘導路・スポット・ゲート）・作業種別・整備士・所要時間で作成し、一覧で状態・進捗・延期・再開・削除ができる。
- **発生源**: プレイヤーの手動作成のみ。劣化モデルによる自動発生は未実装（別途 PO 判断）。
