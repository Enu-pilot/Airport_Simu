## 1. 現状と課題

### 1.1 実装済み

- `src/core/economy/capacity.ts` はチェックイン・保安検査の時間当たり能力、ターミナルごとの計画需要とボトルネックを算出する。
- `AirportCapacitySnapshot.terminalRows` はターミナル別のチェックイン・保安検査・合成スループット・ピーク旅客数を持つ。
- `CapacityPanel` は計画上のピーク運航時間、空港全体の能力、ターミナル設備・時間帯別需要を表示する。
- `TerminalModel` はターミナルID・各エリアの同時滞在目安容量を持つ。
- `FacilityRuntime` は施設ごとの処理済み人数、待ち時間合計、最大待ち人数を持つ。
- トイレは `RESTROOM_SEC = 180` 秒、施設処理は `RESTROOM_SEC / 2 = 90` 秒/人、サーバー数は `fixtures`。現行モデルの理論値は **1 fixture あたり40人/時**。
- ランプバスは `APRON_BUS_CAPACITY = 60` 人/便。運行単位の人数・運行状態・待ち時間は持つが、往復所要時間を含む定常的な人/時能力式はない。
- アクセスは交通手段別の日次人数・一部の時間帯量を記録するが、現行の主な集計は空港全体で、ターミナル別・方向別の同一時間窓の旅客数は十分に保持していない。

### 1.2 不足・未実装

- 現在の「ピーク」は主に時計時刻の1時間単位で、工程ごとの厳密なローリング60分最大値ではない。
- チェックイン・保安検査以外の工程（アクセス・トイレ・ランプバス等）について、ターミナル別に同じ基準で「ピーク需要 / 能力 / 実績最大処理人数」を比較できない。
- 旅客グループが各工程を通過した正確な時刻・人数の時系列がなく、現行の累計 `served` だけでは時間当たりの最大処理人数を復元できない。
- バスや道路・鉄道などの共有設備を各ターミナルへ単純按分すると、同じ設備能力を重複計上する恐れがある。
- 現在の能力表示は計画値と実績値が混ざりやすい。設備から計算した理論能力、計画需要、運航実績、実績待ちを明確に分ける必要がある。

## 2. 目的・対象範囲

### 目的

空港能力画面に、空港全体の最混雑時間帯とボトルネック、各ターミナルの工程別処理能力を表示する。プレイヤーが「どの時間帯の、どのターミナルの、どの工程が、何人/時で限界になるか」を判断し、増設・配置変更・運航調整へつなげられるようにする。

### 対象

1. **ピーク時間帯の共通評価**: 当日計画および運航実績から最混雑の連続60分を求める。空港全体とターミナルごとの対象時間を表示する。
2. **工程別能力**: アクセス、チェックイン、保安検査、トイレ、ランプバスを必須対象とする。既に能力モデルがある場合は、国際審査・手荷物受取・階層移動・ターミナル間連絡設備なども追加する。
3. **ターミナル別比較**: ターミナル単位で、設備の理論能力、ピーク時間帯の需要、実績最大処理人数、使用率、待ち人数・待ち時間を表示する。
4. **ボトルネック診断**: 能力に対する需要の割合と実績待ちを使い、工程・ターミナル・時刻を特定する。
5. **計画値と実績値の分離**: 運航前は計画値、運航中・運航後は実績値を表示し、データがない項目は未算出とする。

### 非目標

- 実在空港の設計基準・法定処理能力・実際の空港運用を保証するものではない。ゲーム内モデルの値として扱う。
- 旅客個人の属性・身体条件に基づく詳細な施設需要予測は行わない。
- 計算根拠のないアクセス・バス・ゲート能力を、車両台数や定員だけから恣意的に人/時へ換算しない。
- 工程能力の表示を理由に、旅客生成数・運航結果・乱数消費順・既存の処理時間を変更しない。

## 3. 表示・集計仕様

### 3.1 1時間窓の定義

- 基準は**連続するローリング60分**とする。時計の00分で固定した「09:00〜10:00」だけではなく、例えば「09:17〜10:17」の最大値も検出する。
- 共通ピーク時間帯は、ターミナルへ入る旅客（出発旅客のアクセス完了、到着旅客のターミナル流入）を一度だけ数え、その合計が最大になる60分とする。工程を通過するたびに同じ旅客を加算して共通ピークを決めることはしない。
- 各工程は共通ピーク時間帯の需要・実績に加え、**工程自身の最大ローリング60分**と発生時刻も保持する。工程ごとにピーク時刻がずれることを隠さない。
- 1時間分の実績がまだない場合は、実績を0や能力として表示せず「集計中」または「未計測」とする。
- 60分窓の境界・同数時の選択は決定的にする（最も早い開始時刻を採用）。

### 3.2 工程ごとの指標

| 工程 | 能力の扱い | 需要・実績の扱い | 注意 |
|---|---|---|---|
| 空港アクセス | 交通手段ごとの既存能力式を使う。全手段の能力が揃う場合だけ合計を確定 | ターミナル別・方向別・手段別に到着人数を計測 | 複数ターミナルで共有する道路・駅・停留所の能力を各ターミナルへ重複計上しない。接続先が一意に割り当てられない能力は空港全体のみ、ターミナル別は未算出 |
| チェックイン | 運用中・利用可能なカウンター数 × 3600 ÷ `serviceSecPerPax` | 実際に処理を完了した旅客数/60分。計画需要は現行のチェックイン利用率を維持 | 未接続・閉鎖中・建設中の施設を能力に含めない |
| 保安検査 | 運用中・利用可能なレーン数 × 3600 ÷ `serviceSecPerPax` | 実際に処理を完了した旅客数/60分 | 国際出発の出国審査・乗継保安検査は別工程として扱う |
| トイレ | `fixtures × 3600 ÷ (RESTROOM_SEC / 2)`。現行値では1 fixtureあたり40人/時 | 実際にトイレ工程を完了した旅客数/60分 | 旅客の経路上で利用可能なトイレのみ集計。需要は全旅客数ではなく実際の利用人数 |
| ランプバス | 1便あたり定員60人は表示可能。人/時の理論能力は、バスの実際の回送・乗降・運転時間を含む根拠が整うまで未算出 | 完了したバス運行の旅客数をターミナル別に集計し、最大60分処理人数・配車待ち・バス待ちを表示 | `APRON_BUS_CAPACITY` の60人/便を60人/時と誤認しない。共有バスの能力をターミナルごとに重複計上しない |
| その他の工程 | 既存コードに明確な能力式があるもののみ算出 | 実績が計測できる工程のみ表示 | 理論値・需要・実績のいずれかがない場合は項目ごとに未算出理由を示す |

### 3.3 ターミナル別の表示項目

各ターミナルの工程行に、以下を表示する。

- 工程名・対象施設数
- 理論能力（人/時）。根拠がない場合は「未算出」
- 共通ピーク60分の需要（人/時）
- 共通ピーク60分の実績処理人数（人/時）
- 工程自身の最大実績処理人数（人/時）とその時間帯
- 使用率（需要 ÷ 理論能力）
- 最大待ち人数・平均待ち時間・最大待ち時間（測定できる項目のみ）
- 判定（余裕あり / 注意 / 能力不足 / 未算出 / 集計中）

ボトルネックは、同じターミナル・同じ60分窓の需要/理論能力で比較する。現行ルールと整合し、使用率80%以上を注意、100%超を能力不足とする。理論能力が未算出の工程は使用率順位に入れず、実績待ち・配車不足などの観測指標で別枠の警告を出す。

### 3.4 空港全体のサマリー

- 最混雑60分の開始・終了時刻、旅客流入数、空港全体の主なボトルネックを最上部に表示。
- ターミナル別の一覧で、各工程の「能力 / ピーク需要 / 実績最大 / 使用率」を横並びに比較する。
- 工程別ピークが共通ピークと異なるときは、その工程の最大時間帯を併記する。
- アクセス・ランプバスなど共有設備は「空港全体の共有能力」と「ターミナル別の実績利用量」を分ける。ターミナル別能力の合計が空港全体能力を超える表示を禁止する。

## 4. 設計方針・実装対象

想定対象（実装前に現行コードを再確認し、最小差分とする）。

- `src/core/economy/capacity.ts`: スナップショットに共通ピーク、工程別ピーク、ターミナル別の工程メトリクスを追加する。
- `src/core/terminal/capacity.ts`: 各工程の能力計算を共通化する。既存の既定処理秒数・個別設定値を維持する。
- `src/core/sim/passengers.ts`: チェックイン・保安検査・トイレ・国際審査等の工程完了を、旅客人数・ゲーム時刻・所属ターミナル・工程IDとともに計測する。
- `src/core/access/runtime.ts`: アクセス利用を方向・手段・ターミナル別に記録する。現行の共有アクセス経路からターミナルの帰属を一意に決められない場合は割当てを推測しない。
- `src/core/sim/apronBus.ts` / `src/core/sim/types.ts`: バス運行完了時の人数・時刻・バスゲートのターミナルを集計する。理論人/時能力はサイクル時間を正しく定義できる場合だけ追加する。
- `src/ui/CapacityPanel.tsx`: 最混雑時間帯、ターミナル別工程一覧、ボトルネック順位、未算出理由を表示する。
- 関連テスト: `tests/unit/capacity.test.ts`、`tests/unit/sim/*passenger*`、`tests/unit/sim/apronBus.test.ts`、`tests/unit/access*.test.ts`、能力画面の E2E。実在ファイルとテスト構成は着手時に再確認する。

### 4.1 時系列データ・保存

- 完了イベントを使い、工程ごと・ターミナルごと・ゲーム時刻ごとの処理人数を集計する。グループ人数を加算し、グループ数と旅客人数を混同しない。
- 保存量を抑えるため、無制限のイベントログではなく、少なくとも現行運航日のローリング60分を算出できる有限長の時系列・分バケット方式を優先する。
- 計測データはシミュレーション結果を変更しない。乱数、旅客発生数、工程時間、状態遷移、予約ルールへの介入は禁止。
- 保存・復元後もピーク集計を継続できること。旧保存に計測履歴がない場合は、過去分を推定せず「計測開始後の実績」と明示する。
- 任意項目・旧保存互換・保存形式番号・`SIM_MODEL_VERSION` の要否は `project.ts` と既存の版判定を調査して判断する。必要性が証明されるまで版を独断で上げない。
- 5-16 の対外交通統合で、アクセスのPortal/ターミナル所属が確定したら、その経路単位の容量・需要配分を接続する。先行実装時は共有アクセス能力を空港全体のみで表示する。

## 6. テスト計画

- **単体・算式**: カウンター/レーン/fixtures 数、serviceSecPerPax の個別値、閉鎖・建設中・未接続施設、0能力・0需要、複数ターミナル。
- **時系列**: 同じ1時間内に処理時刻が偏るケース、00分境界をまたぐケース、23:30〜翌00:30、日跨ぎ、同数ピーク、複数工程のピーク時刻が異なるケース。
- **人数整合**: グループ5人を1件ではなく5人として集計。乗継・国際・到着/出発・欠航・乗り遅れで重複計上しない。
- **共有資源**: 同じアクセス設備・バス fleet を複数ターミナルが使う場合、能力を重複計上せず、空港全体の値とターミナル別実績の整合を検査。
- **ランプバス**: 60人/便を60人/時と誤表示しない。バス不足・待機・故障・到着/出発・複数ゲート・複数ターミナルの実績を検証。
- **決定性・回帰**: 同一seedの計測結果が一致し、計測追加によって便数・旅客数・待ち時間・乱数列・ゴールデンが変化しない。
- **保存/復元**: 計測中に保存し、復元後の60分集計が連続運航と一致。履歴のない旧保存は「未計測」となる。
- **UI/E2E**: ターミナル切替・ピーク時間帯・工程別ボトルネック・未算出理由・運航前/運航中/運航後表示を確認。
- 品質ゲートは CLAUDE.md に従い、`npm run typecheck`、`npm run lint`、`npm test`、`npm run build`、UI変更後の関連E2Eを実行する。

## 7. 依存関係・互換性・リスク

- **5-16 対外交通統合との依存**: アクセスのターミナル別能力は、Portal/入口/ターミナル間の帰属が確定するまで空港全体値とターミナル別実績を分ける。5-16完了後に共有ネットワークの配分を統合する。
- **5-19 運航モードとの関係**: 5-19 の詳細ターミナルSimulationと競合する独自時計・独自集計を作らず、共通の工程メトリクスAPIを使える設計にする。
- **ランプバス**: 60人/便という定員のみでは人/時能力を出せない。車両の割当・実走行・乗降のサイクルを分析し、妥当な式が導けない場合は理論能力を未算出のままにする。
- **保存**: 計測データは任意項目として旧保存を読める形を優先。形式番号・モデル版を変更する必要があれば、根拠と旧保存テストを追加して判断する。
- **計算性能**: 毎tickに全旅客・全履歴を再走査しない。完了イベント時の加算と有限長バケットで集計し、長時間運航の性能を測る。
- **シミュレーション結果**: 計測が運航ロジックに影響しないことをゴールデン・決定性テストで保証する。期待値やゴールデンを合格目的で更新しない。
