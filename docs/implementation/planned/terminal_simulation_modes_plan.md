# Phase 5 / 5-19 実装計画: ターミナル運航の集約モデルと詳細シミュレーションの分離

> 管理状態: **planned（計画済み・実装未着手）**
> 作成日・更新日: 2026-11-18
> 根拠: PO依頼（2026-11-18）、docs/42 §3.4 要件5-19、既存docs/12・35・44
> 依存: 5-14〜5-16（階・形状・複合体・歩行グラフ）、5-18（専用ターミナル設計Workspace）。Phase2.5は空港全体負荷の性能受入に必要。
> 正本: 本書は実装計画。現行旅客挙動はdocs/12・35・44を参照。

## 1. 現状と課題

- 現在の航空機運航中もPaxGroupを生成し、TerminalModelのAreaLinkを使って施設間の歩行・待ち・サービス・搭乗/退出をシミュレートする。旅客グループは少人数単位（現行最大5人）で、運航tickごとに経路/状態を更新する。
- ターミナル内部は矩形TerminalAreaの集合を基礎とし、チェックイン/保安など一部にserviceSecPerPaxと設備数の個別処理能力がある。ターミナル全体/メッシュで定義する総通過能力、一般店舗・トイレ・通路の汎用処理能力・平均歩行時間profileは限定的。
- PaxGroupの経路は実際の旅客進行・待ち・区域判定に使うため、単純に計算を減らすと到達可能性、搭乗締切、人数保存、補償、手荷物、乗継MCTに影響する。
- 現在は空港の建設画面と運航モードが基本であり、ターミナル内部だけの独立した詳細運用モード/分析clock/旅客動線実験画面はない。

## 2. 目的・対象範囲

- 通常の航空機運航時は、ターミナル全体またはメッシュ単位の集約能力・平均所要時間を利用し、個別旅客の経路探索/サービス状態更新の計算量を抑える。
- 別の「ターミナル詳細運用モード」では、選択したターミナル/複合体の内部動線、階層移動、待ち列、店舗・トイレ、乗継、保安区域、建物間連絡を詳細にシミュレーションする。
- 詳細モードの結果を、建設設計・能力調整へ反映できる形で要約する。

### 非目標

- 初回実装で、航空機運航と詳細ターミナルシミュレーションを同一tickで同時実行すること。
- 詳細ターミナル運用の結果を、承認なく航空便スケジュール・旅客需要・収益へ書き戻すこと。
- すべての旅客を個人単位で再現すること。初期段階は確率/集約batchまたは既存の少人数グループモデルを利用する。

## 3. 設計方針

### 3.1 通常運航モード: 軽量集約モデル

- 集計単位は2方式を持つ:
  - terminalAggregate: ターミナル複合体全体を1単位とする。
  - meshAggregate: 建物内部を一定メッシュ/ゾーンに分ける。各セルは入口/出口、処理機能、歩行時間、通過人数/時、サービス能力、ゾーンを持つ。
- 各ノード/メッシュで、少なくともpassenger throughput per hour、service seconds per passenger、mean walk/travel seconds、queue/holding capacity、operational stateを定義する。店舗・レストラン・トイレ・保安・手荷物・上下移動・連絡通路を機能別に区別する。
- 通常運航では旅客の実行経路を簡略化し、工程ごとの集約人数・サービス処理数・平均歩行時間・能力超過待ちを集計する。旅客数保存（予約・到着・搭乗・退出・乗継・乗り遅れ/欠航）を保つ。
- ターミナル全体モデルは初期の簡易設定にし、メッシュモデルを選んだ場合のみセルごとに集約する。過剰な粒度で全セルを毎tick探索しない。
- Shop/restroom等で需要が発生しない任意施設を使用したことにしない。旅客が利用する工程条件・確率・必要性は既存モデルまたはPO承認した仕様で定義する。

### 3.2 詳細ターミナル運用モード

- 運航中の空港simulation clockとは独立したTerminalSimulationを用意する案を第一候補とする。
- 入力: ターミナル/複合体、時間帯ごとの到着・出発・乗継需要、国際/国内比、stepFree比率、設備の運用状態、通路の建設/閉鎖状態、各工程のサービス能力。
- 内部では5-16の複合旅客経路グラフを使い、旅客グループ/バッチが入口、チェックイン、保安、ショップ/トイレ、ゲート、到着/手荷物、乗継、退出を移動する。
- 旅客区域の境界（出発・到着・国際・乗継）、oneWay、stepFree、エレベーター/エスカレーター能力、ターミナル間/高層通路の所要時間を守る。
- 結果: 工程別通過人数、平均/95 percentile walk time、待ち時間、ピーク滞留人数、設備利用率、経路不能人数、乗継成功/失敗、ターミナル/メッシュ別ボトルネック。
- 詳細モードの結果を保存して再現可能にし、設計画面から同一設定で比較できるようにする。詳細simulationで使うseed・需要表・能力設定を固定する。

### 3.3 2つのモードの対応

- ターミナル全体/メッシュの軽量モデルに、詳細シミュレーションの集計値をエクスポートするcalibration導線を設計する。
- 詳細モードの歩行時間/処理能力を集約profileに変換する際、合計容量とセル間ボトルネックを保持する。単純な平均値で狭い通路のボトルネックを消さない。
- 初期段階では詳細モードは分析専用で、実運航へ自動反映しない。適用前に差分プレビューとPO承認を必要とする。

### 3.4 互換・モデル切替

- 新規設定terminalSimulationMode / terminalOperationalProfileを導入する場合、旧セーブにキーがないときの意味を固定する。
- 旧セーブの航空機運航結果を守るため、旧PaxGroupモデルをlegacyDetailedとして維持する。新規ゲームで集約方式を既定にするのは、性能測定・旅客保存・主要KPI比較後にPOが承認した場合とする。
- 集約モデルは乱数消費順を変えずに追加できるか調査し、困難なら独立seed・モデル版・golden baselineを設ける。
- SIM_MODEL_VERSION、project format、layout schemaを混同しない。運航の旅客結果が変わるならモデル版の必要性を検討し、既存運航中セーブの復元条件を定義する。

## 5. 互換性・リスク

- 現行PaxGroupモデルは既に実際の旅客歩行・待ち・乗継に利用されている。置き換えは新規modeとして段階導入し、旧modeの動作を削除しない。
- 集約モデルの工程計上が重複すると、旅客数・座席/搭乗・手荷物の保存則を崩す。各工程で入力・通過・終端人数の保存式をテストする。
- ターミナル総容量を上げても、通路・エレベーター・保安・改札のセル/リンク容量が低ければ全体が通過できない。容量は経路上のボトルネックを反映する。
- 詳細モードの需要profileと運航中の実旅客を二重計上しない。分析用simulation clockとlive simulation clockを分離する。
- 運航結果が変わる変更はmodel version・golden baseline・旧運航中saveに影響する。変更前後のKPI・性能・seedを記録する。
