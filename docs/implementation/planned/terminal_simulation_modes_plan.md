## 1. 現状と課題

### 1.1 現在すでに動いているもの

- 空港全体のSimulationは時刻を進め、航空機・便・スポット・地上作業・旅客・手荷物等を処理する。日次締め・DayFlowも既存の空港運航フローに属する。
- 現在のターミナル旅客はPaxGroup（1〜5人）単位で生成され、TerminalModel / findPaxRoute()により入口、チェックイン、保安、ゲート、到着・手荷物・出口などを移動する。
- 空港アクセスにはcar / dropoff / taxi / bus / rail / walkがある。出発旅客は分担率で手段を選び、道路遅延・満車・バス/鉄道の時間帯定員・施設からターミナルまでの徒歩時間が反映される。到着旅客はタクシー・バス・鉄道の乗り場待ちを行う。
- アクセス手段は現状、外部所要時間や道路混雑、乗り場容量を集約値として扱う。外部の自動車・バス・列車を個々の車両として全経路移動させる仕組みではない。
- analyzeAccess()では鉄道駅に明示walkway経路がある場合はfindPedestrianRoute()を使う。一方、駐車場・タクシー乗り場・バス停等は主に外部道路への接続とターミナルまでの近接距離で判定され、実際の歩行経路が必須とはなっていない。既存のACCESS_ROUTE_UNREACHABLEも駅の徒歩接続が中心で、全アクセス手段の端から端までの検査ではない。
- RoadEdge.walkway・階層コネクタの徒歩網とTerminalModelの内部旅客網は別系統である。5-16で両者をPortal経由で統合する必要がある。
- 現在はターミナルだけの独立時計・需要シナリオ・詳細運行結果を持つ独立シミュレーションモードはない。

### 1.2 解決する課題

1. 空港全体を1日進める運航と、ターミナルだけを詳細検証する運航を明確な2モードとして提供する。
2. 空港全体運航では、滑走路・誘導路・スポット・航空機・地上作業・手荷物・旅客・対外交通を一緒に処理し、ターミナル内部は全館/メッシュの集約能力と所要時間で軽量に処理する。
3. ターミナル単独モードでは、選択したターミナル/複合体の旅客動線・施設待ち・上下移動・区域境界に加え、鉄道・バス・自動車・送迎・タクシー・徒歩の空港アクセスを含めてシミュレートする。
4. 旅客が外部交通の乗降場所からターミナル入口、必要工程、搭乗口まで、または到着ゲートから出口・外部交通乗り場まで、実際に連続して移動できるかを検証する。

## 2. 目的・対象範囲

### 2.1 モードA: 空港全体運航（1日進行）

- プレイヤーが空港全体を運営する通常モード。既存のSimulation時計・航空便スケジュール・DayFlow・日次締めの仕組みを利用する。
- 空港全体の各サブシステムを同じ運航時刻で進行させる。航空機、滑走路/誘導路、スポット、地上作業、手荷物、旅客、空港アクセス、道路/鉄道アクセス容量、収支・評価を対象とする。
- ターミナル内部はterminalAggregateまたはmeshAggregateの集約プロファイルを用い、通常運航中にすべての旅客の詳細な屋内経路探索を毎tick実行しない。
- 対外交通の手段分担、施設容量、道路遅延、駐車・乗り場待ち、駅/バス停から入口までの歩行時間と接続状態を空港全体の旅客処理へ反映する。
- 1日分の運航結果（日次KPI、手段別アクセス人数、混雑、処理能力超過、旅客人数保存）を日次締めで確定する。
- 既存の運航clockを再利用する。空港全体用に第2の運航時計を作ったり、ターミナル詳細時計と同期させたりしない。

### 2.2 モードB: ターミナル単独詳細シミュレーション

- 空港全体運航とは独立して起動・停止・再実行できる分析モード。対象は選択したターミナルまたは5-15で判定したターミナル複合体。
- 専用TerminalSimulation clock、需要スケジュール、seed、アクセス手段の分担、輸送供給、設備運用状態、通路の建設/閉鎖状態を持つ。
- 対象ターミナル内部の旅客は詳細な経路グラフを進み、施設処理、待ち列、混雑、上下移動、Step-free、保安/国際区域、ゲート、手荷物、出口をシミュレートする。
- 外部アクセスは旅客の発着境界として扱い、駐車場・車寄せ・タクシー乗り場・バス停/バスターミナル・鉄道駅・徒歩入口からの到着と、到着出口から各交通手段への退出をモデル化する。
- 外部交通は初期段階では、一般道路・鉄道の外部接続、便数/頻度、定員、乗り場容量、待ち時間、道路区間容量を集約的に計算する。都市全体のバス・列車・自動車を個々の車両として走行させることは含めない。
- 結果はターミナル設計・全館/メッシュ能力プロファイルの比較材料とする。空港全体の運航時刻、航空便、会社の収支、保存中の運航状態を変更しない。

### 2.3 外部アクセス手段と旅客の移動区間

| 手段 | 空港側の交通施設/接続 | 旅客が歩く区間 | 動的に扱う要素 |
|---|---|---|---|
| 自家用車 | 外部につながる一般道路 → 駐車場 | 駐車場 → 徒歩Portal → ターミナル入口 | 駐車台数、満車、道路混雑、駐車滞在 |
| 送迎・車寄せ | 外部につながる一般道路 → 車寄せ/乗降場 | 車寄せ → 徒歩Portal → ターミナル入口 | 道路混雑、車寄せ容量、乗降処理 |
| タクシー | 外部につながる一般道路 → タクシー乗り場/乗降場 | 乗り場 → 徒歩Portal → ターミナル入口 | 道路混雑、乗車枠、到着時の待ち行列 |
| バス | 外部につながる一般道路 → バス停/バスターミナル | バス停・バスターミナル → 徒歩Portal → ターミナル入口 | 便数、乗り場数、定員、発車間隔、待ち |
| 鉄道 | 外部につながる鉄道 → 駅ホーム/改札・駅コンコース | 駅コンコース → 階層walkway/Portal → ターミナル入口 | 列車本数、定員、駅受入能力、連絡通路能力、待ち |
| 徒歩 | 外周の歩行者入口または徒歩接続を持つ周辺施設 | 外部歩行入口 → walkway/Portal → ターミナル入口 | 入口の接続状態、歩行時間、段差なし経路 |

- 自動車道路・鉄道の辺は、その交通手段の外部ネットワークとして使う。道路や線路そのものを歩行可能な経路として扱わない。徒歩には明示walkwayとPortalを使う。
- バス停/バスターミナル、駅、駐車場、車寄せ、タクシー乗り場は、交通側接続と旅客歩行側接続の両方を持つ。片方だけの接続を「ターミナルまで到達可能」と判定しない。
- 「施設が存在しない/その手段を設置していない」はnotConfiguredとし、任意の交通手段がないこと自体をエラーにしない。設置済みの施設が道路/鉄道/歩行網に接続しない場合は問題として表示する。
- 徒歩は旧セーブの簡略モデルとの互換性を保つ。新規の詳細モードで実経路を検証する場合は、外周歩行入口または明示した周辺施設/Portalを必要とし、既定の外部所要時間を実動線の合格として扱わない。

## 3. 設計方針

### 3.1 空港全体運航: 軽量集約モデル

- ターミナル処理は2粒度を選べる。
  - terminalAggregate: ターミナル複合体または館全体を1単位とする。
  - meshAggregate: 建物内部を一定メッシュ/ゾーンに分けて集約する。
- 各ノード/メッシュは、少なくとも通過人数/時、1人あたりサービス秒、平均歩行/移動秒、待機容量、稼働状態、区域、Step-free可否を持つ。
- 旅客の処理人数は、到着入口、チェックイン、保安、出入国審査、待合、搭乗、降機、手荷物、出口の各工程ごとに集計する。必要な工程・利用確率は既存の旅客仕様またはPO承認したルールを使う。
- 通路・上下移動・Portal・建物間リンクの能力は、実際の経路上の最小能力とする。館全体の平均容量により局所的な狭窄や階段/エレベーターのボトルネックを消さない。
- 外部アクセスの交通手段別人数と、ターミナル内部へ入った人数を別の境界KPIとして持ち、同じ旅客をアクセスとTerminalModelで二重に数えない。
- 旧PaxGroupモデルはlegacyDetailedとして選択可能に残す。集約モデルを新規セーブの既定にするのは、性能・人数保存・主要KPI比較をPOが確認した後とする。

### 3.2 ターミナル単独: 詳細モデル

- AirportDaySimulationとは別のTerminalSimulation state/clockを用意する。空港全体のstate.nowやDayFlowを参照・変更しない。
- 入力: 対象ターミナル/複合体、時間帯別の出発/到着/乗継人数、国内/国際比、旅客属性/Step-free比率、アクセス手段別割合または自動選択、車/バス/鉄道供給、設備状態、通路状態、seed。
- 旅客経路は5-16の複合グラフを使い、外部交通ノードからTerminalPortal、TerminalArea、各必須工程、ゲート/出口、外部交通ノードまで進む。
- 出発旅客: 外部交通到着 → 交通施設 → 徒歩Portal → landside入口 → 必須工程 → boarding gate。
- 到着旅客: arrival gate → 到着/入国等の必須工程 → baggage claim（対象旅客のみ）→ landside出口 → 徒歩Portal → 交通施設 → 外部交通退出。
- 乗継旅客は既存の乗継ルールに従い、到着側/出発側の空港外アクセスへ重複計上しない。異なるターミナルを移動する場合は5-16の運用中連絡設備だけを使う。
- すべての旅客は個人単位にせず、初期段階は既存PaxGroupまたは確率batchを使う。乱数は空港運航側から独立したseed streamとする。
- 結果: 手段別利用人数/比率、交通施設の容量・待ち、Portalごとの流入出、歩行距離/平均・95 percentile所要時間、工程別待ち、ピーク滞留、Step-free到達率、経路不能人数、搭乗締切遅れ相当、退出完了率、ボトルネック。
- Door-to-Door KPIの定義と集計規則は5-23を正本とする。出発は外部交通境界/交通施設から搭乗ゲート、到着は到着ゲートから外部交通境界、乗継は到着ゲートから乗継便ゲートまでを別旅程として扱う。
- 総所要時間・工程別時間のp50/p95は旅客人数で重み付けする。旅客グループ数だけを母数にせず、未完了・経路不能を0秒として分位点へ含めない。
- 搭乗ゲートへの期限内到着、実際の搭乗完了、乗り遅れを別KPIにする。締切は既存の搭乗/バスゲート状態遷移を正本とし、予定出発時刻から固定分数を推測しない。
- Step-free旅客は独立した分母で到達率・期限内到達率を算出する。集約モードに個別時刻が存在しない場合、p50/p95を平均値や0で代用せず未計測とする。

### 3.3 全経路の接続検証

接続判定は「構造上の経路」と「交通サービス/容量」を分ける。未設置の交通手段をエラーにはしない。

| 接続状態 | 判定 | 旅客の実移動 |
|---|---|---|
| operational（通行可能） | 必要な全区間が運用中で、区域/方向/階層/Step-free条件を満たす | 利用可能 |
| underConstruction（建設完了待ち） | 運用中の経路はないが、建設中を含めれば全区間をつなげる | 利用不可。完成後の予測表示だけ |
| unreachable（未接続） | 運用中・建設中を含めても接続できない | 利用不可。原因と断線位置を表示 |
| notConfigured（未設置） | その交通手段の施設・サービスを空港側に設定していない | 任意手段として非対象。エラーにしない |

- noService（鉄道サービス条件など）、noCapacity（本数/台数/乗り場能力が0）、closed（一時閉鎖）は経路の3状態とは別のサービス状態として表示する。経路がつながっているだけで運行可能/容量十分と判定しない。
- 交通手段ごとに、空港境界/外部ネットワーク → 交通施設 → 歩行Portal → ターミナル入口 → 必須工程 → 各対象ゲート、または各到着ゲート → 必須工程 → 出口 → Portal → 交通施設 → 外部ネットワークを検査する。
- 出発はゲート/旅客区分ごと、到着はゲート/旅客区分ごとに検査し、ひとつの入口から一部ゲートだけ到達できる状態を全館合格にしない。
- 国内/国際、出発/到着、transfer、Step-freeを別条件で検査する。Step-free旅客には階段のみの経路を合格にしない。
- 建設中経路は将来予測として表示するだけで、通常運航・詳細モードの旅客は通行させない。
- 経路上の最大ボトルネック能力（人/時）、所要時間、未算出能力の有無を返す。未算出は0とも無限大とも扱わず「未計測」と表示する。

### 3.4 UI・操作導線

- モード選択で「空港全体運航（1日進行）」と「ターミナル単独詳細シミュレーション」を明確に分ける。
- 空港全体運航は既存の運航画面/時計/日次締めを維持し、ターミナルの集約方式とアクセス状況を表示する。
- ターミナル単独モードは対象のターミナル/複合体、需要profile、時間帯、アクセス交通供給、Step-free比率、seedを選んで開始する。
- ターミナル設計Workspace（5-18）に「動線チェック」パネルを設け、交通手段×出発/到着×ゲート/出口の接続マトリクス、経路ハイライト、切断箇所、能力最小区間を表示する。
- 結果から該当フロア/交通施設/Portalへジャンプできる。修正後は同じ需要・seedで再実行し、Before/Afterの待ち時間・経路不能数・容量利用率を比較する。
- シナリオ入力は5-22の共通ScenarioDefinitionを使い、Airport DayとTerminal Detailは実行粒度だけを切り替える。モードごとに需要・便時刻・アクセス条件を独自に複製定義しない。

### 3.5 集約モデルと詳細結果の対応

- 詳細シミュレーション結果から全館/メッシュprofileへ、工程別処理能力・平均/95 percentile歩行時間・待ち時間・ボトルネック区間を出力する。
- 平均値に加え、ピーク値・95 percentile・最小能力を残す。平均値だけで通路・保安・エレベーター等の局所ボトルネックが消えないようにする。
- 集約profileへの反映は差分プレビュー付きの明示操作とし、詳細シミュレーションの実行だけで自動変更しない。
- 5-22の既存Phase 8シナリオ比較へ結果を渡す。空港全体と単独ターミナルなど母集団/意味が異なる指標は直接比較せず、同じ定義・単位・対象範囲を持つ指標だけ比較可能とする。

### 3.6 互換・モデル切替

- 空港運航の既存モデルとターミナル詳細モデルのstate、clock、seed、保存領域を分ける。詳細モードを閉じても既存運航を再開できる。
- 旧セーブにモード/プロファイル/Portalがない場合の互換動作を明示する。既存運航結果を維持するため、旧PaxGroupモデルをlegacyDetailedとして残す。
- 旧セーブの近接距離によるアクセス判定は即時に破壊しない。ただし実経路の監査では「旧仕様の簡略推定/実動線未確認」と表示し、新規の詳細モードで実動線合格にしない。
- アクセス集約モデルと複合歩行グラフの両方で同じ旅客/同じ通路を計上しない。人数を確定する境界イベントを定める。
- SIM_MODEL_VERSION、project format、layout schema、terminal scenario formatを混同しない。航空運航結果に影響する変更は版・golden・旧運航中saveを確認する。

## 5. 互換性・リスク

- 現行のPaxGroupは航空運航上の搭乗・降機・手荷物・乗継に直結する。いきなり全旅客の屋内経路処理を削除せず、集約方式を別モデル/opt-inとして導入する。
- 交通手段の利用人数をaccess runtimeで計上した後、Portal/Terminal routeの移動開始でも加算すると二重計上になる。外部乗車/到着・空港境界通過・Terminal入口通過を別イベントとして定義する。
- 「経路あり」と「定員がある」「サービス運行中」は別判定である。駅へ歩けても列車本数0なら利用不能、バス停へつながっていても道路が外部未接続なら利用不能とする。
- ターミナル複合体IDが同じでも実際の通路がない棟間をつながっていると見なさない。Portal/Linkのoperational経路を必須とする。
- 詳細モードのclock/seed/stateが空港運航と共有されると、日付・便・収支・goldenが変わる。独立性テストを優先する。
- 外部の交通車両そのものは初期対象外。外部所要時間や一般道路容量を集約入力とし、空港敷地内の旅客歩行接続と交通施設の利用は詳細に検証する。
- 旧セーブの近接距離ベースアクセスを即時無効にすると旧レイアウトの運航結果が変わる。legacy fallbackと「実動線未検証」表示を設ける。
