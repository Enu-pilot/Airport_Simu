## 1. 現状と課題

### 1.1 現在すでに動いているもの

- 空港全体のSimulationは時刻を進め、航空機・便・スポット・地上作業・旅客・手荷物等を処理する。日次締め・DayFlowも既存の空港運航フローに属する。
- 現在のターミナル旅客はPaxGroup（1〜5人）単位で生成され、TerminalModel / findPaxRoute()により入口、チェックイン、保安、ゲート、到着・手荷物・出口などを移動する。
- 空港アクセスにはcar / dropoff / taxi / bus / rail / walkがある。出発旅客は分担率で手段を選び、道路遅延・満車・バス/鉄道の時間帯定員・施設からターミナルまでの徒歩時間が反映される。到着旅客はタクシー・バス・鉄道の乗り場待ちを行う。
- アクセス手段は現状、外部所要時間や道路混雑、乗り場容量を集約値として扱う。外部の自動車・バス・列車を個々の車両として全経路移動させる仕組みではない。
- analyzeAccess()では鉄道駅に明示walkway経路がある場合はfindPedestrianRoute()を使う。一方、駐車場・タクシー乗り場・バス停等は主に外部道路への接続とターミナルまでの近接距離で判定され、実際の歩行経路が必須とはなっていない。既存のACCESS_ROUTE_UNREACHABLEも駅の徒歩接続が中心で、全アクセス手段の端から端までの検査ではない。
- RoadEdge.walkway・階層コネクタの徒歩網とTerminalModelの内部旅客網は別系統である。5-16で両者をPortal経由で統合する必要がある。
- 現在はターミナルだけの独立時計・需要シナリオ・詳細運行結果を持つ独立シミュレーションモードはない。

### 1.2 解決する課題

1. 空港全体を1日進める運航と、ターミナルだけを詳細検証する運航を明確な2モードとして提供する。
2. 空港全体運航では、滑走路・誘導路・スポット・航空機・地上作業・手荷物・旅客・対外交通を一緒に処理し、ターミナル内部は全館/メッシュの集約能力と所要時間で軽量に処理する。
3. ターミナル単独モードでは、選択したターミナル/複合体の旅客動線・施設待ち・上下移動・区域境界に加え、鉄道・バス・自動車・送迎・タクシー・徒歩の空港アクセスを含めてシミュレートする。
4. 旅客が外部交通の乗降場所からターミナル入口、必要工程、搭乗口まで、または到着ゲートから出口・外部交通乗り場まで、実際に連続して移動できるかを検証する。

## 2. 目的・対象範囲

### 2.1 モードA: 空港全体運航（1日進行）

- プレイヤーが空港全体を運営する通常モード。既存のSimulation時計・航空便スケジュール・DayFlow・日次締めの仕組みを利用する。
- 空港全体の各サブシステムを同じ運航時刻で進行させる。航空機、滑走路/誘導路、スポット、地上作業、手荷物、旅客、空港アクセス、道路/鉄道アクセス容量、収支・評価を対象とする。
- ターミナル内部はterminalAggregateまたはmeshAggregateの集約プロファイルを用い、通常運航中にすべての旅客の詳細な屋内経路探索を毎tick実行しない。
- 対外交通の手段分担、施設容量、道路遅延、駐車・乗り場待ち、駅/バス停から入口までの歩行時間と接続状態を空港全体の旅客処理へ反映する。
- 1日分の運航結果（日次KPI、手段別アクセス人数、混雑、処理能力超過、旅客人数保存）を日次締めで確定する。
- 既存の運航clockを再利用する。空港全体用に第2の運航時計を作ったり、ターミナル詳細時計と同期させたりしない。

### 2.2 モードB: ターミナル単独詳細シミュレーション

- 空港全体運航とは独立して起動・停止・再実行できる分析モード。対象は選択したターミナルまたは5-15で判定したターミナル複合体。
- 専用TerminalSimulation clock、需要スケジュール、seed、アクセス手段の分担、輸送供給、設備運用状態、通路の建設/閉鎖状態を持つ。
- 対象ターミナル内部の旅客は詳細な経路グラフを進み、施設処理、待ち列、混雑、上下移動、Step-free、保安/国際区域、ゲート、手荷物、出口をシミュレートする。
- 外部アクセスは旅客の発着境界として扱い、駐車場・車寄せ・タクシー乗り場・バス停/バスターミナル・鉄道駅・徒歩入口からの到着と、到着出口から各交通手段への退出をモデル化する。
- 外部交通は初期段階では、一般道路・鉄道の外部接続、便数/頻度、定員、乗り場容量、待ち時間、道路区間容量を集約的に計算する。都市全体のバス・列車・自動車を個々の車両として走行させることは含めない。
- 結果はターミナル設計・全館/メッシュ能力プロファイルの比較材料とする。空港全体の運航時刻、航空便、会社の収支、保存中の運航状態を変更しない。

### 2.3 外部アクセス手段と旅客の移動区間

| 手段 | 空港側の交通施設/接続 | 旅客が歩く区間 | 動的に扱う要素 |
|---|---|---|---|
| 自家用車 | 外部につながる一般道路 → 駐車場 | 駐車場 → 徒歩Portal → ターミナル入口 | 駐車台数、満車、道路混雑、駐車滞在 |
| 送迎・車寄せ | 外部につながる一般道路 → 車寄せ/乗降場 | 車寄せ → 徒歩Portal → ターミナル入口 | 道路混雑、車寄せ容量、乗降処理 |
| タクシー | 外部につながる一般道路 → タクシー乗り場/乗降場 | 乗り場 → 徒歩Portal → ターミナル入口 | 道路混雑、乗車枠、到着時の待ち行列 |
| バス | 外部につながる一般道路 → バス停/バスターミナル | バス停・バスターミナル → 徒歩Portal → ターミナル入口 | 便数、乗り場数、定員、発車間隔、待ち |
| 鉄道 | 外部につながる鉄道 → 駅ホーム/改札・駅コンコース | 駅コンコース → 階層walkway/Portal → ターミナル入口 | 列車本数、定員、駅受入能力、連絡通路能力、待ち |
| 徒歩 | 外周の歩行者入口または徒歩接続を持つ周辺施設 | 外部歩行入口 → walkway/Portal → ターミナル入口 | 入口の接続状態、歩行時間、段差なし経路 |

- 自動車道路・鉄道の辺は、その交通手段の外部ネットワークとして使う。道路や線路そのものを歩行可能な経路として扱わない。徒歩には明示walkwayとPortalを使う。
- バス停/バスターミナル、駅、駐車場、車寄せ、タクシー乗り場は、交通側接続と旅客歩行側接続の両方を持つ。片方だけの接続を「ターミナルまで到達可能」と判定しない。
- 「施設が存在しない/その手段を設置していない」はnotConfiguredとし、任意の交通手段がないこと自体をエラーにしない。設置済みの施設が道路/鉄道/歩行網に接続しない場合は問題として表示する。
- 徒歩は旧セーブの簡略モデルとの互換性を保つ。新規の詳細モードで実経路を検証する場合は、外周歩行入口または明示した周辺施設/Portalを必要とし、既定の外部所要時間を実動線の合格として扱わない。

## 3. 設計方針

### 3.1 空港全体運航: 軽量集約モデル

- ターミナル処理は2粒度を選べる。
  - terminalAggregate: ターミナル複合体または館全体を1単位とする。
  - meshAggregate: 建物内部を一定メッシュ/ゾーンに分けて集約する。
- 各ノード/メッシュは、少なくとも通過人数/時、1人あたりサービス秒、平均歩行/移動秒、待機容量、稼働状態、区域、Step-free可否を持つ。
- 旅客の処理人数は、到着入口、チェックイン、保安、出入国審査、待合、搭乗、降機、手荷物、出口の各工程ごとに集計する。必要な工程・利用確率は既存の旅客仕様またはPO承認したルールを使う。
- 通路・上下移動・Portal・建物間リンクの能力は、実際の経路上の最小能力とする。館全体の平均容量により局所的な狭窄や階段/エレベーターのボトルネックを消さない。
- 外部アクセスの交通手段別人数と、ターミナル内部へ入った人数を別の境界KPIとして持ち、同じ旅客をアクセスとTerminalModelで二重に数えない。
- 旧PaxGroupモデルはlegacyDetailedとして選択可能に残す。集約モデルを新規セーブの既定にするのは、性能・人数保存・主要KPI比較をPOが確認した後とする。

### 3.2 ターミナル単独: 詳細モデル

- AirportDaySimulationとは別のTerminalSimulation state/clockを用意する。空港全体のstate.nowやDayFlowを参照・変更しない。
- 入力: 対象ターミナル/複合体、時間帯別の出発/到着/乗継人数、国内/国際比、旅客属性/Step-free比率、アクセス手段別割合または自動選択、車/バス/鉄道供給、設備状態、通路状態、seed。
- 旅客経路は5-16の複合グラフを使い、外部交通ノードからTerminalPortal、TerminalArea、各必須工程、ゲート/出口、外部交通ノードまで進む。
- 出発旅客: 外部交通到着 → 交通施設 → 徒歩Portal → landside入口 → 必須工程 → boarding gate。
- 到着旅客: arrival gate → 到着/入国等の必須工程 → baggage claim（対象旅客のみ）→ landside出口 → 徒歩Portal → 交通施設 → 外部交通退出。
- 乗継旅客は既存の乗継ルールに従い、到着側/出発側の空港外アクセスへ重複計上しない。異なるターミナルを移動する場合は5-16の運用中連絡設備だけを使う。
- すべての旅客は個人単位にせず、初期段階は既存PaxGroupまたは確率batchを使う。乱数は空港運航側から独立したseed streamとする。
- 結果: 手段別利用人数/比率、交通施設の容量・待ち、Portalごとの流入出、歩行距離/平均・95 percentile所要時間、工程別待ち、ピーク滞留、Step-free到達率、経路不能人数、搭乗締切遅れ相当、退出完了率、ボトルネック。
- Door-to-Door KPIの定義と集計規則は5-23を正本とする。出発は外部交通境界/交通施設から搭乗ゲート、到着は到着ゲートから外部交通境界、乗継は到着ゲートから乗継便ゲートまでを別旅程として扱う。
- 総所要時間・工程別時間のp50/p95は旅客人数で重み付けする。旅客グループ数だけを母数にせず、未完了・経路不能を0秒として分位点へ含めない。
- 搭乗ゲートへの期限内到着、実際の搭乗完了、乗り遅れを別KPIにする。締切は既存の搭乗/バスゲート状態遷移を正本とし、予定出発時刻から固定分数を推測しない。
- Step-free旅客は独立した分母で到達率・期限内到達率を算出する。集約モードに個別時刻が存在しない場合、p50/p95を平均値や0で代用せず未計測とする。

### 3.3 全経路の接続検証

接続判定は「構造上の経路」と「交通サービス/容量」を分ける。未設置の交通手段をエラーにはしない。

| 接続状態 | 判定 | 旅客の実移動 |
|---|---|---|
| operational（通行可能） | 必要な全区間が運用中で、区域/方向/階層/Step-free条件を満たす | 利用可能 |
| underConstruction（建設完了待ち） | 運用中の経路はないが、建設中を含めれば全区間をつなげる | 利用不可。完成後の予測表示だけ |
| unreachable（未接続） | 運用中・建設中を含めても接続できない | 利用不可。原因と断線位置を表示 |
| notConfigured（未設置） | その交通手段の施設・サービスを空港側に設定していない | 任意手段として非対象。エラーにしない |

- noService（鉄道サービス条件など）、noCapacity（本数/台数/乗り場能力が0）、closed（一時閉鎖）は経路の3状態とは別のサービス状態として表示する。経路がつながっているだけで運行可能/容量十分と判定しない。
- 交通手段ごとに、空港境界/外部ネットワーク → 交通施設 → 歩行Portal → ターミナル入口 → 必須工程 → 各対象ゲート、または各到着ゲート → 必須工程 → 出口 → Portal → 交通施設 → 外部ネットワークを検査する。
- 出発はゲート/旅客区分ごと、到着はゲート/旅客区分ごとに検査し、ひとつの入口から一部ゲートだけ到達できる状態を全館合格にしない。
- 国内/国際、出発/到着、transfer、Step-freeを別条件で検査する。Step-free旅客には階段のみの経路を合格にしない。
- 建設中経路は将来予測として表示するだけで、通常運航・詳細モードの旅客は通行させない。
- 経路上の最大ボトルネック能力（人/時）、所要時間、未算出能力の有無を返す。未算出は0とも無限大とも扱わず「未計測」と表示する。

### 3.4 UI・操作導線

- モード選択で「空港全体運航（1日進行）」と「ターミナル単独詳細シミュレーション」を明確に分ける。
- 空港全体運航は既存の運航画面/時計/日次締めを維持し、ターミナルの集約方式とアクセス状況を表示する。
- ターミナル単独モードは対象のターミナル/複合体、需要profile、時間帯、アクセス交通供給、Step-free比率、seedを選んで開始する。
- ターミナル設計Workspace（5-18）に「動線チェック」パネルを設け、交通手段×出発/到着×ゲート/出口の接続マトリクス、経路ハイライト、切断箇所、能力最小区間を表示する。
- 結果から該当フロア/交通施設/Portalへジャンプできる。修正後は同じ需要・seedで再実行し、Before/Afterの待ち時間・経路不能数・容量利用率を比較する。
- シナリオ入力は5-22の共通ScenarioDefinitionを使い、Airport DayとTerminal Detailは実行粒度だけを切り替える。モードごとに需要・便時刻・アクセス条件を独自に複製定義しない。

### 3.5 集約モデルと詳細結果の対応

- 詳細シミュレーション結果から全館/メッシュprofileへ、工程別処理能力・平均/95 percentile歩行時間・待ち時間・ボトルネック区間を出力する。
- 平均値に加え、ピーク値・95 percentile・最小能力を残す。平均値だけで通路・保安・エレベーター等の局所ボトルネックが消えないようにする。
- 集約profileへの反映は差分プレビュー付きの明示操作とし、詳細シミュレーションの実行だけで自動変更しない。
- 5-22の既存Phase 8シナリオ比較へ結果を渡す。空港全体と単独ターミナルなど母集団/意味が異なる指標は直接比較せず、同じ定義・単位・対象範囲を持つ指標だけ比較可能とする。

### 3.6 互換・モデル切替

- 空港運航の既存モデルとターミナル詳細モデルのstate、clock、seed、保存領域を分ける。詳細モードを閉じても既存運航を再開できる。
- 旧セーブにモード/プロファイル/Portalがない場合の互換動作を明示する。既存運航結果を維持するため、旧PaxGroupモデルをlegacyDetailedとして残す。
- 旧セーブの近接距離によるアクセス判定は即時に破壊しない。ただし実経路の監査では「旧仕様の簡略推定/実動線未確認」と表示し、新規の詳細モードで実動線合格にしない。
- アクセス集約モデルと複合歩行グラフの両方で同じ旅客/同じ通路を計上しない。人数を確定する境界イベントを定める。
- SIM_MODEL_VERSION、project format、layout schema、terminal scenario formatを混同しない。航空運航結果に影響する変更は版・golden・旧運航中saveを確認する。

## 5. 互換性・リスク

- 現行のPaxGroupは航空運航上の搭乗・降機・手荷物・乗継に直結する。いきなり全旅客の屋内経路処理を削除せず、集約方式を別モデル/opt-inとして導入する。
- 交通手段の利用人数をaccess runtimeで計上した後、Portal/Terminal routeの移動開始でも加算すると二重計上になる。外部乗車/到着・空港境界通過・Terminal入口通過を別イベントとして定義する。
- 「経路あり」と「定員がある」「サービス運行中」は別判定である。駅へ歩けても列車本数0なら利用不能、バス停へつながっていても道路が外部未接続なら利用不能とする。
- ターミナル複合体IDが同じでも実際の通路がない棟間をつながっていると見なさない。Portal/Linkのoperational経路を必須とする。
- 詳細モードのclock/seed/stateが空港運航と共有されると、日付・便・収支・goldenが変わる。独立性テストを優先する。
- 外部の交通車両そのものは初期対象外。外部所要時間や一般道路容量を集約入力とし、空港敷地内の旅客歩行接続と交通施設の利用は詳細に検証する。
- 旧セーブの近接距離ベースアクセスを即時無効にすると旧レイアウトの運航結果が変わる。legacy fallbackと「実動線未検証」表示を設ける。

## 運営モード別の施設シミュレーション粒度（PO提案・2026-11-19）

### 1. 基本方針

店舗・飲食店・ラウンジ・待合室などは、配置データ上では個々の施設として保持する。一方、シミュレーションでは目的に応じて粒度を切り替える。

| 項目 | ターミナル詳細設計・詳細運営モード | 空港運営モード |
|---|---|---|
| 主目的 | 店舗配置・動線・サービス・混雑・売上を個別に検証 | 空港全体の1日運航、旅客処理、経営収支を安定した計算量で評価 |
| 施設の識別 | 店舗/飲食店/ラウンジ等を個別IDで扱う | 店舗単位の旅客立寄り先は扱わず、施設カテゴリ×ターミナル/区域（必要ならメッシュ）に集約 |
| 旅客の立寄り | 個別の店舗/飲食店/ラウンジ等を候補に選び、対象施設IDまでの経路・立寄り・滞在を扱う | 「物販」「飲食」「ラウンジ」「待合」等のカテゴリ利用率・総利用人数・平均滞在・需要/能力を集約計算 |
| 待ち・混雑 | 店舗/設備ごとの定員・処理能力・待ち行列・混雑を評価 | カテゴリ/区域単位の利用需要・能力・混雑指標を評価。各店舗ごとの待ち行列は作らない |
| 経営指標 | 店舗別売上・利用率・滞在・人気・サービス品質など | カテゴリ/ターミナル別の売上・利用人数・能力使用率等を集約 |
| 空間粒度 | 個々の施設入口/位置までの動線 | ターミナル/区域またはメッシュ単位。店舗ごとの経路探索を旅客ごとに反復しない |

- 「詳細設計」は店舗個々の位置・属性を編集するモードであり、編集操作そのものが旅客シミュレーションを常時実行する意味ではない。個別店舗への立寄りを検証するのは、ターミナル詳細運営/詳細Simulationを実行したときとする。
- 詳細モードでは、旅客の立寄り先は実在する個別施設IDで識別する。旅客を必ず1人1オブジェクトとして生成するかは性能テストで決めてよい。旅客グループ/属性が同質なら重み付きbatchで表現してもよいが、立寄り先の店舗ID・店舗別利用人数・店舗別待ち/売上は失わない。
- 空港運営モードは、店舗・飲食店・待合室等の存在数・カテゴリ・区域・合計能力・営業状態・品質/価格帯等を集約profileへ変換し、カテゴリ単位の利用率/滞在/需要/売上を計算する。店舗ごとの入口ノード、店舗別ルート探索、店舗別キューを空港運営のtickごとに生成しない。
- 空港運営モードでも店舗の存在を無視するわけではない。個々の施設定義からカテゴリ×ターミナル/区域単位の集約値を導出し、施設数・合計能力・営業時間・区域分布の変化は集約結果に反映する。
- 待合室は一般の買い物先と同じ選択型店舗ではなく、搭乗前/到着後の滞留容量・快適性・区域を持つ待合カテゴリとして集約する。詳細モードでは待合室/待合エリア個々の容量と位置を使う。
- 集約の単位は空港全体一括にしない。局所的な混雑・アクセス距離を消さないため、少なくとも「カテゴリ×ターミナル」、必要に応じて「カテゴリ×ターミナル×区域/メッシュ」とする。メッシュ採用は性能とデータ根拠を確認して決める。

### 2. 共通データと集約境界

- 個別施設の配置・ID・カテゴリ・位置・階・営業状態・能力・価格/品質等を唯一の元データとする。詳細用と運営用に別々の店舗台帳を持たない。
- 空港運営モード用の集約profileは個別施設レコードから派生生成する。手入力で個別施設と集約値の二重管理をしない。集約値はレイアウト変更・営業状態変更・セーブ読込時に再計算または安全にキャッシュ無効化する。
- 集約変換では、合計能力/席数/店舗数/供給時間は加算、価格・品質・滞在時間等は定義した重み（利用可能席数・能力・施設数等）で算出する。重み付けの根拠が決まらない値は未算出として扱い、単純平均で意味を変えない。
- 詳細Simulationの店舗別実績をカテゴリ/ターミナル/区域へ集約する共通adapterを用意する。詳細Simulationの実行結果だけでAirportDayの進行中stateや財務へ自動反映しない。運営モードへ取り込む場合は差分プレビュー付きの明示操作とする。
- いずれのモードでも施設の営業中/閉鎖/建設中、利用資格、対象区域、営業時間、定員/処理能力を判定する。存在するだけ、または設置数が多いだけで利用可能・満足度改善としない。
- 既存PaxGroup・TerminalModel・5-16の経路探索、5-21の工程能力/時系列を再利用し、店舗専用の重複した経路探索/能力基盤を新設しない。

### 3. 詳細モードの店舗立寄りモデル

- 店舗/飲食店/ラウンジ等を個別施設ノードとして扱い、旅客属性・目的・利用資格・価格/品質・営業時間・混雑・搭乗締切までの余裕等に基づいて候補を選ぶ。
- 立寄り先は具体的なfacilityIdで記録し、入口までの移動、必要なら待ち、サービス/滞在、退出を表現する。
- 同じカテゴリでも別店舗は別の候補/立寄り先として扱う。店舗別利用人数・待ち時間・売上・稼働率が集計できること。
- 商業・ラウンジ等は任意の寄り道とし、必須工程を迂回させない。利用資格外、閉店中、容量不足、経路未接続の店舗は候補から除外または利用不可として記録する。
- 容量が大きい店舗や複数階/離れた店舗を追加した場合も、動線・待ち・利用候補の整合が保たれる。

### 4. 性能テストと粒度の判断基準

実装時に、店舗単位モデルをどこまで詳細に実行できるかを実測して決める。事前に根拠のない最大店舗数/旅客数を固定せず、テスト環境・対象機器・シナリオを記録し、実装着手時に受入目標を定める。

| テスト群 | 負荷の段階 | 測定・確認する内容 |
|---|---|---|
| AirportDay集約 | 小/中/大の店舗・飲食・ラウンジ・待合施設数 × 小/中/大の旅客需要 | 1日運航の実時間、tick p50/p95、CPU/メモリ、集約profile再生成時間。施設数増加が旅客数×個別店舗数の組合せで膨張しないこと |
| TerminalDetail個別立寄り | 店舗数・カテゴリ数・フロア数・旅客需要・立寄り候補数を段階増加 | 総実行時間、tick/イベント p50/p95、経路探索回数・キャッシュヒット率、ピークメモリ、店舗別待ち/利用集計の正確性 |
| 空間負荷 | 同じ店舗数を単一区域へ集中/複数区域・複数フロアに分散 | 混雑局所性、区域間の移動時間、route検索コスト、メッシュ集約の有効性 |

測定項目は少なくとも、対象環境/CPU・メモリ、施設数（カテゴリ別・区域別）、旅客数/グループ数、立寄り候補数、実行期間、実時間、tick/eventのp50/p95、ピークメモリ、経路探索回数を記録する。描画性能を含める場合はsimulation計算時間と分離する。

#### 性能による採否・調整ルール

1. AirportDayは常にカテゴリ×ターミナル/区域の集約方式を採用する。テスト環境で高速だったことを理由に、店舗ごとの立寄り/キュー/経路探索へ切り替えない。
2. TerminalDetailは個別店舗IDへの立寄りを維持する。重い場合は、まず経路キャッシュ、候補の空間/区域絞り込み、同一条件旅客の重み付きbatch、イベント駆動、集約profileのキャッシュ等で最適化する。
3. 最適化後も目標を満たさない場合は、実測結果に基づいて「推奨/対応店舗数」「対応旅客数/同時グループ数」「シミュレーション時間」「推奨端末」を定義する。テスト失敗後に受入目標を後付けで緩めない。
4. 性能上、旅客個人単位の生成が難しい場合は旅客をbatch化してよい。ただし、店舗をカテゴリへ統合して個別立寄りを失う変更は別の粒度変更として扱い、PO承認とBefore/Afterの店舗別KPI比較を必要とする。
5. TerminalDetailでも個別店舗粒度を保てないことが判明した場合、個別店舗モードを削除せず、実行対象範囲/需要規模/シミュレーション時間を制限する案を先に検討し、制限内容をUIに表示する。
6. 速度だけでなく、店舗別利用人数合計=旅客の立寄り実績合計、施設別売上合計=カテゴリ別売上合計、旅客人数保存、営業時間/利用資格/経路の制約を満たすことを同時に受入条件とする。

### T11: 集約 profile adapter（`src/core/terminal/serviceProfile.ts`）

- `buildServiceProfiles(layout)`（純関数）: 個別 TerminalArea を唯一の元データとして、施設別 profile と カテゴリ×ターミナル（×区域内訳）profile を導出する。台帳の二重化なし。
- カテゴリ: retail（shop）/ dining（restaurant）/ lounge / waiting。施設別: 能力 = `areaServerCount(props)`（運営側キューと同一根拠）、収容 = タイル数 × `PAX_PER_TILE`、滞在・単価は `BALANCE.retail` の既存定数（shop 480s・15 / restaurant 1200s・22）。
- **根拠のない値は未算出（null）**: 待合の滞在・単価、価格・品質（priceQuality）は既存モデルに算出根拠がないため常に null。ラウンジはエリア種別自体がないため `notConfigured`。
- 状態: available / notOperational（建設中・閉鎖）/ notConfigured を区別する。
- キャッシュ: `serviceProfilesFor(layout)` が layout オブジェクト同一性で WeakMap キャッシュする。レイアウトは不変更新されるため、編集・営業状態変更は新オブジェクトになり自動で無効化される。毎 tick の再走査はしない（Simulation 生成時に `SimContext.service` へ1回だけ構築）。
- 集約 adapter: `aggregateServiceRecords(profiles, records)` が 店舗別実績 → カテゴリ×ターミナル → 空港全体 を集約する。平均待ち・平均滞在は利用者 0 のとき null（未算出）。運営・詳細の両モードが同じ指標定義（users/groups/waitPaxSec/dwellPaxSec/revenue/busyServerSec/turnedAway）を使う。

### T12a: 運営モードの集約接続（`src/core/sim/serviceAggregate.ts`）

- `createSimulation` の `CreateOptions.serviceGranularity?: 'detailed' | 'aggregate'` で切替。**既定は 'detailed'（現行挙動）**であり、既定の切替（集約を標準にするか）は PO 判断事項として残す。ゴールデン/フィンガープリントは既定経路で不変。
- 集約方式の `planShop` 差し替え: 店舗エリアへの移動・店舗別キュー・個別経路探索を行わず、カテゴリ（retail/dining）×ターミナルの空き能力と見込み待ち（滞在×稼働率の近似、10分超は不成立＝現行 planShop の規則に対応）で判定し、滞在はグループの状態として処理する。売上は現行と同じ `onShopDone`（retail/dining 台帳）へ計上する。
- 集約方式の利用実績は `serviceAggregateUsage(sim)` でカテゴリ×ターミナル単位に取得できる（ランタイム保持のみ・保存対象外）。
- 待合は集約方式でも購買対象に含めない（従来どおり待合エリアで滞留）。

### T12b: 詳細モード（`src/core/terminal/serviceDetailSim.ts`）

- `runServiceDetailSim(layout, opts)`: 独立した clock / state / seed（`${seed}:${terminalId}`）を持つ単独実行。AirportDay の state・乱数・収支・保存データには一切触れない（layout は読み取り専用。テストで不変を固定）。
- 処理: 入口 → チェックイン → 保安 → 店舗立寄り（候補化 → 営業中・到達可能・区域資格・見込み待ち ≤10分・満員でない店舗から 経路コスト+見込み待ち 最小を選択）→ 待合滞留（締切 − ゲート歩行時間まで）→ 搭乗口。移動は `findPaxRoute`（区域制約・Step-free を強制）に経路キャッシュ（始点|目的地|条件）を併用する。
- 店舗別実績（利用人数・グループ数・待ち・滞在・売上・窓口稼働・締切超過で離脱した人数）をエリア ID 単位で記録し、`aggregateServiceRecords` で運営 profile と同じ定義へ集約できる。
- 計測用クロックは呼び出し側注入（`opts.nowMs`）。core は実時間へ依存しない。
- **未完了の依存**: 5-16 T6（複合グラフの容量予約・Step-free 統合）は未実装のままであり、本実装はそれを完了扱いにしない。詳細モードの移動は TerminalModel 上の実経路 + エリア単位キューであり、複合グラフ全体の経路進行ではない。

### 1B: 集約方式（serviceGranularity 'aggregate'）の既定化

- 変更: `createSimulation` の既定を `'detailed'` → `'aggregate'`（`src/core/sim/simulation.ts`）。`'detailed'` は `CreateOptions.serviceGranularity` の明示指定で従来どおり選べる。手組み Simulation で粒度が欠落した場合は従来どおり詳細経路（passengers.ts は 'aggregate' のときだけ集約経路に入る）。
- 目的（PO 判断）: もっと大きな規模で動かすため。集約方式は店舗単位の経路探索・キューを作らず、規模拡大時の計算量を抑える（T13 実測: 同一条件で約31%短縮、店舗数・旅客数が増えるほど差が開く構造）。
- 影響計測: legacyFingerprint 全 6 ハッシュが変更前（ベース `3fa56d1ea00d` で採取）と完全一致し 7/7 通過。代表シナリオ（サンプル空港・city core・線形/交差/ストレス）は店舗エリアを持たないため、既定変更の影響範囲外であることを確認した。店舗のあるレイアウトでは、既定運航の店舗利用が集約近似に変わる（新規テストで「省略時 = 明示 aggregate と完全一致」「明示 detailed では集約実績が立たず従来経路」を固定）。

### 2A: ラウンジのエリア種別新設（店舗の派生にしない）

- 登録: TerminalArea 種別 `'lounge'` を追加（`model/types.ts`）。カタログ仕様（`model/catalog.ts`）: 既定 4×2、zone 'departure'（変更可）、props は `seats`（int 0–5000、既定 40）。配置は TERMINAL_AREA_SPECS 経由でツールボックスに自動で載る。ラベル `AREA_KIND_LABEL.lounge = 'ラウンジ'`（i18n/ja.ts）、描画色 `AREA_COLOR.lounge`（render/MapRenderer.ts、色の最終判断は UI 側）、建設費 `BALANCE.costs.areaUnit.lounge = 100,000`（飲食店 120,000 と同規模の内装費として置いた暫定値）。
- 利用資格（`isLoungeEligible`、terminal/serviceProfile.ts）: 区域が保安検査後の出発区域（departure / departureIntl）、所属ターミナルが運用中、席数 > 0。実際の到達可能性は利用側の経路探索（詳細モードの findPaxRoute、区域制約・Step-free を強制）が決める。**航空会社のクラス/ステータスによる資格は未対応**: 既存モデルに該当する旅客属性が存在しないため新設しなかった（全旅客が同じ資格モデル）。
- 滞在モデル: 購買ではないため売上を持たない（spendPerPax / dwellSec は根拠なしとして null）。収容は席数ベース（profile の capacity は areaServerCount ではなく props.seats）。詳細モードでは待合の代わりの滞留先になり、満員（滞留人数 + グループ人数 > 席数）なら入れず待合へフォールバックし、turnedAway / loungeSkipped に記録する。立寄り意図は「締切までの残り ≥ 60 分（minSlackMin）かつ確率 25%（visitProb）」。
- 満足度への接続: AirportDay の満足度式（computeKpi）には快適性・アメニティの入力項が存在せず、接続できる既存経路がない。したがって満足度式は変更せず、新規係数を `BALANCE.lounge` に明示したうえで、詳細モードの結果にだけ現れる体験指標（利用者・時間 × satisfactionPerUserHour = 2、上限 satisfactionCapPoints = 5、完了旅客あたり）として出す。**この係数は実測根拠のないゲームバランス定数**であり、AirportDay への接続はバランス変更として別途 PO 判断が要る（未接続であることを明記する）。
- 集約 profile: 独立カテゴリ 'lounge' のまま（retail/dining/waiting に混ぜない）。能力契約 adapter `readingsFromServiceProfiles`（core/capability.ts）が domain 'passenger-service' でターミナル×カテゴリの読み取りを出し、ラウンジは単位 'seats'。
- 保存形式: **PROJECT_FORMAT_VERSION_8 を新設**（形式 7 = 動く歩道の前例と同じ扱い）。`layoutUsesFormat8` = ラウンジエリアを含むレイアウト。含まないプロジェクトは従来どおりの版で書かれ、旧セーブの読込互換は維持される（PROJECT_FORMAT_MAX_READABLE = 8）。SIM_MODEL_VERSION は 1B の 10.8 で既に上がっており、ラウンジ自体は既存運航の計算を変えないため追加の版上げはしない。
- 運営モード（AirportDay）の planShop は従来どおり shop/restaurant のみを対象とし、ラウンジは運営側の滞留先にはまだ接続していない（詳細モードと profile・能力契約までが本実装の範囲。運営側への接続は UI 更新と合わせて別途判断）。

### 5A: 乗継需要モデルの OD 集計（計算は変えない）

- `summarizeTransferOd(plan, hub)`（economy/hub.ts）: planConnections が確定した計画を OD（到着路線 × 出発路線）ごとに集計する純粋関数。需要の計算式・配分・乱数は一切変更していない。魅力（onwardAppeal）と品質（connectionQuality）は計画時と同じ決定的関数を計画データから再計算して内訳として添える（乱数不使用）。合計は Σ connections.pax = Σ transferIn と一致することをテストで固定。
- 保持と日報: `generateContractSchedule` が計画確定時に `sim.transferOdPlan`（実行時データ・保存対象外）へ会社日単位で保持し、`settleDay` がその日の日報 `DailyReport.hubOd?: TransferOdEntry[]` へ写す。ハブ無効・日ずれ・配分なしの日はフィールド自体が付かない。
- 既存集計との関係: `report.hub` / hubStats は当日の**実績**（spawned/connected/missed/noShow）、hubOd は**計画**（配分）であり別フェーズの値で二重計上ではない。計画と実績は通常一致しないため合計の一致は要求しない。
- フィンガープリントへの影響: フィクスチャの会社はハブ機能を持たないため hubOd は付かず、全ハッシュ一致（再採取なし）。
