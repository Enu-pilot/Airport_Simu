## 2. 目的・対象範囲

### 目的

空港全体運航とターミナル単独詳細シミュレーションを、同じシナリオ入力から実行できるようにする。ベースラインと代替案の差分を明示し、ターミナル配置・設備能力・旅客アクセス条件などの変更が結果へ与える影響を比較可能にする。

### 対象

- 共通シナリオ定義と再実行可能な入力スナップショット。
- シナリオの複製、ベースライン/代替案、変更点の記録。
- 空港全体運航/ターミナル詳細の両実行モードへの同一入力の受け渡し。
- Phase 8の既存シナリオ比較機能への結果登録・比較。
- 5-21の工程メトリクス、5-23の旅客Door-to-Door KPIとの連携。

### 非目標

- 既存のPhase 8シナリオ比較を置き換える別画面・別集計基盤。
- 詳細シミュレーションの結果を、確認なしに本番レイアウトや空港全体運航へ反映すること。
- 空港全体集約値と単一ターミナルの詳細値を、意味の違いを無視して同じ数値として比較すること。
- シミュレーションの途中状態そのものを、シナリオ入力として複製すること。

## 3. 設計方針

### 3.1 共通ScenarioDefinition

シミュレーションの実行粒度とは独立した、読み取り専用のScenarioDefinitionを定義する。少なくとも次を再現可能な入力として固定する。

- 基準プロジェクト/レイアウトの識別子、入力スナップショットまたは内容ハッシュ。
- 会社・空港設定、契約、便数/時刻表、機材構成、国内/国際比、乗継率。
- 時間帯別の旅客需要、アクセス手段別割合または自動選択条件、外部交通サービスの供給条件。
- 対象日・開始時刻・終了時刻、営業時間、夜間制限、施設/通路/滑走路の初期状態。
- 天候、難易度、障害・イベントなど、運航/旅客結果へ影響する条件。
- 基準seed、モデルバージョン、シナリオ定義のバージョン。

全項目を無条件に保存するのではなく、既存プロジェクト形式の再利用と入力差分だけを持つ方式を監査して決める。ただし、参照先のプロジェクトが後から変更されても同じ結果を再現できるよう、参照先の版/ハッシュまたは必要な値のスナップショットを残す。

### 3.2 実行モードとシナリオ入力を分離

- Airport Day: 共通シナリオから空港全体運航用の入力を構築し、既存の空港clock・日次締め・運航stateの規則を使う。
- Terminal Detail: 同じシナリオから対象ターミナルに必要な需要・便・アクセス条件を抽出し、独立state/clock/seed streamで実行する。空港本番stateへの書き戻しは禁止。
- 実行モードは「何をどの粒度で動かすか」であり、旅客需要・便時刻・アクセス供給などのScenarioDefinitionとは別フィールドにする。
- 乱数はシナリオseedから機能別の独立streamを派生させ、旅客側の追加処理が航空機運航側の乱数列をずらさないようにする。
- ターミナル詳細で必要な旅客コホートは、元の時間帯別需要・便・アクセス比率から決定的に抽出する。全空港の旅客総数を単一ターミナルへ重複投入しない。

### 3.3 シナリオ複製・差分・比較

- ベースラインを固定し、レイアウト/設備/アクセス/需要/運用条件を変更した代替シナリオを複製できる。
- 各代替案は、ベースラインから変更した項目、変更前後、変更理由、対象ターミナル/施設を記録する。
- 同じScenarioDefinition・seed・モデルバージョンから再実行できる。比較目的の再実行でseedを暗黙に変えない。
- 比較結果に、シナリオID、実行モード、対象ターミナル、期間、入力版/ハッシュ、seed、モデルバージョンを添付する。
- Phase 8の比較UI/データ構造を再利用し、必要なメタデータ・指標だけを拡張する。

### 3.4 比較可能性の規則

- 空港全体と単独ターミナルで母集団/範囲が異なる値は、そのまま比較しない。ターミナル別に切り出した同一範囲、旅客1人あたり、便1便あたりなど、意味が一致する指標だけを比較する。
- 集約モデルで分布が得られないp50/p95は、平均やゼロで代用せず「未計測」とする。詳細モデルにだけ存在する指標は「詳細モードのみ」と表示する。
- 指標ごとに単位、対象旅客/便、集計期間、母集団、実測/推定/未計測を保持する。
- 5-21のローリング60分能力/需要/処理量/待ちは共通工程メトリクスを使い、5-23の旅客移動時間・搭乗締切指標も同じ実行結果に紐づける。
- 比較不能な指標を隠して総合点へ混ぜない。欠損がある場合は理由を示す。

## 5. 互換性・リスク

- シナリオ入力の保存形式と、空港プロジェクト形式・レイアウトschema・SIM_MODEL_VERSION・ターミナル詳細シナリオ形式を混同しない。
- シナリオ保存を追加する場合、既存プロジェクトを開いたときの既定値、旧シナリオの読み込み、往復保存、復元後の再実行を確認する。
- 詳細モードの独立clock/state/seed streamを維持し、空港全体の進行時刻・日報・会社評価・収支を書き換えない。
- 同じシナリオでも実行モードが異なると集約/詳細の差が出る。全指標が一致することを受入条件にしない。比較できる同一定義の指標に限って差を評価する。
- 既存シナリオ比較の期待値・ゴールデンは、合格目的で変更しない。データ追加に伴う変更が必要な場合は、入力差分とKPI影響を示して承認を得る。
