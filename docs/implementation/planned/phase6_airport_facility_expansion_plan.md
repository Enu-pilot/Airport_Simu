## 1. 目的と位置づけ

### 1.1 目的

空港の建設物・固定設備・車両・インフラを、単に配置できるオブジェクトではなく、空港の運航能力・旅客処理能力・貨物処理能力・安全性・快適性・収益に影響する運営資産として扱う。

Phase 6 では次を実現する。

1. 施設の能力を算出する共通の考え方を定め、建設画面と経営画面で同じ根拠・同じ値を表示する。
2. 貨物・旅客ターミナル・夜間拠点・空港インフラを、既存の運航・旅客・経営・空港格の仕組みと接続する。
3. 設備の建設、接続、稼働、人員・車両の配置、保守の違いを能力に反映する。
4. 空港の格に応じて段階的な施設・運営機能を解放し、規模拡大と運営の複雑化をゲームの成長要素にする。
5. プレイヤーが能力不足の場所・時間帯・原因を特定し、建設・増設・人員配置・運航調整によって改善できるようにする。

### 1.2 Phase 5 との境界

Phase 6 は Phase 5 の置き換えではない。Phase 5 が整備している建物階層・複合体・歩行網・空港格・旅客能力等を基盤として、施設機能を横断して完成・統合する後続フェーズである。

- Phase 5 の既存要求・受入条件・個別計画の状態は変更しない。
- 既存の計画書がある機能は、本書にタスク内容を複製せず、既存計画を詳細の正本とする。
- Phase 5 の機能が未完了であれば、依存する Phase 6 タスクはその受入完了を待つ。ただし、PO 指示で既に進行中の貨物 A6 は現在の進行を止めない。
- Phase 6 の計画登録は、全サブ機能の同時着手や、Phase 5 の完了扱いを意味しない。
- 既存の ATC（管制官）モードは独立ゲームモードであり、Phase 6 の空港経営・施設能力・旅客/貨物シミュレーションへ統合しない。

施設候補・羽田での確認度・一般設備との区別は、[羽田空港の施設・設備調査](../../design/haneda_airport_facilities_survey.md)を参考台帳とする。同調査は現行実装仕様や完全な設備台帳ではなく、施設候補の調査資料として扱う。

### 1.3 基本方針

- 能力は根拠のある値だけを表示する。根拠・単位・計算対象が不明なものは「未算出」とし、推定値で埋めない。
- 施設を建設しただけで能力が有効になるとは限らない。接続・稼働状態・必要な人員/車両・電力/燃料等の条件を別々に評価する。
- 旅客、手荷物、貨物、航空機、車両、電力、水、廃棄物など、異なる処理対象・単位を合算しない。
- ゲーム値と現実の施設能力・法定基準・実際の運用基準を混同しない。
- 新機能は原則 opt-in とし、旧保存・既存の運航結果・乱数列・ゴールデンへの影響を明示する。

## 4. 共通能力モデルとUI（P0）

### 4.1 能力指標の共通定義

各設備・施設について、算出可能な範囲で以下を区別する。

| 指標 | 意味 |
|---|---|
| 理論能力 | 設置数・設定値・既定処理時間から求める設備固有の能力 |
| 有効能力 | 接続・稼働・閉鎖・故障・人員・車両・供給制約等を反映した、現在利用可能な能力 |
| 需要 | 対象時間帯に処理する必要がある量。計画値と実績側の需要を区別 |
| 実績処理量 | 実際に処理を完了した量。同じ時間窓・同じ単位で集計 |
| 使用率 | 需要÷有効能力。有効能力が0または未算出の場合は数値を出さず理由を表示 |
| 待ち・滞留 | 待ち人数、待ち時間、待ち台数、積み残し等。対象領域で測定できる値だけを表示 |
| 能力余力 | 有効能力−需要。需要と能力の単位・時間窓が一致するときだけ算出 |

能力には領域別の単位を必ず付与する。例: 人/時、個/時、個/分、機/夜、発着回/時、m³/時、保管m³、台/時、kW、m³/日。単位が異なる値を総合能力として加算しない。

### 4.2 理論能力と有効能力の考え方

- 理論能力は、設備自体の処理速度・台数・窓口数・ベイ数等から求める。
- 有効能力は、実際に機能する経路・設備・要員・車両・供給源・営業時間の制約を反映する。
- 直列工程の処理能力は、同一フロー・同一時間窓・同一単位で接続された各工程の最小能力を基本とする。
- 独立した並列設備は、同じ需要を分散でき、共通ボトルネックがないことを確認した場合のみ合算する。
- 共有する道路・バス・駅・電力・燃料・通路等を複数ターミナルや複数機能に重複計上しない。
- 建設中、接続待ち、閉鎖中、故障中、必要人員不足、供給不足の設備は、条件に応じて有効能力から除外または制限する。状態理由を表示する。
- 車両・作業員は同時に複数作業へ割り当てない。既存の資源予約・稼働状況を使い、施設台数と作業能力を二重に数えない。
- 能力の理論式だけ存在し実績時系列がない場合、実績・使用率は未算出とする。利用数や待ち時間を記録できる前に実績値を推定しない。

共通API/データ契約は計画段階であり、着手時に現在の AirportCapacitySnapshot、施設モデル、FacilityRuntime、各ドメインの計算処理を監査して最小差分で決める。全施設に同一の数式を強制せず、能力の意味・単位・制約を共通契約で表し、具体的な算出式は領域別 adapter に置く。

### 4.3 未算出・状態の区別

最低限、次の状態を表示・診断で区別する。

| 状態 | 意味 |
|---|---|
| 未設置 / 未設定 | 施設・機能が構成されていない |
| 未算出 | 能力式または必要データがなく、値を求められない |
| 0能力 | 算出可能だが、稼働できる有効能力が0 |
| 未接続 | 必要なネットワーク・区域・供給設備へ接続していない |
| 建設中 | 建設完了前で稼働していない |
| 閉鎖中 | 工事・運用判断等で一時的に使用不可 |
| 故障 / 停止 | 設備故障・停止操作により使用不可 |
| 人員 / 車両不足 | 必要な作業資源が不足 |
| 供給不足 | 電力・燃料・水・資材等の供給が不足 |
| 稼働中 | 必要条件を満たし、能力を提供している |

「未設置」「未算出」「0能力」を同じ0として表示しない。未算出を能力不足のランキングや格の昇格条件へ混ぜない。

### 4.4 建設画面の能力UI

施設・設備・車両基地等を選択したとき、既存のプロパティパネルに能力セクションを表示する。ターミナル内部設備は5-18のWorkspace、階層設備はdocs/34の接続情報を使う。

表示項目:
- 施設名、カテゴリ、設置数、対象ターミナル/階/区域。
- 理論能力・有効能力・単位・計算根拠。
- 接続先と接続状態、供給源、対応スポット/経路。
- 稼働・建設中・閉鎖・故障・人員/車両不足等の状態。
- 現在需要または対象ピークの需要（根拠がある場合）。
- 追加配置・増設・設定変更後に増える理論能力/有効能力の差分（試算できる場合）。
- 費用・維持費は既存の経済モデルに接続できる場合のみ表示。

プレビューは実際の能力計算を再利用し、画面だけの別式にしない。接続・人員・共有資源が未確定なら「仮の理論能力」「有効能力未確定」と明示する。提案設備の配置が他の資産や通路を壊す場合も、確定前に既存の配置検証を通す。

### 4.5 経営画面の能力UI

既存「空港能力」パネルを拡張し、分野別の能力一覧と共通のボトルネック表示を提供する。

| 分野 | 主な指標 |
|---|---|
| 航空機運航 | 滑走路発着回/時、スポット同時駐機機数、誘導路区間の理論能力/実績（算出できるもの） |
| 折り返し | 機種別作業可能数、必要車両・作業員・整備士、作業待ち・完了時間 |
| 旅客出発/到着 | アクセス、チェックイン、保安、CIQ、搭乗、到着審査、手荷物受取、出口 |
| ターミナル内部 | 通路、上下移動設備、トイレ、待合、ゲート、内部サービスの能力・混雑 |
| 手荷物 | 受託、搬送、検査、仕分け、メイクアップ、搭載、到着返却 |
| 貨物 | 貨物需要、契約供給、上屋/荷役、航空機搭載、道路搬出入、積み残し |
| 夜間拠点 | 滞泊可能機数、整備枠、整備士、Work Order、翌朝の出発可能機数 |
| インフラ | 電力、燃料、水、排水、廃棄物等の供給/処理能力と需要 |
| 安全・環境 | 消防・救難の対応資源、環境処理量、障害・保守状況 |

表示の原則:
- 空港全体とターミナル別・施設別の階層を持たせる。
- 旅客については5-21のローリング60分と工程自身のピーク時刻を引き継ぐ。貨物・夜間・インフラ等は各領域に適切な日次/時間帯/瞬時窓を用い、旅客の60分と混在させない。
- 計画需要、理論能力、有効能力、実績処理量を別列で表示する。
- 使用率80%以上は注意、100%超は能力不足という既存5-21のゲーム内判定を、旅客工程の範囲では維持する。他領域に適用する場合は、単位・時間窓・バランスを個別検証する。
- ボトルネックから該当設備・建設画面の選択対象へ移動できるようにする。選択先が複数の場合は候補を表示し、曖昧な対象を自動選択しない。
- 計画前・運航中・運航後で参照できる値を切り替え、データがない場合は「未計測」「未算出」を表示する。

### 4.6 施設データの責務分離

施設マスタ・配置・能力計算では、少なくとも次の4層を区別する。既存モデルに同等の責務がある場合は再利用し、Phase 6のためだけに同じデータを重複保存しない。

| 層 | 例 | 主な管理属性 |
|---|---|---|
| 建築物・区画 | ターミナル、格納庫、貨物上屋、GSE基地、倉庫 | 用途、面積、階、収容寸法、親子関係、建設/稼働状態 |

## 5. P1：貨物機能の完成

### 5.1 既存実装と残件

貨物は Phase 5 / 5-12（A6）の既存計画が active である。2026-11-18 時点で、貨物需要モデル、契約/計画層、機種の貨物室容積参照、貨物上屋と荷役能力の基盤、貨物収支計算層、保存検証、格解放の基盤が一部実装されている。一方、貨物便のSimulation実機化、貨物専用機、実運航での荷役、日報表示・永続化、道路区間との競合、格5〜7の規模拡張・関連テストには残件がある。

**詳細タスクと進捗は [貨物輸送計画](../active/cargo_operations_plan.md) が唯一の正本。** Phase 6 は貨物計画を複製せず、以下の優先順・能力UI接続を管理する。

### 5.2 完成に必要な機能

1. 貨物契約・DayPlan の貨物便を実際のSimulation上の便・機体として扱う。貨物便は旅客を生成しない。
2. 貨物専用機カタログを用意し、旅客便候補と分離する。貨物室容積が未設定の機種は推定せず、能力未算出/対象外とする。
3. 既存の cargoUnload / cargoLoad タスク基盤を実便に接続する。手荷物の unload/load を貨物に流用しない。貨物便に不要な旅客向け折り返しタスクを生成しない。
4. 貨物上屋の m³/時能力、保管容量、スポットへの搬送、荷役要員/機材を実運航へ反映する。能力超過は待機/積み残しとして記録し、需要 = 搬送 + 積み残し等の保存式を維持する。
5. 貨物地区・上屋のトラック搬入出需要を道路区間能力へ反映する。旅客アクセスと道路を共有する場合は共通道路容量を一度だけ消費する。個別トラック走行が未実装なら集約モデルと明記する。
6. 貨物収入・荷役費・施設維持費・契約未達・積み残しを日報・経営分析へつなぐ。旅客収支と分離する。
7. 貨物能力の建設画面表示と、経営画面の貨物専用サマリーを追加する。貨物需要・契約供給・理論/有効荷役能力・実績取扱量・積み残し・収支を同じ日付/単位で表示する。
8. 格3国内貨物、格4国際貨物、格5規模拡張、格6複数貨物地区・道路物流、格7大規模国際貨物ハブの段階解放は、5-20 と既存貨物計画の定義を再利用する。格に到達しただけで施設・契約・便を自動生成しない。

貨物の初期完成範囲は一般貨物を中心にする。郵便、危険物、生鮮品、医薬品、動植物、ベリー貨物、詳細通関、個々の貨物パレット追跡は既存計画の非目標/後続拡張を維持し、別途 PO 判断を得る。

## 7. P3：夜間拠点・航空機整備・設備保守

### 7.1 既存の夜間機能を維持する

docs/44 で実装済みの夜間滞泊・翌朝への持ち越し、拠点契約、航空機周期整備を基礎にする。既存の夜間滞泊は「機体を置く」軽量方式（docs/42 K-5）を維持し、通常の滞泊すべてにWork Orderを必須化しない。

既存の整備能力は、格納庫・整備ベイ・整備士・機体サイズ・周期整備の現行判定を再利用する。新しい作業管理で同じ整備を二重実行・二重課金・二重判定しない。

### 7.2 高度な夜間Work Order

Phase 5 / 5-25 の正本を用い、夜間の作業を段階的に広げる。

| 作業対象 | Work Orderの例 | 影響・管理項目 |
|---|---|---|
| 航空機 | 周期整備、追加点検、故障修理 | 整備士、格納庫/ベイ、部品、翌朝出発可能性 |
| GSE | 車両点検・故障修理・充電 | 車両停止時間、整備人員、翌日の車両稼働率 |
| 滑走路・誘導路 | 舗装/灯火/標識の点検・補修 | 閉鎖区間、代替経路、夜間運航との競合 |
| ターミナル・アクセス | 設備点検、改修、通路工事 | 工事区画、代替旅客経路、営業時間 |
| ライフライン | 電力・燃料・給排水の保守 | 供給停止範囲、予備系統、稼働制限 |

Work Orderは対象資産、作業種別、必要時間、必要人数/資格/設備、資材、優先度、費用、予定/実績時刻、進捗、閉鎖範囲、未完了理由を持つ。初期は個人単位の疲労や詳細資格育成まで扱わず、既存人員・設備モデルに適合させる。

### 7.3 ゲーム性と表示

プレイヤーは翌朝始発便、定期整備、故障修理、滑走路・施設工事の優先順位を決める。夜間要員・格納庫・資材を増やせば作業余力は増えるが、費用と施設投資が必要になる。夜間運航を行う場合は、5-24の滑走路方向・運航可能時間と5-25の資産閉鎖・作業枠を調停する。

建設画面は整備施設の対応サイズ、格納庫/ベイ数、必要人員、夜間作業能力を表示する。経営画面は夜間駐機数/上限、整備対象/整備可能数、Work Orderの予定/完了/延期、翌朝出発可能機数、工事閉鎖予定を表示する。

### 8.2 供給インフラの段階導入

電力・燃料・水・排水・廃棄物は共通の「供給ネットワーク」という概念を検討するが、同じネットワーク型や同じ単位へ無理に統一しない。各ネットワークは固有の設備・接続・流量・供給先・冗長性を持つ。

- まず既存の燃料施設・ハイドラント・給油車・変電等の能力参照を監査する。
- 次に、建物/設備がどの供給源へ接続し、何を消費・排出するかを明示する。
- 供給能力を算出できる設備から有効能力を表示する。実装されていない供給制約を画面だけで演出しない。
- 供給不足時にどの設備を停止・制限するかは、優先負荷・予備系統・プレイヤー設定を含む独立仕様として定義してから実装する。
- 全施設に電力・水等の消費を一度に付与しない。主要な処理施設・サービス施設から導入し、影響範囲と保存互換性を段階検証する。

### 8.3 安全・環境・商業の経営連携

- 消防・救難は、建物の設置数だけでなく車両・隊員・配置・施設までの経路/所要時間を評価する。事故を完全に防止する万能施設として扱わない。
- 環境設備は、実際に処理した廃棄物・汚水・電力等の単位と費用/効果を明確にする。
- 商業設備は、旅客の動線・利用可能区域・営業状態・旅客需要に基づいて売上とサービス評価を算出する。旅客が到達できない店舗に売上を計上しない。
- 商業収入・環境指標・安全評価は、旅客数・空港評価・空港格と混同しない。格への反映は5-20の多軸基準で PO 承認された項目だけに限定する。

## 9. 空港格・施設解放・ゲーム進行

### 9.1 既存の8段階体系を唯一の基準にする

- 格0〜7の名称・昇格条件・連続日数・移行は Phase 5 / 5-20 を正本とする。

- 「格による解放」と「会社設定で機能を有効化」と「施設の建設」と「接続・人員配置・運用開始」は別段階にする。
- 格が上がっても施設・契約・便・車両を自動で配置しない。プレイヤーが投資・契約・配置を選択する。
- サンドボックス・目標なし会社の全解放、既存会社の旧格移行、features ON/OFF の互換性を5-20の基準で保つ。

### 9.3 格の昇格評価

- 施設能力を格の評価軸に用いる場合は、計算式・単位・対象期間・需要の定義・データ完全性が受入済みの指標に限る。
- 未算出能力や、施設を建設しただけの名目能力を昇格条件にしない。
- 同じ実績（旅客数、空港評価、収益等）を複数軸で二重加点しない。
- 貨物取扱・貨物収支は任意のネットワーク/経営評価材料であり、貨物未運営を格昇格の必須条件にしない。
- 上位格で初めて解放される機能を、その格への昇格条件にして循環依存を作らない。5-20 の既存ルールを維持する。

## 12. 互換性・リスク・非目標

### 互換性・リスク

- **保存形式:** 能力メトリクス・実績時系列・Work Order・インフラネットワーク等の永続化要否を個別に判断する。ProjectFile・SCHEMA_VERSION・保存形式の番号を独断で変更しない。旧保存に存在しない実績は推定せず未計測とする。
- **SIM_MODEL_VERSION:** Simulationの旅客・貨物・運航・作業時間・収支・乱数消費に影響する変更はモデル版要否を判断し、旧版の差分・移行・ゴールデンを事前に調べる。
- **opt-in:** 新しい詳細能力・供給制約・Work Order・商業収益は、既存保存の挙動を変えない導入方法を優先する。旧レイアウトに無条件で新コスト/新ボトルネックを付けない。
- **決定性:** 同一seed・入力・実行順で能力・Simulation結果が一致する。能力集計で既存乱数列を消費しない。
- **性能:** 毎tickに全旅客・全施設・全履歴を全走査しない。時系列は有限長/バケット等を検討し、長期運航・大規模マップ・多ターミナルを測定する。
- **共有資源:** 共通道路・通路・駅・車両・人員・電力等の資源を、各ターミナルや機能で重複計上しない。
- **能力の誤認:** 理論能力を実績能力と見せない。名目定員/便を時間当たり能力に変換しない。単位変換は根拠を用意する。
- **ゲームバランス:** 高い格を取得するための設備費・維持費・能力値は、複数難易度・初期レイアウト・複数seedで到達可能性を検証してから確定する。

### 非目標

- 羽田空港の全施設・設備・配置・実能力を完全再現すること。羽田調査は施設候補・構成の参考であり、ゲームの数値は必要に応じて独自のゲーム値とする。
- 現実の航空安全基準・空港消防基準・法令・整備規則・建築基準・環境基準への適合保証。
- 初期から全施設を個別のエンティティ・車両アニメーション・在庫品単位でSimulationすること。
- 貨物・旅客・手荷物を単一の処理モデルへ統合すること。
- ATCモードを経営モードへ組み込むこと。
- PO承認前に全P4施設の価格・収益率・容量・事故軽減率を固定すること。

## 13. テスト・受入方針

- **共通能力:** 正常/境界/異常系、単位、未算出/0/未設置、閉鎖・故障・接続・人員/車両/供給不足の状態をテスト。
- **直列/並列/共有資源:** 直列工程の最小能力、独立並列の合算、共有資源の一度だけの予約を検証。
- **UI整合:** 建設画面の設備値、経営画面の施設値、能力スナップショット/計画値が同一の定義・入力から一致する。
- **Simulation接続:** 能力不足時に実際の待ち・遅延・積み残し・未達が発生し、増設・接続・人員配置で予測どおり改善する。UI表示だけの疑似効果を認めない。
- **ターミナル:** PaxGroup人数保存、工程通過、区画・区域・Step-free・ターミナル帰属、共有通路・バス・アクセスの二重計上を検査。
- **貨物:** 需要→契約→DayPlan→実便→荷役→搬出入→収支/日報の保存式とデータ一貫性。cargo OFFで既存便・旅客・乱数fingerprint不変。
- **夜間:** 滞泊スポット・サイズ・朝の始発、既存整備cycle、Work Order、資源競合、滑走路/誘導路閉鎖、翌朝運航の整合。
- **インフラ:** 供給元・接続・容量・需要の保存式、供給不足・冗長系統・停止時の影響。
- **ゲームバランス:** Normal/Hard/Expert等の難易度、複数初期レイアウト・複数seedで格・設備投資・経営収支・到達日数を記録。
- **保存/決定性:** 保存→復元→継続が連続実行と一致。旧保存・新設定なし・opt-in OFF・長期運航を検証する。
- **E2E:** 建設→接続→稼働→能力不足発生→経営画面で原因特定→設備増設/人員配置→能力改善→運航/旅客/貨物/収支改善まで確認する。

CLAUDE.mdの品質ゲート（typecheck / lint / test / build）を必須とし、UI変更は関連E2E、Simulation/性能変更は決定性・不変条件・ベンチマークを追加する。ゴールデンは合格目的で更新しない。

### 特定した課題

1. **理論/有効の未分離**: 既存 CapacityMetric は capacity 一値のみ。建設中・未接続の施設は facilities 行の state で区別されるが、能力値自体は理論値のまま。有効能力の減額は F6-01 の契約で表現し、既存値は変えない。
2. **実績の所在が分散**: 実績は processPeak（工程）、日報 KPI、hubStats 等に分散。共通契約では adapter が各源を参照し、新たな集計を作らない。
3. **未算出のままにするもの（docs/33 の判断を維持）**: 誘導路区間の回/時、ランプバスの人/時（便/時 × 定員は施設容量としてのみ表示）、アクセスの需要・実績、車両利用率。
4. **二重計上の危険箇所**: アクセス合計（能力なし手段があると全体が未算出になる現行仕様を維持）、貨物トラックの道路消費（集約モデルで一度だけ計上済み。区間モデル接続時に再確認）、共有工程能力のターミナル別合算（5-21 で全空港一度だけ計上済み）。

F6-01 は上記の算出源を adapter で包む共通契約とし、既存計算の値は一切変更しない。
