## 1. 現状と課題

- docs/18 のシナリオ比較は、プレイヤーが条件を変更した複数シナリオを独立実行し、KPIの改善・悪化・同じ・判定不能を比較できる。
- 条件変更案を自動生成し、制約を満たす候補を探索・評価する機能は未実装。
- 現在のシナリオ比較は基盤として再利用できるが、候補生成・目的関数・制約・探索上限・途中キャンセル・採用案の適用は新たに設計する必要がある。
- 「最良案」を単一スコアだけで決めると、定時性を改善する代わりに旅客満足度・費用を悪化させる等のトレードオフを隠す危険がある。

## 2. 目的・対象範囲

### 目的

プレイヤーが指定した目標と守るべき制約に基づき、現在の空港・会社を複製した候補シナリオを自動評価し、実行可能な改善案とその根拠を提示する。

### 対象

1. **最適化条件**
   - 目的プリセット例: 定時性を高める、処理旅客数を増やす、旅客満足度を高める、営業利益を高める。
   - 目的指標と制約指標を分けて選択できる。
   - 制約例: 建設変更なし、追加費用上限、既存契約維持、必要な定時率下限、能力超過禁止。
   - 目標・重み・制約は画面上で確認でき、初期設定を提供する。

2. **探索対象の段階化**
   - MVPでは、既存の設定値・運航計画で調整可能な有限の変数だけを対象にする。
   - 例: 便の時間帯分散、契約便数の組合せ、料金倍率、運用時間、既存の滑走路方向/モード、割当ルール。
   - 建物・滑走路・誘導路などの幾何形状を自動で編集する機能は初期対象外。
   - 対象変数は候補数・値域・刻みを定義し、プレイヤーに見せる。

3. **シナリオ評価**
   - 現在のプロジェクトを不変のベースラインとして保存し、各候補は完全に独立した複製状態で実行する。
   - 同一seed・同一需要・同一期間・同一シミュレーション版を使い、変更要因以外を揃える。
   - 同一候補の評価結果は再実行で一致する。
   - 目的指標の改善だけでなく、制約違反・悪化したKPI・追加費用を併記する。

4. **候補の順位付け**
   - 制約違反候補は実行可能案から除外し、違反理由を表示する。
   - 複数目的の場合はPareto優越関係を残し、単一の重み付き順位だけで情報を失わない。
   - 重み付きスコアを使う場合は、係数・正規化・高低の向きを画面で確認できる。
   - 候補間で同点の場合の順序は決定的にする。

5. **提案の適用**
   - 最適化は提案を返すだけで、現在のセーブへ自動適用しない。
   - プレイヤーが選択した案について、変更差分・影響KPI・追加費用・契約への影響を確認してから適用する。
   - 適用前に保存または複製を作り、元へ戻せるようにする。

6. **実行制御**
   - 最大候補数・最大シミュレーション時間・最大日数・並列数の上限を設ける。
   - 進捗、現在評価中の候補、キャンセルを提供する。
   - UIを長時間ブロックしない。実行環境・ブラウザの負荷を計測し、必要ならWorker化を別タスクとして扱う。

### 非目標

- 初期版で滑走路・ターミナル・誘導路を自律的に新設/撤去する完全自動空港設計。
- プレイヤー確認なしに契約・料金・運用方針・レイアウトを変更すること。
- 一つの万能スコアで「最適」を断定すること。
- 無制限の探索、巨大な候補集合、学習モデルのオンライン学習。
- 最適化結果が実在空港の能力・安全性・収益を保証すること。

## 3. 設計方針

- Phase 8 のシナリオ複製・実行・比較を再利用し、別のシミュレーション実装を作らない。
- Phase 5 の5-19（運航モード）・5-21（ピーク能力）・5-22（共通シナリオ比較）が受入済みであることを前提にする。
- 探索器とシミュレーションを分離する。探索器は候補を列挙し、実行器は同じ条件で候補を実行し、評価器は記録から指標を算出する。
- 決定性を維持し、探索順・候補ID・同点処理を決定的にする。既存simの乱数列に探索乱数を混ぜない。
- 評価指標にデータがない場合はゼロ扱いせず「判定不能」とする。特に docs/33 の未算出能力を推定値で補わない。
- 基本は有限候補のグリッド/段階探索から開始し、性能・品質を確認して探索方式を拡張する。
- 元のプロジェクト・履歴・現在の運航状態を変更せず、候補は一時コピーで評価する。

## 5. 互換性・リスク

- 最適化の途中状態は、初期版では永続保存しない。結果を保存する場合は、入力スナップショット・seed・SIM_MODEL_VERSION・候補定義・実行結果を保存する。
- 最適化の導入だけで既存シミュレーション結果を変えない。運航コアの変更が必要になった場合は別計画に分ける。
- 候補評価で長時間のシミュレーションを繰り返すため、CPU・メモリ・ブラウザ停止リスクがある。候補数と実行期間のハード上限を必須とする。
- 最適化で提案された設定を適用しても、実際の運航結果は再実行で検証する。評価値は将来の運航を保証するものではない。
- 機能ON/OFFで乱数消費・既存ゴールデン・既存セーブの結果が変わらないことを確認する。
