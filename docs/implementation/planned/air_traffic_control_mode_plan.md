## 0. 基本方針・設計上の結論

管制官モードは、既存の空港経営モードのサブ画面・運航設定・会社モードの一種ではなく、**独立したゲームモード**として実装する。画面だけでなく、ゲーム進行・データ・状態ストア・シナリオ・保存形式・評価を分離する。

1. **ゲーム進行**: ATC専用のシミュレーション状態・時計・乱数・イベント・スコアを持つ。経営モードの時計や日次締めを進めない。
2. **ゲームデータ**: 管制官シナリオ・航空機・管制要求・管制指示・通信記録は専用モデルとする。CompanyState、契約、資金、航空会社評価、旅客・手荷物・地上作業タスクを必須依存にしない。
3. **画面・状態管理**: 専用アプリルート・UI・状態ストアを持つ。既存 EditorState の build/operate や OpsState に ATC 状態を追加しない。
4. **保存**: 専用保存形式・保存領域・インポート/エクスポートを持つ。既存 ProjectFile / ProjectFormatVersion に ATC の進行状態を混在させない。
5. **空港データの受け渡し**: 経営モードから利用できるのは、ユーザーが明示的に取り込んだ空港レイアウトの**一回限りのスナップショット**だけとする。会社・契約・便・運航中 SimState を移さず、取り込み元とのライブ同期もしない。
6. **物理シミュレーションの共有**: 静的な空港形状・誘導路ネットワーク・機種寸法・経路探索・滑走路占有など、独立性を損なわない共通ロジックは再利用する。ただし経営用 stepSimulation 全体を ATC の実行エンジンとして直接呼び出さない。

初期リリースは **地上管制（GROUND）＋飛行場管制（TOWER）を一人で担当する単独プレイ**とする。管制官は許可・指示・順序を決め、航空機は指示を受領した後に物理ルールに従って自律移動する。高度・速度・針路を直接操作する本格的な進入管制・レーダーベクターは後続段階とする。

### 0.1 初期実装の推奨既定

| 項目 | 初期既定 | 理由 |
|---|---|---|
| プレイ形態 | 1人・GROUND/TOWER兼務 | 最初の遊び方を明確にする |
| 到着管制 | 到着要求・進入順序・滑走路選択・着陸許可 | 現行の到着状態機械を活用し、高度モデルは後回し |
| 出発管制 | プッシュバック・地上走行・横断・滑走路進入・離陸許可 | 現行の地上走行・滑走路制御を活用 |
| 航空機の応答 | 定型テキストの要求・復唱・実行報告 | 音声合成なしで管制らしい手順を表現 |
| 空港選択 | 標準シナリオ空港、または経営モードからレイアウトのみ複製 | 建設成果を利用しつつ進行・保存を分離 |
| ゲーム目標 | 安全・処理数・待機/遅延・地上走行効率 | 経営の売上・満足度・格昇格と切り離す |
| 時間 | ATC専用固定tick・一時停止・早送り | 経営モードの時間設定・日次処理に依存しない |

上記は実装計画を具体化するための推奨既定であり、実装開始前に PO が最終確認する。未決事項は §9 にまとめる。

### 1.1 再利用できる資産

| 領域 | 現行実装 | ATCでの扱い |

| 空港レイアウト | AirportLayout、滑走路・誘導路・スポット・施設の安定ID | 読み取り専用スナップショット |
| エアサイドネットワーク | AirsideNetwork、ノード/エッジ、一方通行、滑走路入口・横断ノード | 派生ネットワークを再構築 |

| 滑走路 | 方向、運用モード、占有、進入予約、直前運用、間隔判定 | 物理占有・予約の正本として利用 |

### 1.2 現状のままでは完全分離にならない理由

- 現行 EditorState は mode が build / operate の二択であり、company と ops を同じ状態ストアに持つ。ATCをここへ追加すると経営モードと状態管理が結合する。
- 現行 Simulation.stepSimulation は、経済処理・契約便生成・滑走路制御・航空機状態遷移・旅客・ランプバス・アクセス・手荷物・地上作業・分析を一つのループから呼び出す。ATCからそのまま実行すると不要な経営・旅客・作業系の依存が入る。
- 現行 Aircraft / Flight / SimState は、到着便と出発便の折り返し、CompanyState、旅客・作業・手荷物を前提とする箇所がある。ATCの唯一のドメインモデルに流用しない。
- 現行 ProjectFile は layout・company・catalog・scenarios・任意の運航中 sim を一体として扱う。ProjectFile に ATC セッションを追加すると保存境界が曖昧になる。
- 現行 App.tsx / TopBar は CompanyBadge、建設/経営/運行ページ、OpsNav、日次締め等に依存する。ATC画面を同じレイアウトへ継ぎ足さない。
- 現行管制塔レベルは src/core/safety.ts に能力評価値があるが、管制官の処理・指示・担当数を制御する機能ではない。その値を根拠なく実運用の上限として使わない。
- Phase 5 / 5-19 の「空港全体運航・ターミナル単独詳細シミュレーション」は旅客動線・ターミナル能力の分析モードであり、本計画の管制官ゲームモードとは別機能である。時計やシナリオの仕組みを混同しない。

### 1.3 実装前に監査する既存制御

現行 simulation.ts 内の runwayControl、stepInbound、stepReadyForPushback、stepAircraft 等には、自動許可・予約・移動の判断が含まれる。departureBlocked / approachBlocked 等の判定も同ファイル内の関数・状態に依存する。

実装前に次を特定する。

- 滑走路の許可と予約、物理占有がどの関数で確定するか。
- 到着機の進入許可・滑走路予約・接地・滑走路離脱の順序。
- 出発機のプッシュバック・経路予約・誘導路走行・holdShort・lineUp・takeoff の遷移条件。
- 滑走路横断の連鎖予約、交差滑走路の従属運用、予約解放、不変条件の責務。
- taxiMode が従来方式 / block 方式のときの差と、既存ゴールデン・フィンガープリントの対象。
- 手動指示を導入しても既存の自動運航判断が実行されない／変わらない境界。

推測で関数を再実装せず、既存コード・テスト・Docsを照合してから共通化する。

## 2. 目的・対象範囲

### 2.1 目的

- 管制官として航空機の要求を受け、許可・待機・経路・順序を判断するゲーム体験を追加する。
- 滑走路・誘導路・スポット・機体寸法・交通競合を使い、安全性と処理効率の両立をゲームとして成立させる。
- 経営モードで建設した空港も、静的レイアウトを複製して管制シナリオに使えるようにする。
- 経営モードのセーブ・運航結果・経済・日次履歴・プロジェクト進行を変更せず、別セッションとして保存・再開できるようにする。

### 2.2 初期対象（ATC 1.0）

**管制対象**
- 到着機: 空港管制圏への到着要求、到着順序、使用滑走路、最終進入開始、着陸許可、着陸復行、着陸後の地上走行指示。
- 出発機: 出発準備完了要求、プッシュバック許可、地上走行許可、停止指示、滑走路横断許可、滑走路手前待機、滑走路進入/整列許可、離陸許可。
- 滑走路: 運用方向・到着/出発/混合/閉鎖、占有・予約・直前運用、交差滑走路の競合。
- 誘導路: 運用中/閉鎖、一方通行、機体適合、経路選択、区間容量、対向交通、停止位置。
- 交通管理: 到着順序・離陸順序、待機時間、滞留、滑走路・誘導路のボトルネック。
- 通信: 要求、許可、復唱、実行開始・完了・拒否を定型テキストで記録。
- 評価: 安全性、処理数、遅延、待機時間、地上走行効率、要求への応答時間。

**初期版の簡略化**
- 到着機はシナリオで定義した進入境界から出現し、到着要求を出す。高度・上昇/降下・針路ベクターは扱わず、進入経路はシナリオの固定経路/簡略な進入状態で扱う。
- 出発機はスポットに駐機した状態から開始する。旅客搭乗・手荷物・給油・清掃・整備・GSEの実作業は行わず、出発可能時刻や準備完了条件はATCシナリオ側で与える。
- 航空機は管制指示の復唱後、許可された範囲で自律移動する。速度・舵・エンジンを直接操作する操縦ゲームにはしない。
- 初期版は単独プレイヤーがGROUND/TOWERを兼務する。複数管制官間の引継ぎ・マルチプレイは対象外。
- 3D管制室・実音声・音声認識は初期対象外。既存2D空港マップを管制用に拡張する。

### 2.3 非目標

- 経営モードの代替・統合、会社経営、資金、建設費、航空会社との契約、需要・路線誘致、格昇格、日次収支。
- 旅客グループ、チェックイン、保安検査、搭乗、手荷物、ランプバス、旅客満足度。
- GSE・地上作業員の配置や整備工程そのもの。ATC初期版は出発準備完了の通知を受け取る簡略モデルとする。
- 高度・速度・方位の連続値を使う本格レーダー管制、SID/STAR、空域セクター、隣接空港との調整。
- 現実の航空管制資格・実運用・安全基準への適合を保証すること。ゲーム用の簡略モデルとして明示する。

## 3. 独立アーキテクチャ

### 3.1 アプリケーション境界

- アプリ最上位に「ゲームモード選択」を設け、「空港経営」と「管制官」を別のアプリルートとして起動する。
- 現行の経営側 App / EditorState / editorStore / OpsState / ManagementPage / OperateLayout は経営モード専用のまま維持する。
- ATC側は専用の AtcApp / AtcStore / AtcSession / AtcLayout を持ち、EditorState.mode に atc を追加しない。
- 経営モードとATCモードは同時に進行させない。モードを離れると当該モードの時計を停止し、戻ったときはそのモードの独立した保存/メモリ状態から再開する。
- ATCから経営モードへ戻る導線は「モード選択へ戻る」とし、経営側の「建設モードに戻る」と混同しない。
- 経営モードの CompanyBadge、ManagementPage、DayReview、DayFlow、日次締め、建設費精算、会社設定 UI は ATC 画面に表示しない。

### 3.2 データモデル

| 型（候補名） | 主な内容 |
|---|---|
| AtcAirportSnapshot | 複製した AirportLayout、元レイアウト識別情報、取り込み時刻、静的データ参照版 |
| AtcScenarioDefinition | シナリオID、名称、空港スナップショット、開始時刻、交通パターン、天候、難易度、seed、目標・評価条件 |
| AtcSessionState | ATC専用時計、乱数、航空機、管制要求、指示履歴、滑走路/誘導路運用状態、イベント、統計 |
| AtcAircraft | 機体ID・機種ID・コールサイン・便表示、到着/出発、現在状態、位置・方位・経路・待機理由・次の要求 |
| AtcRequest | 要求ID、機体ID、要求種別、発生時刻、期限、必要な応答、要求中/対応済み等 |
| AtcClearance | 指示ID、対象機体、指示種別、滑走路/経路/停止位置、発行時刻、有効期限、状態 |
| AtcEvent | 要求・指示・復唱・実行・拒否・取消・警告・安全違反の時刻付き履歴 |
| AtcScore / AtcReport | 安全指標、処理数、遅延、待機、地上走行、シナリオ達成度 |

- AtcAircraft は経営用 Aircraft / Flight を唯一の正本として参照しない。折り返し便ID・会社契約・旅客・地上作業タスクがなくても動作する。
- 機種ID・寸法・滑走路/誘導路適合は既存の静的機種カタログとの互換アダプタを検討する。数値を二重管理しない。
- AirportLayout はスナップショットとして複製し、AirsideNetwork 等の派生データはロード時・開始時に再構築する。派生キャッシュを保存しない。
- 時計は整数ゲーム秒または固定tickで管理する。ATC時計を CompanyState.day / DayFlow / 日次締めに接続しない。
- seed と乱数ストリームはATC専用とし、経営運航の RNG state を共有しない。

### 3.3 共通物理コアと依存禁止

**共有候補**
- geometry、layout、AirportLayout、AirsideNetwork の生成
- 滑走路幾何・番号・機体適合
- 機種の寸法・性能データ
- 誘導路経路探索・運用中エッジ判定
- 滑走路の物理占有、進入予約、必要間隔、交差滑走路の従属判定
- taxiBlocks の区間分割・容量・向きロック・予約・解放・デッドロック検出

**ATC側から直接依存させない領域**
- core/economy / CompanyState / Finance / Contract / airline evaluation / airport tier
- passengers / baggage / apronBus / ground task / GroundUnit / turnaround
- dayloop / daily settlement / management KPI / journal / management scenario result
- editorStore / EditorState / OpsState / projectActions / ProjectFile の更新処理

現行の地上移動・滑走路制御は経営用シミュレーションと同じファイルにまとまっているため、T4で物理コアの抽出境界を監査する。共通化のために既存の経営用ループを全面書き換えない。既存挙動の保持が難しい場合は段階抽出し、回帰ゲートを通せない大規模変更は分割・保留する。

**単一情報源の原則**
- 滑走路の物理占有・予約は共有物理コアの一箇所だけで管理する。
- 誘導路区間の占有・方向ロック・ノード予約も一箇所だけで管理する。
- AtcClearance は指示・許可を示すものであり、物理占有の代替データではない。
- UI用に複製した状態を安全判定の正本にしない。指示実行時はコアの最新状態から再検証する。

### 3.4 管制要求・指示のライフサイクル

- 要求: 航空機が管制官へ応答を求める情報。例: プッシュバック、地上走行、滑走路横断、滑走路進入/離陸、到着・着陸要求。
- 指示/許可: 管制官が航空機へ与える行動範囲。例: 指定経路の走行、停止位置までの走行、横断、滑走路進入、着陸、離陸、待機、復行。
- 状態例: requested → issued → readback → accepted/executing → completed。拒否・取消・期限切れは別の終端状態とする。
- 指示には対象機体・指示種別・経路/滑走路/停止位置・発行時刻・有効期限・一意の連番を持たせる。
- 同じ要求への二重許可、古い要求への許可、対象機体が状態遷移した後の許可を防ぐ。
- 指示取消は未実行指示と実行中指示を区別する。実行中の機体を安全に止められない場所では、取消を受理したように見せず、安全に停止できる位置まで継続させる。
- 復唱は発行済み指示の内容と一致するかを検証する。初期版は定型文で表現し、音声認識を必須にしない。
- AI航空機は決定的な規則で要求・復唱・実行応答を返す。管制官が操作していないのに許可が自動で出ることはない。

### 3.5 安全判定

管制指示はUIのボタン制御だけで安全化しない。コア側に独立した判定関数を置き、発行時と実行直前の両方で再検証する。

| 指示 | 必須判定 |
|---|---|
| プッシュバック | 機体が駐機中・出発可能、スポットと接続経路が有効、必要な最初の区間を原子的に確保できる |
| 地上走行 | 指定経路が連続した運用中ネットワーク、機体サイズ/一方通行/閉鎖/区間容量/対向交通/予約に矛盾なし |
| 停止 | 安全に停止できる位置を特定し、滑走路・交差点・停止禁止区間上に停止させない |
| 滑走路横断 | 対象滑走路が占有/予約されていない、交差滑走路・連続横断の必要な全予約が可能、向こう側に安全に抜けられる |
| 滑走路進入/整列 | 運用方向・モード・機体適合、物理占有・予約・到着進入との競合なし |
| 離陸 | 滑走路が使用可能、先行機間隔、交差滑走路制約、天候・閉鎖・機体適合を満たす |
| 着陸/進入 | 滑走路が到着運用可能、進入予約・先行機・離陸/横断との必要間隔、滑走路離脱経路を確保 |
| 着陸後の地上走行 | 滑走路を安全に離脱でき、出口から指定スポットへの経路が成立し、横断・予約・区間容量に矛盾なし |

- 滑走路占有・予約・誘導路区間占有・ノード予約の既存不変条件を維持する。
- 判定結果は「許可可能 / 条件付き・警告 / 許可不可」と理由コードで返す。物理安全のハード制約はプレイヤーが無視して強行できない。
- 指示発行後に閉鎖・天候・他機予約・競合が変わった場合、実行開始前に再判定する。失効時は理由を表示し、再許可を求める。
- 滑走路横断は既存の連鎖予約・交差滑走路の一括確保を維持し、部分予約で滑走路上に機体を閉じ込めない。
- 指示拒否はまず理由を理解・再計画できるフィードバックにする。危険な強制操作による例外経路は作らない。

## 4. 画面・ゲームループ

### 4.1 画面構成

| 領域 | 表示 |
|---|---|
| 上部ステータス | ATC時刻、時間倍率、一時停止、風/天候、使用滑走路、交通量 |
| 中央マップ | 滑走路、誘導路、スポット、航空機位置/方位、停止位置、閉鎖、予約/占有、指示経路 |
| 左側リスト | 到着要求、出発要求、地上走行中、待機中、管制応答待ち |
| 右側詳細 | 選択機のコールサイン、機種、現在状態、要求、待機理由、次に必要な操作 |
| 管制操作 | プッシュバック、走行、待機、横断、滑走路進入、着陸、離陸、復行、経路変更 |
| 下部通信 | 要求、管制指示、復唱、実行報告、拒否理由、警告履歴 |
| 終了/評価 | シナリオ目標、処理数、安全評価、遅延、平均待機、終了レポート |

- 初期版は2D表示を正とし、既存Viewport/描画資産を再利用してATCオーバーレイを追加する。
- 航空機の選択はマップと航空機リストで双方向に同期する。
- 現在位置だけでなく、許可済み経路・次の停止位置・未処理要求を区別して表示する。
- 色だけに依存せず、テキスト・アイコン・凡例でも状態を識別できる。
- 表示を絞っても要求自体を消さず、未処理件数と一覧から再選択可能にする。

### 4.2 時間・進行

- ATC専用固定tickで進行し、UIの実時間・描画フレーム数に依存しない。
- 一時停止・1倍・早送りを設ける。初期版の倍率は操作可能性と描画負荷を測定して決め、経営モードの倍率設定をそのまま流用しない。
- 管制官が未処理の間も航空機は許可済み範囲内で移動・待機し、許可が必要な境界では必ず停止する。
- 時間を進めるたびに要求/指示の期限、滑走路/誘導路の占有、警告を更新する。
- 同じseed・同じコマンド列なら同じ結果とイベント履歴を再現する。

### 4.3 シナリオ・交通生成

- ATC専用シナリオは、空港スナップショット、交通量/時間帯、到着・出発便の時刻、機種、コールサイン、使用可能滑走路、天候、seed、目標を持つ。
- 便の生成はATCシナリオが行い、経営の航空会社契約・路線需要・契約更新・会社の便計画を使わない。
- 航空会社名はシナリオの表示ラベルとして任意に付けられるが、CompanyState や航空会社評価のIDを必須にしない。
- 初期シナリオはチュートリアル（低交通量・単滑走路）、到着集中、出発集中、滑走路交差、誘導路混雑、複数滑走路の基本セットを用意する。
- 交通生成の負荷・出現順はseedで固定し、同じ入力から同じ要求列を得られる。
- 空港レイアウトの条件不足（運用可能な滑走路なし、スポット/誘導路未接続、機種適合なし等）は開始前に検出し、理由を提示する。問題を黙って補正しない。

## 7. 互換性・保存・モデル版

### 7.1 保存境界

- ATC専用ファイル型を AtcSessionFile とし、専用の形式版 ATC_SAVE_FORMAT_VERSION を持つ。
- ATCの保存先は経営プロジェクトの保存キー/一覧から分離した IndexedDB データベースまたは専用オブジェクトストアとする。推奨は **skyport-atc 専用DB**。
- ATCのセッション一覧・オートセーブ・JSONエクスポート/インポートは専用ストレージAPIから操作する。
- 経営モードの SAVE_FORMAT / PROJECT_FORMAT_VERSION / ProjectFile / localStorageのスロット一覧は、ATCデータを理由に変更しない。
- 空港スナップショット取り込みは経営プロジェクトの検証済みデータから layout のみを取り出す。取り込み元の会社・契約・sim・scenarios・journal・日次履歴は無視し、ATC側で独立に再検証する。
- derived network / route cache / UI選択状態は保存しない。ロード時にスナップショットから再構築する。

### 7.2 バージョンとゴールデン

- ATC専用モデルの変更は ATC_MODEL_VERSION / ATC_SAVE_FORMAT_VERSION で管理し、既存 SIM_MODEL_VERSION と混同しない。
- 既存の経営用シミュレーション結果が変わらない共通ロジックの抽出は、既存の版ルールに従い、legacyFingerprint・goldenで不変を証明する。
- 共通物理コア変更により既存経営レイアウトの運航結果が変わる場合、CLAUDE.md と docs/42 §5 に従い、原因・変更前後の主要KPI・対象ゴールデン・旧進行中セーブへの影響を示し、PO判断を得る。テスト合格目的の期待値・ゴールデン更新は禁止。
- ATCだけの機能追加で PROJECT_FORMAT_VERSION / SCHEMA_VERSION / SIM_MODEL_VERSION を便宜的に引き上げない。

## 9. PO確認事項・実装開始ゲート

本計画は設計を進めるために既定案を置いている。実装開始前に次を最終決定し、計画書へ判断と理由を記録する。

1. **空港の入手方法**: 標準シナリオを初期搭載し、経営モードの保存ファイルからは「レイアウトのみを複製」してATC空港を作る方式を推奨。ライブ同期は行わない。
2. **初期担当範囲**: 1人でGROUND/TOWERを兼務し、進入順序・着陸許可・地上管制・離陸許可を扱う。高度/方位/速度を使うAPPROACH/DEPARTUREは後続段階。
3. **ゲーム進行**: 時間制限付きシナリオ、一定時間のフリー運航、到着/出発の波を扱うチャレンジを候補とする。初期は短いチュートリアルと定型シナリオを優先。
4. **難易度**: 交通量・天候・使用可能滑走路・誘導路障害で調整する。理不尽な安全違反や根拠のない罰則は導入しない。
5. **管制塔レベル**: 初期版では能力表示/参考情報に留める。レベルを理由に指示を自動拒否する上限値は、実測・ゲームバランス検証後に採用する。
6. **評価**: 安全性はハード評価、処理量・遅延・効率はスコア評価として分離する。安全性を発着数で相殺しない。
7. **実装順**: Phase 5 のターミナル/旅客基盤とは別トラックで管理する。実装開始日・優先順位は計画完成だけでは確定せず、POが着手を指示した時点で planned → active に移す。
