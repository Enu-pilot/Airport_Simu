## 3. 進め方（体制と手順）
- 指示・統合: Fable ／ 設計・重要レビュー: Opus ／ 実装: Sonnet ／ 調査・監査: Haiku。
- 各段階: Fable が分割 → Opus が設計（コード変更なし）→ Sonnet が小さなステップで実装（ステップごとにコミット・push）→ Haiku が独立監査（リポジトリの写しで実行、読み取りのみ）→ Opus が差分レビュー → 修正 → PR。
- 同じ技術的エラーが 2 回続いたら Opus に原因分析を依頼。設計変更は勝手に進めない。
- 使用量の上限で実装役が止まることがある。小さく検証してコミット・push し、止まったら中断箇所から再開する。

## 4. 守ること（PO のルール）
1. 既存のセーブデータ（レイアウト v1/v2/v3、プロジェクト v1/v2、運航中の状態）が読める。
2. 既存のレイアウト・プロジェクトの運航と検証の結果を変えない。`tests/golden` の既存ファイルはバイト一致（新しい仕組みは新しいデータ・設定があるときだけ動く opt-in。新規ゴールデンは新しいファイルで追加し、`sim-versions.json` の台帳に記録）。
3. 既存テストの期待値と既存の e2e spec を、テストを通すために編集しない。
4. `SIM_MODEL_VERSION` は上げない（保存中の運航状態が破棄されるため）。`SCHEMA_VERSION` は 3、プロジェクトの版は新しい項目を使うファイルだけ 2。
5. 実機の値（出典つき）とゲーム値を区別し、推定値を公式値として扱わない。実際の航空安全基準への適合を保証する表示をしない。
6. 2D と 3D は同じデータ・同じ形状（`frames`・`surfaces`）から描く。core は ui/render に依存しない。core で `Math.random`・`Date.now` を使わない。
7. コミットメッセージの末尾に `Co-Authored-By` と `Claude-Session` の 2 行。モデル名をコードやコミットの他の場所に書かない。
8. push・PR は PO の指示に従う（現在: 段階ごとに PR を作成、マージは PO が行う）。
